## 〇、溯源归因：四缺陷分层定谳（全部实证确认）

### 缺陷① 巡检异常静默降级 PASS —— **成立（代码 + 运行时双证）**

| 层 | 结论 |
|---|---|
| 现象 | 巡检报 `verdict=PASS`，但内部某规则实际执行失败 |
| 直接原因 | `run_check` 的兜底 `except Exception` 一律置 `detected=False`（`quality_orchestrator.py:132-134`） |
| **代码缺陷** | 异常**未进入判定链**：`generate_report` 只看 `detected` 与 `level`（`L147-148`），异常信息仅写入 `details` 文本 ⇒ `verdict` 仍可为 `PASS` |
| **运行时实证** | 本机实跑 `scripts/quality_orchestrator.py --check` ⇒ `verdict=PASS, detected=0`，而 `cloud_parity` 规则 `details='检查异常: Command [...] 失败'` ⇒ **异常被吞、PASS 照出** |
| 业务边界 | 设计上 L1 异常应升级为 FAIL/告警；当前实现与设计意图不符 |
| 隐性风险 | 与缺陷③叠加：**「未实现规则」+「异常吞掉」双重静默**，巡检可长期报绿而实际几乎未检测 |

### 缺陷② eps_backfill 判定 bug（空输出当「检出」）—— **成立（实验复现）**

| 层 | 结论 |
|---|---|
| 直接原因 | `result["detected"] = "gap=0" not in output`（`quality_orchestrator.py:108`）——**反向包含判定** |
| 代码缺陷 | ① 未校验 `returncode`（已存入 `result["exit_code"]` 但**从不使用**，`L110`）；② 未看 `stderr`；③ 空输出（崩溃/超时/缺库）落于 `""` ⇒ `"gap=0" not in "" == True` ⇒ **判为「检出」** |
| **实验实证** | 真实复现：`backfill_eps_gap.py --check --db <不存在库>` ⇒ `returncode=2`、`stdout=''`、`stderr='数据库不存在…'` ⇒ orchestrator 判定式给 `detected=True` ⇒ **把「运行失败」当成「检出缺口」**（假阳性）；反向地，崩溃/超时同样落入「检出」，而**真缺口**与**假运行失败**无法区分 |
| 业务边界 | 「检出」语义应为「数据缺口存在」，不含「工具运行失败」——两者须分流 |
| 隐性风险 | 与缺陷①方向相反的双错：规则①**失败→PASS（漏报）**，规则②**失败→检出（误报）**；同一模块两种相反的错误方向，掩盖真实状态 |

### 缺陷③ 规则库缺 6 表行数/水位检查与阈值定义 —— **成立（两项均有权威依据）**

| 层 | 结论 |
|---|---|
| 直接原因 | `QUALITY_RULES` 共 **7 条**，**无一条含阈值字段**（字段集仅 `level/description/detection/repair/tool`）；行数/水位类检查仅 `cloud_parity` 一条且为**外部脚本透传** |
| **权威缺口依据** | `scripts/verify_v2_cloud_parity.py:4` 载明口径（总调度 2026-09-12）：**「64 表 ≥1 日期对拍 + 高风险 6 表 ≥3 日期」**；`:22 HIGH_RISK = {cyq_chips, ths_daily, ths_hot, sw_daily, stk_factor_pro, …}`；`:28 HIGH_RISK_DATES = 3` ⇒ **6 表清单与「≥3 日期」阈值在仓内已存在，但未进巡检规则库** |
| 代码缺陷 | 巡检规则库与既有对拍权威口径**未对接**：6 表无独立规则、无行数/水位阈值、无日期覆盖数要求 |
| **附带发现（更严重）** | `run_check` 内**只有 5 条规则有实际检查分支**；`timestamp_normalize`、`minute_front_rewrite`（**2 条 L2 规则**）**无任何分支** ⇒ 结构性永不执行检测，却计入报告 `total_rules` ⇒ **造成「覆盖完整」错觉** |
| 业务边界 | 「规则声明」≠「规则已实现」≠「规则已通过阈值」——三者当前混为一谈 |

### 缺陷④ 巡检时机/通道与 daemon 锁冲突 —— **成立（结构缺失 + 环境实测依据）**

| 层 | 结论 |
|---|---|
| 直接原因 | 模块**无时机/通道设计**：无空档窗协议、无锁探测/退避、无与 daemon 的排程耦合 |
| 环境事实 | 本项目已实测（项目记忆「duckdb 跨进程锁事实」）：**库被任一进程打开时（含只读），其他进程以读写打开立即失败**；daemon 为唯一写者且轮次内持库 ⇒ 巡检在 daemon 活跃期运行必遇冲突面 |
| 现状连接方式 | `gap_heal` → `duckdb.connect(read_only=True)`；`eps_backfill` → 子进程 `--check`（内部 `read_only=True`）；`cloud_parity` → 外部脚本透传（连接方式不由本模块决定）⇒ **只读侧相对安全，但无锁探测与退避**；而 **L1 自动修复路径（写）**若在 daemon 活跃期执行，冲突面显著放大 |
| 隐性风险 | 与缺陷①叠加：锁冲突异常被吞成 `PASS` ⇒ **「因锁冲突而没检查成」被误报为「检查通过」**——这正是客户观察到的 FAIL/异常静默现象之一种 |

## 一、背景与动机

客户在 `E:\quantstudio` 部署上运行质量巡检（`quality_orchestrator` v0.1），报告四个缺陷面。经主仓独立复核：**四缺陷全部成立**，且发现两项附加问题（未实现规则、异常方向相反的双错）。核心危害是**「巡检可信度」**：当前巡检可同时出现
- **漏报**（规则异常/未实现 → 照出 PASS），
- **误报**（工具运行失败 → 当成检出），
- **覆盖幻觉**（未实现规则计入 `total_rules`），
- **环境性失败被静默**（daemon 锁冲突 → 吞成 PASS）。

⇒ 巡检结论**不可作为数据健康的判据**。这与本项目既有铁律（异常显性化、禁静默降级）冲突，且客户已在真实部署上被误导（客户侧临时口径已由调度给出：FAIL 系误报，数据未检出异常）。

## 三、任务拆解

### T1 异常显性化（缺陷①）

- `run_check` 返回值增加 **`status` 三态**：`ok`（检查已执行且未检出）/ `detected`（检出）/ **`error`**（检查未完成：异常、超时、锁冲突、脚本非零退出且非「检出」语义）；
- `generate_report` 判定升级：**任一规则 `error` ⇒ verdict 至少 `WARN`；L1 规则 `error` ⇒ verdict `FAIL`**（异常不再静默）；
- `details` 保留异常原文，并新增 `error_kind`（如 `lock_conflict`/`timeout`/`tool_error`）便于分流；
- **锁冲突识别**：复用既有 busy 串族判别（`Could not set lock on file`/`Conflicting lock is held`/`could not lock`）⇒ 归为 `error_kind=lock_conflict`。

### T2 eps_backfill 判定修正（缺陷②）

- 判定改为**契约化**：`--check` 的输出契约明确为 `gap=<int>`；
  - `returncode == 0 && gap == 0` ⇒ `ok`（无缺口）；
  - `returncode == 1 && gap > 0` ⇒ `detected`（真缺口）；
  - `returncode == 2`（缺库/参数错）或**任何非 0/1 退出**或**输出解析失败**或**空 stdout** ⇒ **`error`**（工具运行失败，**不得**计入「检出」）；
  - `stderr` 非空时进入 `details`，不参与「检出」判定但参与 `error_kind`；
- **禁止**保留 `"gap=0" not in output` 这类反向包含判定（改为正则解析 `gap=(\d+)`）。

### T3 规则库补齐（缺陷③）

- **新增 6 表行数/水位规则**（数据源＝`verify_v2_cloud_parity.py` 的 `HIGH_RISK` 与 `HIGH_RISK_DATES=3`）：
  - 规则形态：每表一条（或一条参数化）——检查**行数守恒/水位/日期覆盖数 ≥3**；
  - **阈值字段显式化**：新增 `threshold` 字段（如 `dates_min: 3`、`row_delta_tol`），规则库从「只有描述」升级为「**可机读阈值**」；
- **实现状态显式化**：每条规则新增 `implemented: true/false`（或 `status`）；`timestamp_normalize` / `minute_front_rewrite` 当前**无检查分支** ⇒ 标 `implemented=false` 并在报告中单列「未实现规则」段，**不再计入「已覆盖」**；
- `--list-rules` 同步输出实现状态与阈值。

### T4 时机/通道设计（缺陷④）

- **只读优先**：巡检全部检查路径统一 `read_only=True`（现状 `gap_heal`/`eps_backfill` 已只读；`cloud_parity` 透传需显式声明并加只读断言）；
- **锁探测 + 退避**：巡检启动时先做轻量锁探测（尝试只读连接 + 短超时），命中锁冲突 ⇒ `error_kind=lock_conflict` + 按配置退避重试 N 次，仍失败则**显性报 error（不报 PASS）**；
- **空档窗协议**：写路径（L1 自动修复）**禁止**在 daemon 活跃期执行——前置 daemon 活性判定（复用既有 daemon 身份校验设施），活跃即拒绝并提示走空档窗（既有「窗协议」：停旧 daemon → 空档窗内跑只读/修复 → 起新代际）；
- **排程钩子（可选，建议）**：与既有每日巡检/晨检排程对接，避免与 daemon 轮次高峰重叠（配置项，不改排程器本身）。

### T5 回归与验收设施

- 新建 `tests/test_quality_orchestrator.py`：四缺陷各自一条回归钉（见 §五）；
- 证据件落 `docs/evidence/`。

## 五、验收要点

### 功能验收（四缺陷逐条）

| # | 判据 |
|---|---|
| ① | **注入异常**（模拟锁冲突/子进程崩溃）⇒ `verdict` **不再是 PASS**（L1 ⇒ FAIL；非 L1 ⇒ WARN），`details` 含异常原文与 `error_kind` |
| ② | 三种 eps 场景分流正确：`gap=0`→ok；`gap>0`→detected；**缺库/崩溃/空输出/解析失败→error（不计检出）**；且 `returncode` 参与判定 |
| ③ | 6 表规则存在且带**可机读阈值**；`--list-rules` 显示实现状态；**未实现规则单列**且不计入已覆盖 |
| ④ | 锁冲突场景 ⇒ `error_kind=lock_conflict` + 显性 error；写路径在 daemon 活跃期被拒并提示空档窗；外部脚本路径改为可配且不可达报 error |

### 场景验收

- 本机（daemon 运行中 / 停止后）两种状态各跑一次巡检，verdict 与 error 分流符合预期；
- 客户环境等价模拟（路径不可达、无 daemon）⇒ 报 error 而非 PASS/误报。

### 边界验收

- 既有 5 条「已实现规则」的判定结果**不因本批改动而变**（除异常路径外）；
- `backfill_eps_gap.py` 输出契约不变（仅在 orchestrator 侧解析）；
- 不改 daemon/水位/写通道语义。

### 回归与防回归

- `tests/test_quality_orchestrator.py` 四缺陷回归钉全绿；
- 相关既有套件全绿（含 `test_writer_channel_contract` 等写通道契约测试——本批不触写通道）；
- **防回归**：每条缺陷至少一条「构造故障 → 断言不静默」用例（如注入异常须见 FAIL）。
