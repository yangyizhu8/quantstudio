## 1. 问题定义

### 1.1 现象

项目当前推进呈现"二叉树式问题蔓延"：

- 解决一个问题 → 冒出几个新问题，问题产出速率 > 解决速率；
- 传导链条：本地数据质量 → 云端数据质量 → DuckDB 数据质量 → 策略代码双端对齐；
- 某策略双端对齐解决后，下一个策略又不对齐；数据修复又反过来影响已对齐的策略；
- 数据修复（重拉、批量修复）锁库数小时至数十小时，阻塞所有并行任务（实证：`docs/evidence/backtest-align-golden-20260817.md` 中"主库被后台任务独占、备份被 reanchor 任务占用"）；
- 多会话并行（ZCode×3 + DeepSeek-harness×3）无共享权威状态，互相踩踏。

### 1.2 根因（结构性，非执行层失误）

| # | 根因 | 后果 | 实证 |
|---|---|---|---|
| R1 | **数据无版本化、无冻结基线** | 无法回答"该策略当时用哪份数据对齐的"；任何数据改动使历史对齐结论失效 | smallcap 源切换后 57 笔→59 笔、final_asset 偏 390.68 元，历史结论失效 |
| R2 | **以双端回测结果（极高噪声信号）作为数据层改动的验收标准** | 回测差异含数据源、复权、include 语义、撮合、拒单等多个自由度；修一处、结果随机变动，被误判为新问题 | pr6a 基线漂移分析 |
| R3 | **各层无独立验收标准，问题跨层透传** | 数据层缺陷直达策略层；策略层修复反向"追认"数据变化 | 同上 |
| R4 | **读写不分离，长事务锁库** | 一锁数十小时，并行全停；会话中间状态过期后产生新分歧 | backtest-align-golden 取证（主库独占 + 备份被占） |
| R5 | **并行度超过协调能力，无问题登记与串行修复机制** | 发现即修、修中带修，缺乏优先级与关单判定 | — |

### 1.3 修复目标

- 建立使问题从"二叉树蔓延"变为"线性队列收敛"的治理机制；
- 数据改动对下游的影响**可判定**（黄金基线回归）、数据状态**可追溯**（快照版本）；
- 消灭锁库对并行任务的阻塞（读写物理隔离）；
- **不改变**现有撮合/资金/订单/复权等回测引擎行为，不改变已对齐策略的结论有效性。

## 2. 改动范围（四项核心措施）

> **命名约定（审计 B3）**：数据管线验收层命名为 **D1–D4**，与既有引擎保真门禁 Fidelity L1–L4（`docs/strategy-compiler/strategy-fidelity-regression-gate.md`）严格区分，避免同名歧义。

### 2.1 措施一：数据版本化 + 黄金基线冻结（最优先，治本）

#### 2.1.1 数据快照版本

- 每次全量拉取 / 增量同步 / 批量修复入库完成后，产出**不可变快照**：
  - 快照标识：`SNAP_<yyyymmdd>_<seq>_<content_hash8>`；
  - **快照覆盖范围（审计 B4，按性能铁律第 1 条先梳理完整取数调用链后确定清单）**：回测实际读取的**全部**库文件与配置，至少包括：DuckDB 主库（含 stock_dividend 公司行为表）、复权辅助库 `data/qfq_aux.db`、`data_config.json` 等取数配置；只拷主库会漏掉复权因子，基线不可复现。实施第一步即产出"回测取数调用链 → 消费文件清单"作为快照清单依据；
  - **content hash 采用逻辑内容 hash**（导出后聚合/拼接 hash，复用 `mcp_protocol_probe.md` 中 concat_sha256 先例），不用库文件字节 hash——DuckDB checkpoint 后字节变化但数据等价，字节 hash 不稳定；
  - 快照清单文件（JSON）：快照 ID、生成时间、覆盖文件、逻辑内容 hash、来源任务 ID。
- 策略回测、巡检脚本、对齐验证**必须绑定快照 ID** 运行；回测产出的结果目录记录所用快照 ID，使任何历史结果可复现。
- **"逐字节一致"的适用范围声明**：逐字节一致仅指**回测产物**（trades.csv / daily_stats.csv / 净值 / 审计日志行）；数据层等价性以逻辑内容 hash 判定。两处措辞全文严格区分。
- **存储策略（审计建议 4，与既有备份机制合并，不建第三套）**：复用现有 `.bak_*` 备份习惯与磁盘公式（5×main + 2×aux + max(10GiB, 20%×(main+aux))，见 `b6-post-cutover-observation-runbook.md`），全量副本快速落地、滚动保留 N=3。

#### 2.1.2 黄金基线

**与既有黄金资产的关系（审计 B2）**：项目已有策略层黄金回归与冻结资产——`scripts/etf_t0_regression.py`（零差异档 + 归因档双档方法学，`docs/evidence/etf-t0-g2-regression-20260816.md` 已实践）、`scripts/benchmarks/run_golden.py`、Fidelity 门禁（`strategy-fidelity-regression-gate.md`）、P0 双库基线冻结产物（`output/mcp_migration/P0_baseline/`）。职责分工：

| 资产 | 职责 |
|---|---|
| P0_baseline 冻结 | 迁移前**一次性**状态冻结（历史档案） |
| Fidelity L1–L4 门禁 | 引擎实现保真（策略层，持续） |
| **本方案基线** | **数据层持续治理**：数据/管线改动对回测产物的影响判定 |

本方案新增脚本**必须复用/扩展现有 manifest + comparator 双档方法学**（以 etf_t0_regression.py 的双档结构为模板），不另造比较器；基线产物目录与 P0 冻结目录概念分开、互不覆盖。

- 选定 2-3 个代表性策略 × 固定区间 × 固定快照，产出：trades.csv、daily_stats.csv、净值序列、关键审计日志行（`QS_REBALANCE_AUDIT` / `QS_FILL_AUDIT`），存入 `output/golden_baseline/`（记录 hash，不入 git 大文件）。
- **基线策略与区间选型（审计建议 1，风险提示）**：`etf_theme_rotation_quantstudio.py`（含 2026-07 取证区间）+ 1 个股票日线策略（复用 smallcap 系列）+ 1 个分钟 Profile 策略。注意：① 2026-07 分钟数据有已知缺口（07-17 无分钟数据；smallcap 分钟仅 19 个交易日且 5 天不完整，见 `profiling_report_smallcap_phase4_20260812.md`）——分钟策略基线区间**避开已知缺口日**，或显式登记缺口为已知噪声；② 基线冻结时刻的数据源状态必须显式记录（xtquant 单源锁定 2026-07-21 已定）。

**判定规则**：

- 任何数据层/管线层改动后，必须重跑黄金基线：**回测产物逐字节一致** → 改动在基线策略覆盖范围内无害，**覆盖范围内**下游免审（覆盖范围外的策略按登记制另行评估，"免审"不得被误读为全量豁免——审计建议 2）；**不一致** → 必须先归因到具体表/字段/日期/证券，禁止直接修改策略代码去"追认"新数据；归因不清即回退改动。
- 该机制是现有 AGENTS.md 性能优化铁律（行为等价性验收）向数据层的自然扩展。

**合法 re-baseline 例外流程（防呆②补全——只有禁止没有例外的规则最终会被绕道执行；项目已有合法先例：pr6a 中 tushare→xtquant 源切换即合法 re-baseline 而非追认）**：

- **触发条件（仅限二类）**：① 数据源切换且切换本身已经批准与归因；② 数据修正经独立确认（如 601628 单位修正类，有明确错误证据）。**严格排除**："为让回测通过而改数据/改策略"的一切情形；
- **批准人**：审计方 + 用户，**执行会话无自判权**；
- **记录要求**：re-baseline 原因、旧基线 hash、新基线 hash、证据文档归档于 `output/golden_baseline/rebaseline_log/`；协议格式**扩展自** `docs/strategy-compiler/zcode-handoff-20260721.md` §11 黄金基线变更协议（既有先例来源，本方案不另创规则）。

#### 2.1.3 基线建立的完整闭环（防呆①操作化——审计补全）

1. **量化门槛（审计：无门槛则"通过 D2/D3 验收"无法执行）**，参照 `docs/qfq-production-enablement-checklist.md` bootstrap"必须 0 blocked"先例：
   - D2（QuestDB→DuckDB 入库）硬门槛：行数对账差 = 0；抽样 diff 主键命中率 100%、数值字段容差 0；空值率 ≤ 既有 `config_lint`/`quality_audit` 规则阈值（以现行规则值为准，不新造宽松阈值）；blocked 项 = 0；
   - D3（数据质量巡检）硬门槛：巡检报告异常项 = 0 个未登记项（已知缺口/公司行为群必须先登记为已知噪声，剩余未解释异常 = 0）；
   - 门槛检查结果作为证据归档进 `output/golden_baseline/` 同目录。
2. **基线建立窗口期数据冻结**：从 D2/D3 验收通过 → 基线产出并双跑确认期间，**写入会话暂停一切数据改动**（唯一写入会话挂起队列），这是防呆①的完整闭环。
3. **基线自证可复现**：基线产出后，同快照 ID 重跑一次，回测产物必须逐字节一致。
4. **观察期**：基线建立后 24–48h 观察期，期间该基线工单不关单（防隐性依赖未暴露）。

### 2.2 措施二：分层验收，各层只对自己负责（D1–D4）

| 层 | 验收标准（本层内可判定） | 现有资产复用 |
|---|---|---|
| **D1** 云端→QuestDB 同步 | 行数对账、日期覆盖、schema 一致、空值率、主键唯一性 | collector_tasks / 同步管线日志 |
| **D2** QuestDB→DuckDB 入库 | 与源行级抽样 diff、标准化规则 lint（硬门槛见 §2.1.3） | `config_lint` / `qfq_invariant` / `quality_audit` / `source_capabilities` |
| **D3** DuckDB 数据质量 | 数据巡检报告（停牌日、公司行为跳变、边界样本；硬门槛见 §2.1.3） | `scripts/audit_etf_corporate_actions.py`（另案已审） |
| **D4** 回测↔PTrade 对齐 | **只验"差异可解释、可机械对照"，不验"结果逐点一致"** | `QS_FILL_AUDIT` 计划-实际对照（另案已审） |

**关键原则**：D4 的验收目标明确为"差异可解释"。两端数据源不同，净值逐点一致在物理上不可能；追求它等于自己制造无限问题。

### 2.3 措施三：读写物理隔离，消灭锁库阻塞

- **读走快照物理副本**：回测、巡检、审批会话一律读取**快照的物理副本文件**；**禁止 ATTACH/打开任何正在被写入的库文件**——DuckDB 单写多读模型下，对正在写入的库做只读打开会拿锁失败（`r5_clone_db.py` 注释中的"只读 ATTACH 被锁的源库"是特例场景，不可作为通用保证——审计 B5）；
- 只读 ATTACH 仅适用于**快照副本**与**确认无写者时段**的库，此约束写入脚本实现要求；
- **写走单线程**：数据重拉、批量修复集中到**唯一写入会话**（排它 + 任务队列），其余会话全部为只读消费者；
- **长任务准入**：预估执行 >1 小时的写任务，开锁前必须产出**影响面预估**（涉及表、日期段、预期黄金基线差异），评估通过才允许执行；
- 队列状态记录于实时进度报告，供全部会话可见。

### 2.4 措施四：收敛并行度 + 问题登记制

- 并行度从 6 会话降为 **1 写 + 2 读** 共 3 会话（**分阶段：先 4 后 3**，避免与当前排期硬冲突），其余问题排队；
- **问题登记制**：新发现问题一律先进登记表（字段：编号、现象、疑似根因、涉及层级 D1–D4、发现时间、状态），**禁止"发现即修"**；
- 每个迭代只从登记表按优先级取 1-2 个问题修复；修复完成必须过黄金基线回归才能关单；
- **单层修复原则**：一次修复只允许动一层（数据修复不得同时动策略代码，反之亦然），跨层修复必须拆分为独立工单串行执行；
- 登记表为独立文件（JSON/Markdown，模板含上述字段），落于实时进度报告同目录，进度报告以引用方式关联——登记表是通用治理资产，不隶属 MCP 项目专属档案，同时**不取代**进度报告的唯一权威地位（审计建议：确认此分工）。

### 2.5 文档同步（铁律要求）

- `README.md`：数据管线章节补充"快照版本、黄金基线、分层验收（D1–D4）、读写隔离"说明；

## 3. 明确不纳入本次改动的范围

| 事项 | 原因 |
|---|---|
| 回测引擎撮合/资金/订单/复权行为 | A 股正确语义，本方案零行为改动（继承性能铁律） |
| 云端数据源本身的质量问题 | 属 D1 上游，只能通过验收标准暴露并登记，由数据源侧修复 |
| PTrade 端 API 语义（include、序列差异） | 无本地数据可复核，维持外部核对清单机制 |
| 已对齐策略的重跑 | 基线建立后按需复现，不在本方案强制重跑范围（重跑会产生新差异噪声） |

## 4. 影响面分析

- **代码/脚本**：新增快照管理脚本（`scripts/snapshot_manager.py` 或等价管线钩子）、黄金基线回归脚本（**复用 etf_t0_regression.py 双档方法学**，非另造）、问题登记表模板；快照物理副本读取的取数入口参数化（实施前先梳理完整取数调用链——性能铁律第 1 条）；
- **行为影响**：回测结果零变化（读取同一数据内容的物理副本）；数据内容不因本方案改变（快照是副本，不修改数据）；
- **风险点**：
  - ① 快照存储成本（主库 14.3GB + aux 2.6GB，实测冻结基线字节数见 b6 复审包）→ 已并入既有备份磁盘公式、滚动保留 N=3（§2.1.1）；
  - ② 只读副本访问与现有连接代码兼容性 → 实施前核对全部取数调用点，参数化改动不触碰查询语义；
  - ③ 基线依赖当前数据状态 → 已由 §2.1.3 量化门槛 + 窗口期冻结 + 自证复现闭环覆盖；
  - ④ 流程纪律依赖约束 → 写入 AGENTS.md 规则固化（§2.5）。

## 5. 验收标准

1. **快照机制**：一次全量入库后产出快照 ID 与清单（含 qfq_aux、stock_dividend、配置文件）；回测结果目录记录快照 ID；同快照 ID 重跑黄金基线策略，回测产物逐字节一致（可复现性 = 基线自证）。
2. **黄金基线回归**：基线回归脚本对 2-3 个代表策略输出 PASS/FAIL + 归因档：
   - PASS 用例：修改一张**回测不消费的表**的数据（审计建议：比"仅追加快照元数据"更有意义）→ 回归 PASS；
   - FAIL 用例：修改某日某 ETF 价格 → 回归 FAIL 且 diff 归因定位到具体表/日期/证券。
3. **读写隔离**：写入会话执行长任务（重拉/批量修复）期间，只读会话通过**快照物理副本**正常完成一次黄金基线回测，全程不打开正在写入的库文件（不依赖"被锁库的只读 ATTACH"特例）。
4. **登记制运行**：登记表模板落地，首批存量问题（含 2026-07 对齐取证外部核对清单 4 项）完成登记入队。
5. **现有测试全量通过**，且回测相关单元测试无回归。

## 6. 实施顺序（审计通过后；已按审计 B1 重排——基线必须建立在快照之上）

1. 取数调用链梳理 → 快照清单确定（回测消费的全部库/配置文件）；
2. D2/D3 硬门槛检查脚本化 + 当前数据通过门槛（含已知噪声登记）；
3. **快照版本机制落地**（先于基线——否则基线无法绑定快照 ID）；
4. **在通过验收的快照上建立黄金基线**（窗口期写入冻结 → 产出 → 自证复现 → 24-48h 观察期）；
5. 读写隔离改造（快照物理副本读取）+ 写入单线程队列 + 长任务准入；
6. 问题登记表 + 并行度分阶段收敛（6→4→3）；
7. 文档同步（README / 引用文档 / AGENTS.md 规则固化）；
8. 验收证据文档 → 用户确认 → 双仓库推送。

> 顺序设计原则：**门槛 → 快照 → 基线 → 隔离**，四者先于一切新修复——不做这四项，后续任何修复都不可判定。

## 7. 回退条件

- 快照/基线/登记表均为**增量机制**：删除脚本与快照文件即回退，无数据行为残留；
- 快照物理副本读取若与现有调用点冲突，回退为直连模式（仅损失隔离能力，不影响正确性）；
- 若黄金基线回归机制本身产生误报（无害改动被判 FAIL）且两周内无法归因稳定：暂停强制回归、降级为人工抽查；**降级过渡规则（审计建议 3）**：降级期间数据层改动**全部**走人工抽查（不是暂停一切数据工作，但每一项改动须人工审阅影响面后放行），直至基线问题修复并恢复强制回归。
