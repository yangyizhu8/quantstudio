## 二、双因证据链

### 因一：分钟任务排程在「盘前」，当日分钟数据尚不存在（**结构性**）

| 时刻 | 事件 | 证据（`data/logs/daemon.log`） |
|---|---|---|
| 06:42:19 | `mcp_etf_minutes` START | `[mcp_etf_minutes_mcp_20261109_064219_bc7a12] === START task=mcp_etf_minutes table=etf_minutes/1min` |
| 07:31:59 | `mcp_stock_minutes` START | `[mcp_stock_minutes_mcp_20261109_073159_5f25de] === START task=mcp_stock_minutes table=stock_minutes/1min` |
| 07:31 | etf_minutes **完成** | `✅[streaming] raw=8517183 aligned=8517183 passed=8512667 rejected=4516 written=2284263` |
| 09:24 | stock_minutes **完成** | `✅[streaming] raw=18874638 aligned=18874638 passed=18874638 rejected=0 written=1286838` |

**关键**：两任务**在 07:31 / 09:24 即已收工**，而 A 股当日分钟数据要到 **15:00 收盘后**才完整 ⇒ 本次拉取窗口内**不含当日**（写库 `new 0 + upd …` 全为历史更新，`new=0` 侧面印证无新日期）⇒ **当日必然 0 行**，且**盘后无任何补跑班次**（15:00 后日志无分钟任务 START）。

### 因二：daemon tick 空转（每 5 分钟重复初始化，无退避）

| 证据 | 读数 |
|---|---|
| `15:00 后 tables initialized` | **70 次**（`15:02 / 15:07 / 15:12 … 23:30`·间隔恒 5min = `check_interval=300s`） |
| 伴随异常 | `06:30` 有 `MCPExportBudgetError: export_exceeds_time_budget hint=split the request: narrow time_start/time_end, filter ts_codes, or lower row_limit`（**命中该错的任务是 `mcp_llm_text_events_enriched_pt`，非分钟任务**——如实修正：分钟链未直接命中预算错） |
| 00:22 他线 once（stock_minutes） | `00:43→01:10` 连续 **约 27 分钟** `0 rows (skip)` 心跳后才写出 50,000 行 ⇒ **空转重试无退避**的另一实证面 |

⇒ **因二定性**：tick 层**每 5 分钟无条件重跑初始化**，遇错/遇空**不退避、不跳过、不降频** ⇒ 夜窗持续噪声，且**掩盖了「盘后无补跑」的真实缺口**（看起来 daemon 一直在动）。

## 三、判型（铁律 18）

- **主型：纯恢复型**——修复目标是「让本应每日采到的当日分钟数据被采到」，不改任何口径/契约/字段语义
- **附型：新增检测型**——因二的「预算/空错退避 + 盘后缺口告警」属新增能力（会让原本静默的缺口开始报警），方案阶段单列
- **不属数据修正型**（不改变既有已入库数据的正确性口径）

## 四、三修法对比

| 修法 | 内容 | 优点 | 缺点/风险 | 我方倾向 |
|---|---|---|---|---|
| **M1 盘后补跑班** | 新增独立「盘后分钟班」（如 `15:40` 起），只跑 `mcp_etf_minutes`/`mcp_stock_minutes`，与主轮解耦 | 语义最清晰；不扰动现有轮次；可独立开关/回退 | 需新增排程槽与去重（防与主轮并发） | **首选** |
| **M2 轮内第二班** | 主轮 `06:00` 之后加「盘后第二段」（同轮内顺序执行） | 无需新排程概念 | 主轮已 5-7h；加段会拖长并挤占夜窗；失败耦合 | 次选 |
| **M3 export 分片 + 预算错退避** | 分钟 export 按 `time_start/time_end` 窄化分片；遇 `MCPExportBudgetError` 指数退避（而非每 5min 撞） | 直接治因二；对大盘分钟量大表必要 | 单独做**不解决当日缺口**（因一未修） | **必须并入 M1/M2**（治因二） |

**推荐组合**：**M1（治因一） + M3（治因二）**，M2 作为 M1 不可行时的备选。

## 五、验收标准（可机检）

1. **当日分钟入库**：修复后首个交易日 `stock_minutes`/`etf_minutes` 的**当日**行数 > 0，且 `max(time)` **≥ 15:00**（下限；候⑪ 六时点取样后可上移，见 §7.3）——校验方式 `ORDER BY time DESC LIMIT 1` 取 max(time) 并比对当日日期
2. **连续 3 个交易日**均达标（防单次偶然）
3. **盘后班存在证据**：`daemon.log` 出现盘后分钟的 `=== START task=` 与其 `✅[streaming]`
4. **tick 空转消除**：`tables initialized` 在无任务窗口的频次 **≤ 轮次边界次数**（不再每 5min 一次）；遇预算错**只报一次并退避**（日志可见退避间隔递增）
5. **无回归**：日线/其它表当日数据不受影响；`pytest tests/` 相关段全绿

## 六、回退条件与手段

- **回退触发**：①修复后出现日线/其它表回归；②盘后班与主轮并发导致 DuckDB 写锁冲突；③分钟表出现 `invalidated`
- **回退手段**：①盘后班独立开关（env/配置项 `QS_MINUTE_POSTCLOSE_ENABLED=0`）立即停用；②M3 退避参数可归零（`QS_MCP_BUDGET_BACKOFF=0` 恢复原行为）；③主轮排程不变 ⇒ 回退后回到当前态（**不劣于现状**）

## 九、交易日判定口径约束（2026-11-10 14:50 补·⑪ 通传）

**凡判「交易日」必须带 is_open**——SELECT COUNT(*) FROM trade_calendar WHERE cal_date BETWEEN ? AND ? **会把周末计入**，导致把非交易日误判为交易日。

本件相关的正确写法：

`sql
-- ✅ 判区间内交易日（带 is_open）
SELECT cal_date FROM trade_calendar WHERE cal_date BETWEEN ? AND ? AND is_open ORDER BY cal_date;
-- ✅ 判单日是否开市
SELECT is_open FROM trade_calendar WHERE cal_date = ?;
-- ⚠️ 只有「自然日缓存完整性」判定才数自然日（不带 is_open，语义正确）
SELECT COUNT(*) FROM trade_calendar WHERE cal_date BETWEEN ? AND ?;  -- 与 _natural_day_count 比对
`

**我方域核查结论（2026-11-10 14:50）**：qfq_calendar.py 三处判交易日均正确带 is_open（:282-283 列表、:302/:314 单日判定）；:97 _range_fully_covered 不带 is_open 属**故意的自然日完整性判定**（对照 82-85 _natural_day_count）⇒ **零缺陷**。另 coverage_gate.py:156、writers.py:1632 亦带 is_open ✓。
