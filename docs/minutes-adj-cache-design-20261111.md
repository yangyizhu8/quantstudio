## 零、一句话

**每批 shard 都重复做一次「标准化 5,224 行 adj_factor + 注入 qfq_aux.db」（12.2 分钟），而因子缓存容量只有 8（需求 65）导致命中率恒 0%——两处都是配置/作用域问题，不触及判据，改动可逆。**

### 2.1 改动②的实际实施（2026-11-11 02:28，+23/−4 行）

```python
# 原（L3361）
_QFQ_FACTOR_CACHE_MAX = 8

# 改后（L3359-3380）
_QFQ_FACTOR_CACHE_ENV = "QS_QFQ_INVARIANT_FACTOR_CACHE"
_QFQ_FACTOR_CACHE_MAX_ENV = "QS_QFQ_FACTOR_CACHE_MAX"
_QFQ_FACTOR_CACHE_MAX_DEFAULT = 512
_QFQ_FACTOR_CACHE_MAX = 8  # 保留旧常量（回退语义/外部引用兼容），实际容量走 _qfq_factor_cache_max()

def _qfq_factor_cache_max(self) -> int:
    """缓存容量上限：env 覆盖 > 默认 512。非法值/异常一律回落默认（fail-safe）。"""
    import os as _os
    raw = str(_os.environ.get(self._QFQ_FACTOR_CACHE_MAX_ENV, "")).strip()
    if not raw:
        return self._QFQ_FACTOR_CACHE_MAX_DEFAULT
    try:
        v = int(raw)
    except (TypeError, ValueError):
        return self._QFQ_FACTOR_CACHE_MAX_DEFAULT
    return max(1, v)

# 消费点（L3413-3418）：循环外读一次，避免每次迭代读 env
_cache_max = self._qfq_factor_cache_max()
while len(cache) > _cache_max:
    cache.popitem(last=False)
    ...

# 日志增强（L3421-3423）：size=%d → size=%d/%d（便于下轮直接看容量是否生效）
```

### 3.1 定性（铁律 18 分型）

**⇒ 「纯性能型」**（可观察结果不变）。
- 验收标准：**同一轮次的入库结果逐位一致**（行数、内容、水位全部相同）
- 任何数据差异 ⇒ 验收失败立即回退

### 3.2 改动①的 V3 前提验证 —— **已执行，结论不成立（改动①作废）**

**前提**：同轮次同 `(table, freq, asset_type)` 各 shard 的 `adj_factor` **值**相同。

**验证结果（2026-11-11 01:12，QuestDB 直查 20 万行/天 × 3 天）**：
```
2026-10-19 vs 2026-10-27（共同 code 5,222）：
  相同 5,110 / **不同 112（2.1%）**
  688809: 1.0016 → 1.4022（差 40%）
⇒ ❌ 前提不成立 ⇒ 改动①作废
```

**⇒ 正确做法（若将来要做）**：按 shard 实际时间窗缓存（key 含 lo_ms/hi_ms），而非全局一次。**但那正是改动②已经在用的设计**——所以不必重复实现。

### 3.3 改动②的容量取值依据（已实测，非估算）

**测量结果（2026-11-11 01:50，`adj_factor` 3,221 万行表）**：
```
单次有效查询（有数据窗口）：约 2.2 秒
  10-19→10-20: 1.975s  5,571 条
  10-21→10-22: 2.124s  5,572 条
  10-27→10-28: 2.271s  5,568 条
  11-06→11-07: 2.286s  5,574 条
索引：idx_adj_factor_code_time ON adj_factor(code, time) 存在
```

**⇒ 容量取值依据**：
| 依据 | 值 |
|---|---|
| 一轮需求 | **13 shard × 5 adj_table = 65 个不同 key** |
| 默认值 | **512**（远超 65，留余量给跨轮/多表场景） |
| 回退 | `QS_QFQ_FACTOR_CACHE_MAX=8` = 改动前行为 |
| 实测 hit/miss/evict | `hit=0 miss=65 evict=57 hit_rate=0.0% size=8`（改动前）|

**⇒ 缓存项类型**：`_load_factor_lookup` 返回 `Dict[Tuple[str,str], float]`（code, bar_day）→ adj_factor，**是小字典不是 DataFrame** ⇒ 512 项内存可忽略。

### 3.4 🔴 改动②的真实收益（实测，第二次下调）

**测量结果**：
```
65 次 miss × 2.2s ≈ 143s = 2.4 分钟
缓存生效后（65 → 13 次）可省 ≈ 114s = **1.9 分钟**
占 5,035s 的 **1.9%**
```

**⇒ 收益仅 1.9%，远低于本方案初版的「10-30%」估算（已作废）。**

**⇒ 但仍执行的理由（总调度 2026-11-11 裁甲）**：**「一个设计好的缓存机制因容量配错而完全失效」本身是缺陷**，1.9% 只是附加收益。

**⇒ 方案取「默认 512 + env 可调」，实施时按实测类型定最终默认值。**
