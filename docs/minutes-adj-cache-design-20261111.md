### 1.3 改动 ②：因子缓存容量不足（hit_rate 恒 0%）

**代码实测**（`daemon.py`）：
```python
L254:  _qfq_factor_cache = None          # OrderedDict[(table, lo, hi, codes_fp)] -> lookup
L3361: _QFQ_FACTOR_CACHE_MAX = 8         # ← 容量 8
L3392-3406:  命中则 move_to_end + hit+=1
             未命中则 miss+=1, 计算, 写入 cache
             while len(cache) > MAX: popitem(last=False); evict+=1
             每批打一条 hit/miss/evict/hit_rate 日志
```

**日志实测**：
```

```

**⇒ 因果链闭合：需求 65 个键 > 容量 8 ⇒ 每批写入即 evict ⇒ 命中率恒 0%。**
**⇒ 这不是「键值设计错」，是**容量不足**。**

## 三、影响面评估（铁律 18 纯增益三问）

| 问 | 答 |
|---|---|
| **影响其他功能？** | 改动①只影响 mcp 流式路径的 shard 循环；改动②只影响缓存容量。**不动任何判据/校验/对齐逻辑。** |
| **影响回测性能？** | **不改回测路径**（这是采集侧）。采集更快 ⇒ 对回测是**间接利好**（数据更早可用）。 |
| **影响回测精度？** | **不降**。两处都不改数据内容：① adj_factor 值不变（只是不重复算）；② 缓存只存查询结果，容量大了命中率升，值不变。 |

### 3.1 定性（铁律 18 分型）

**⇒ 「纯性能型」**（可观察结果不变）。
- 验收标准：**同一轮次的入库结果逐位一致**（行数、内容、水位全部相同）
- 任何数据差异 ⇒ 验收失败立即回退

### 3.2 关键风险：**改动①的正确性前提**

**前提**：同一轮次内，同一 `(table, freq, asset_type)` 的所有 shard，其 `adj_factor` 集合**完全相同**。

**⇒ 这个前提**必须实测验证**，不能假定：**

```python
# 验证方式（实施前必做）
for df_shard in shard_iter:
    a = normalize_mcp_adj_factor_df(df_shard, freq, asset_type)
    hashes.add(hash(a[["code","time","adj_factor"]].to_csv(index=False)))
# 若 len(hashes) == 1 ⇒ 前提成立，可缓存
# 若 > 1 ⇒ 前提不成立，本改动作废
```

**⇒ 若前提不成立**（不同 shard 的 adj_factor 不同），则改动①改为「按 shard 首尾时间窗缓存」，而非全局一次。

### 3.3 改动②的内存风险

**⇒ 每个缓存项是什么？** 注释写 `-> lookup`，需在实施时确认类型。若为小 dict/标量，512 项可忽略；若为 DataFrame，需控制在 64-128。

**⇒ 方案取「默认 512 + env 可调」，实施时按实测类型定最终默认值。**
