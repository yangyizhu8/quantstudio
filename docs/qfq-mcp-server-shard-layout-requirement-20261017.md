## 1 需求（一句话）

**MCP export 的分片布局，请由「按数据量顺序切分（`part_000NN` 纯序号）」改为「按证券码分区」，或提供「每码 → 分片」索引。**

## 2 现状与实测成本结构

**客户端读取路径**（`mcp_adapter.py:1296-1347` `_read_ckey_filtered`）：对每个 ckey **遍历全部 shard_paths**，逐文件 `pd.read_parquet(filters=[(code_col,"in",want)])`；谓词下推只能跳过**文件内的行组**，**无法跳过文件本身**。

**分片命名实测**（`data/mcp_landing/_export_cache_manifest.json`）：
```
j_<jobid>_<table>_part_00000 … part_00050
```
⇒ **纯序号，无码段/时间编码 ⇒ 客户端无法据此跳过任何文件。**

**实测读数**（单实例单周期 70 单元，全 STOCK，只读日志）：

| 项 | 读数 |
|---|---|
| 每次读触达分片数 | 均值 **41.4**（中位 51；51 出现 5121 次、26 出现 2637 次） |
| 每次读耗时 | **0.412 s**（中位 0.430） |
| 每分片固定开销 | **6.6–7.1 ms**（恒定） |
| 每次读行数 | 均值 392、中位 482 ⇒ **每分片仅约 9.5 行** |
| 每单元读次数 | **121.0**（`stock_minutes` 111.7 + `stock_daily` 9.3） |
| ⇒ 分片触达/单元 | **121 × 41.4 ≈ 5,011** |
| ⇒ 外推耗时 | **5,011 × 6.9 ms ≈ 34.6 s/单元**（实测 `2a shard_read` **49.9 s/单元**，偏差 31%，量级成立） |

**判别器结论（一次分离两个假设）**：

| 变体 | 分片数 | 行数 | 耗时 |
|---|---|---|---|
| 基线 | 51 | 482 | 345.2 ms |
| A1 | **6** | 58 | **42.3 ms** |
| B2 | 51 | **48,200** | **363.5 ms** |

⇒ **分片数 6→51（×8.5）⇒ 耗时 ×8.2（近似线性）**；**行数 ×100 ⇒ 耗时 ×1.1（几乎无影响）**。
⇒ **成本 ＝ 分片触达次数 × 约 6.9 ms，与行数无关**。⇒ 开销**全在文件打开/元数据/行组扫描**，不在反序列化。

## 3 期望收益（一阶）

**若服务端按码分区（或提供每码索引）**：每次读只需触达 **1–2 个分片**（该码所在分片）：

| 项 | 现状 | 按码分区后 |
|---|---|---|
| 分片触达/单元 | 5,011 | **121**（降 **97.6%**） |
| 外推耗时/单元 | 34.6 s | **0.8 s** |
| 削减倍数 | — | **约 41×** |

## 4 为何必须服务端做（客户端四候选已全部出局，实测）

| 候选 | 判定 | 实测依据 |
|---|---|---|
| (a) `(ckey,code)` 小 memo | ❌ 跨单元零命中 | **70 单元 ＝ 70 个不同 code**（`000900`…`002012` 无一重复）⇒ 过滤结果逐单元不同 |
| (b) 缓存全市场帧 / 提高 `_SHARD_CACHE_MAX` | ❌ 违反内存约束 | 全市场帧 **46.4 MB/条目**（p50 59.96）；191 条目 ＝ **8.9 GB**（`_SHARD_CACHE_MAX` 现仅 30） |
| (c1) 放宽 ckey 粒度 | ❌ 不可行（会静默丢数据） | 2 天窗口是**尺寸驱动**：`safe_window = row_limit/(daily_rows×1.2)`（`:900-906`），受服务端 **`_EXPORT_ROW_LIMIT_BIG = 5_000_000`**（`:807`）约束；超限时「服务端按最老优先**静默截断（批尾丢数据）**」（`:887` 原文） |
| (c2) 每码分片索引 | ❌ 客户端不可实现 | 分片名纯序号；`_read_ckey_filtered` 遍历全部分片，谓词下推无法跳文件 ⇒ **须服务端** |

⇒ **客户端实施项已归零**。本需求即唯一杠杆。

## 5 二阶收益：解开「水位永不推进」的死循环（**同等重要**）

**实测因果链**（全部有代码/DB 出处）：

1. applying 逐单元取全历史 ⇒ 单轮 4,783 单元 × **61.2 s** ≈ **3.4 天**；
2. 而 cycle 实测仅存活数小时即被中断/替换（最近 8 个 cycle：**5 个 `started` 从未 finished**、3 个 `interrupted`）；
3. `begin_cycle` 用**随机 UUID** 生成 `cycle_id`（`qfq_resident_orchestrator.py:289`），且注释逐字写明 restart 语义（`:283-286`）⇒ **每次重启新建 cycle，不续跑**；
4. 新 cycle 把上一轮 `pending` 水位意图统一标 `superseded`（`:287` / `:341-381`）——**只改 status，不动 `source_watermark`**（**清障 ≠ 推进**）；
5. ⇒ **水位永不推进**：`stock_daily` 水位冻在 **2026-09-03**（落后实际数据 43 天）、`etf_daily` **09-04**、`stock_minutes` **2026-03-31**（约 6.5 个月）；
6. ⇒ `_get_safe_watermark`（`daemon.py:2917-2947`）**只防「水位领先」不防「水位落后」** ⇒ 陈旧水位原样成为增量锚点 ⇒ **每轮从 09-03 重拉 43 天**（`defer_watermark` 内 W3 告警原文已写明此后果）。

**⇒ 服务端 41× 兑现后**：applying 34.6 s → 0.8 s/单元 ⇒ 单轮 ≈ **1.1 小时** ⇒ **cycle 可在单窗内跑到 finalize** ⇒ gate 通过 ⇒ `_commit_or_hold_watermarks` 推进水位 ⇒ **重拉消失**。

⇒ **一阶收益＝applying 提速 41×；二阶收益＝水位自愈 + 重拉消失。二者同源。**

## 6 验收工具（可复用，改动前后对照）

本轮的**判别器与对账方法**可直接作为服务端改动前后的验收工具：

1. **判别器微基准**：对同一磁盘命中路径，分别变动「分片数」与「行数」，确认改动后**耗时随分片数线性下降**而不再触达全部分片；
2. **对账公式**：`分片触达/单元 ＝ 读次数 × 均值分片数`，与日志 `PROFILE_2a shard_read` 聚合值对账（容差按实测 31% 量级）；
3. **作用域纪律**：聚合前必须**只取单实例单周期**的 `PROFILE_*` 行（混算两周期会得出负的秒/单元）；
4. **不得重复相加**：`PROFILE_2a shard_read` 与 `PROFILE_2a_pushdown` 是**同一操作的两层计时**（计数同为 8472、耗时 3490.5 vs 3482.8 s），**不得相加**。

## 7 约束（服务端方案须遵守）

1. **不得要求客户端缓存全市场帧**（违反 `:1444` 防 OOM 取舍）；
2. **不得以放宽 `row_limit` 换取更少批次数**——超限即**静默截断丢数据**（`:887`）；
3. 若改为按码分区，须同步给出**该布局下的分片命名/索引规则**，使客户端可据此**跳过**非目标分片；
4. 现有 `export_cache` 磁盘层命中语义（manifest 判定 / size 校验 / 空窗墓碑 / TTL）**不变**。

- **实证读数**：2026-10-13 → 10-19（7 天）同型冲突 **12 次**，且撞的 key **七天一次没变**——
  `mcp_etf_minutes` 恒撞 `159512 @ 2026-09-11 09:30`、`mcp_stock_minutes` 恒撞 `000055 @ 2026-09-07 09:30`；
  两 key 时刻**均 ≥ 各自表的陈旧水位（2026-09-04）**。

- **⇒ 与本需求的关系**：本需求的二阶收益兑现后，**该规律应同步消失**（不再反复重写旧 bar）。
  ⇒ **W-1 的「重试能力」仍值得具备**（任何冲突都整轮丢分钟数据，候选源仅 `mcp` 无兜底），
  **但其紧迫性应在二阶收益落地后重估；不得在水位缺陷未修时把 W-1 当根因独立实施。**
