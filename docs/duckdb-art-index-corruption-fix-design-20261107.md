## 1 问题定义（现象 · 证据 · 影响）

### 1.1 现象（Obs-2 实测，2026-11-07 15:2x）

```
06:03:11 ERROR [mcp_etf_daily_...] ❌ FAILED[streaming]:
  FATAL Error: Corrupted unique ART index "PRIMARY_etf_daily_0":
  encountered an existing gated leaf in unique index while inserting
```

随后全部连带失败（同进程）：
- `[DuckDBWriter] spill 兜底设置失败: FatalException: database has been invalidated because of a previous fatal error`
- `[Watermark] get_last_date 读失败（按无水位处理）: 同上` ← **W5 仪器首次捕获 ③b**
- `[mcp_stock_minutes] 无锚点（首次/升级后）⇒ 增量退化为「建基线」全量拉取 2026-01-01→2026-11-07（≈310 天，≈4.8 亿行）`
- `QFQ post-ingest 异常（水位保持，下轮重试）`

### 1.2 后果链（为何这是 P0）

| 层 | 后果 |
|---|---|
| **存储引擎** | `etf_daily` 唯主键索引（ART）损坏 ⇒ **该表写入必 fatal**（`existing gated leaf`）⇒ 每轮重演 |
| **进程** | DuckDB fatal ⇒ **进程级句柄全失效**（`database has been invalidated`）⇒ 该轮后续所有读写失败 |
| **水位** | 写失败 + 水位读失败 ⇒ 不提交 ⇒ **水位永久冻结**（`etf_daily` 冻在 09-04） |
| **降级链** | 判「无锚点」⇒ `stock_minutes` **自动**进入 310 天全量重建（≈4.8 亿行/数小时~数十小时） |
| **与链① W1 的关系** | **W1 改 gate 救不了写失败** ⇒ **P0 不修，W1 无意义**（W1 呈裁待本项目修复后再裁） |

### 1.3 当前健康实态（15:3x 实测，用于设定修复基线）

| 项 | 读数 |
|---|---|
| 主库文件 | `data/quantstudio.db` **62.47 GB**，最后写 **08:04:19** |
| 新进程只读开库 | **成功**；`etf_daily` 行数 **2,220,975** ⇒ **DB 文件可读、未整体损坏** |
| daemon | PID 33780 `--mode forever`，**空转**（5 分钟心跳），06:00 轮异常收尾 |
| 4.8 亿行全量重建 | **未实际发生**（08:04 后无写）——止步于判定 |

> **关键区分（本方案的设计前提）**：`database has been invalidated` 是 **DuckDB 进程级句柄状态**（遇 fatal 后该连接/实例整体不可用）；
> **不等于 DB 文件损坏**。实测新进程可正常只读打开并读出 222 万行 ⇒ 文件层大概率完好，**损坏点集中在 etf_daily 的 ART 唯一索引结构**。

### 2.1 命中的官方口径（可直接引用）

| 路径 | 官方原文要点 | 出处 |
|---|---|---|
| **`EXPORT DATABASE` / `IMPORT DATABASE`** | 「save the whole state of the current database in use inside folder `tmp`」→ 再 `IMPORT DATABASE 'tmp'` 载入新库；官方用于**跨存储格式迁移**（旧版打开→导出→新版导入） | `duckdb.org/docs/2.0/internals/storage` |
| **`ATTACH` + `COPY FROM DATABASE`** | 「Attaches the original database 'db1' and a new empty database 'db2', then copies all content from db1 to db2 to create a **compacted copy**」 | `duckdb.org/docs/2.0/operations_manual/footprint_of_duckdb/reclaiming_space` |
| `CHECKPOINT` / `VACUUM` | **不回收空间**（官方明示）⇒ 不能作为修复手段 | 同上 |

### 2.2 未获确认项（如实声明，实施前必须实测）

2. **损坏表能否被完整 SELECT**（索引损坏通常影响写入路径的唯一性检查，列扫描可能不受影响）⇒ 实测项 T2（只读校验行数 + 校验和）；
3. **`COPY FROM DATABASE` 是否支持单表粒度**（官方示例为整库）⇒ 实测项 T3；
4. **`database has been invalidated` 后是否必须重启进程**（本件按「必须重开进程」设计，实测项 T4）。

## 3 候选方案（A/B/C/D）与适用条件

### 候选 A：单表**索引重建**（若 T1 确认 `REINDEX` 可用）

```sql
-- 仅在 T1 实测确认 1.5.6 支持 REINDEX 且语法匹配后执行
REINDEX TABLE etf_daily;   -- 或 REINDEX DATABASE / 官方等价语法（以实测为准）
```

| 项 | 评估 |
|---|---|
| 代价 | **最小**（仅重建该表索引，不动数据） |
| 前置 | T1 必须成立；且 DuckDB 允许对损坏索引直接 REINDEX（未知） |
| 风险 | 若索引损坏已影响数据一致性，REINDEX 可能二次失败或产出一致性可疑的索引 |
| **结论** | **首选（若可行）**，但**不可假定** |

### 候选 B：单表**导出→重建→导入**（不依赖 REINDEX）

```sql
-- 1) 只读导出损坏表（先验 T2：SELECT 完整性）
COPY (SELECT * FROM etf_daily) TO 'etf_daily_dump.parquet' (FORMAT parquet);
-- 2) 关闭 daemon（无写窗）
-- 3) 删表 + 重建（走既有 _init_tables / schema 契约，铁律 24 六件套不适用——表结构不变）
DROP TABLE etf_daily;
-- 重建由代码路径完成，或按契约 DDL 显式重建
-- 4) 导入 + 校验
COPY etf_daily FROM 'etf_daily_dump.parquet' (FORMAT parquet);
```

| 项 | 评估 |
|---|---|
| 代价 | **中**（表级导出/导入；etf_daily 222 万行，估分钟~小时级） |
| 前置 | T2 成立（损坏表可完整读出）；无锁窗；磁盘余量 ≥ 表大小×2 |
| 风险 | 若 SELECT 本身受阻（索引损坏影响扫描）⇒ 退化到候选 C |
| **结论** | **主力候选**（不依赖未知语句、影响面限于单表） |

### 候选 C：**整库重建**（`COPY FROM DATABASE` 或 `EXPORT/IMPORT DATABASE`）

```sql
ATTACH 'data/quantstudio.db' AS old_db;
ATTACH 'data/quantstudio_new.db' AS new_db;
COPY FROM DATABASE old_db TO new_db;   -- 官方「compacted copy」路径
```

| 项 | 评估 |
|---|---|
| 代价 | **高**（62.47 GB 全库复制；需额外 ≥63 GB 磁盘；时间估数小时） |
| 前置 | 磁盘余量；无锁窗；全部表可读 |
| 风险 | 若损坏表在复制中触发同一 fatal ⇒ 整库重建也失败（届时须排除该表后单独处理） |
| **结论** | **保底路径**（候选 B 失败时启用） |

### 候选 D：**排除损坏表的部分重建**

即候选 C + 跳过 `etf_daily`，随后用候选 B 单独补建该表。

| 项 | 评估 |
|---|---|
| 代价 | 高（同 C）+ 中（补 B） |
| **结论** | C 失败时的组合兜底 |

### 候选排序与决策树

```
T1 实测确认 REINDEX 可用？ ──是──> 候选 A（最小代价，仍须过 V1~V4 校验）
        │否
        ↓
T2 确认 etf_daily 可完整 SELECT？ ──是──> 候选 B（主力）
        │否
        ↓
磁盘 ≥63GB 且其余表可读？ ──是──> 候选 C（保底）
        │否
        ↓
候选 D（排除 etf_daily 的部分重建）+ 上报候裁
```

## 6 【丙·独立小节】「无锚点全量重建」熔断护栏（框架层）

> 总调度裁定：丙项作为**独立小节**入本件；即期熔断由 daemon 停机承担（节点1 即办），本小节为**框架层长期护栏**。

### 6.1 问题

现状：`get_last_date` 返回 `None`（读失败或被 W5 按无水位处理）⇒ 判「无锚点」⇒ **自动**进入「建基线」全量拉取（本例 310 天/≈4.8 亿行/数小时~数十小时），**无任何确认或限额**。这是一个**静默的极端代价降级**。

### 6.2 候选设计（三条，供②审择一或组合）

| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **丙-1 显式确认门** | 判定「无锚点」且估算行数 > 阈值（如 >5000 万行或 >30 天）时，**不自动执行**，改为写入待确认文件 + 告警，需人工确认 | 最安全，杜绝静默长跑 | 需人工介入（无人值守时会卡住） |
| **丙-2 限额拉取 + 分批推进** | 无锚点时**只拉最近 N 天**（如 7 天）建最小锚点，后续轮次自然推进 | 无需人工，自动恢复 | 首次水位语义为「近 N 天」，与"全历史一致"预期不同，需明确声明 |
| **丙-3 环境开关（默认拒绝）** | 新增 `QS_ALLOW_FULL_REBUILD`（默认 0）；无锚点大范围重建需显式置位 | 改动最小、可回退 | 无人值守时默认卡住（等同丙-1 但无交互） |

**我方倾向**：**丙-2 为默认行为 + 丙-3 作为逃生阀**。理由：丙-2 让系统自动恢复（符合"全自动管线"目标），丙-3 保留人工强制全量的通道；纯丙-1 会让无人值守场景停摆。

### 6.3 丙的验收（V7–V8）

| # | 判据 |
|---|---|
| V7 | 构造「`get_last_date` 返回 None + 表内已有数据」场景 ⇒ 断言**不触发**全量重建，而是走限额路径（或拒绝+告警） |
| V8 | `QS_ALLOW_FULL_REBUILD=1` 时行为恢复为「全量重建」（逃生阀有效） |

### 6.4 丙的实施边界

- 只改「无锚点判定 → 拉取范围决策」这一处（`daemon.py` 中 `无锚点（首次/升级后）` 分支）；
- **不改** `get_last_date` 返回语义（W5 已按"warn + return None"定稿，不重复动）；
- 与 P0（索引修复）**完全解耦**，可独立实施、独立回退。

## 7 影响面与风险（修复前置纯增益审计，铁律 18）

| 子件 | ①其他功能 | ②性能 | ③精度 | 判定 |
|---|---|---|---|---|
| **P0-A/B**（索引修复/单表重建） | 仅 `etf_daily` 表，其余表不动 | 修复后写入恢复（**收益**） | 数据逐位一致为证（V1/V2） | **纯恢复型**（回到损坏前原态） |
| **P0-C/D**（整库/部分重建） | 全库或大部分表（影响面大，**须择无锁窗**） | 重建期间不可用 | 同上 | **纯恢复型**（但影响面大，风险高于 A/B） |
| **丙**（熔断护栏） | 仅无锚点分支 | 避免数十小时无效拉取（**收益**） | 水位语义改为"近 N 天"，**须显式声明**（新增检测型/行为修正型边界） | **行为修正型**（须显式声明影响面） |

**风险清单**：
| # | 风险 | 缓解 |
|---|---|---|
| R1 | 备份磁盘不足（62.47GB×1~2） | 修复前先核余量；不足则先清理（**不跳过备份**） |
| R2 | 重建期间有写入（锁冲突/二次损坏） | **必须**在 daemon 停机 + 无锁窗执行（铁律 19：先声明占用窗） |
| R3 | 损坏表 SELECT 受阻 ⇒ B 不可行 | 决策树退化到 C（实测 T2 前置判定） |
| R4 | 修复后下一轮再次损坏（根因未除） | V3/V4 观察 1–2 轮；若复发 ⇒ 转"C+排除该表"并升级为引擎缺陷上报（可能需升级 DuckDB 版本，属另一决策） |
| R5 | 索引损坏根因未明（并发写？旧版本 bug？异常退出？） | 本件**先修后归因**：修复同时保留修复前文件以便后续分析（不因归因未明而阻塞恢复） |
