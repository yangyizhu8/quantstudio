# 技术债 #18 升级版设计：数据质量自动闭环体系（三层架构）

> Step 1 草案（总调度起草，2026-08-28）——8/31 解禁日启动后走 Step 2 审计。
> 铁律依据：AGENTS.md 总调度铁律 + 用户"移交前数据防线封死"指令。

## 一、目标

把本周已验证的三个数据质量模式（缺口自愈/P-A3 门禁/P-D14b 归一）升级为**统一的三层自动闭环体系**，使数据问题从"反复发生+事后救火"降级为"写入前拦截为主+检测层兜底"。

## 二、三层架构

### L1 全自动闭环（已知模式+低风险幂等修复）
- 触发：检测层命中已知模式
- 链：检测 → 自动定性（规则库匹配）→ 自动修复（修复器库）→ 自动验证（断言）→ 归档登记
- 现有实例：gap_registry 缺口自愈（OPEN→重拉→HEALED→云补推）
- 准入条件（四件套）：幂等（二次执行零效果）/可逆（备份+逆向 SQL）/备份（原值落盘）/影响面断言（命中数精确）

### L2 半自动（已知模式+数据写入需授权）
- 链：检测 → 自动定性 → 方案自动生成（修复器模板+参数填充）→ 用户一句话授权 → 执行 → 验证 → 归档
- 现有实例：P-A3 补推/SO 补推/A 残留窗口（本周三次实战验证效率）
- 与 L1 区别：修复涉及生产数据 UPDATE/INSERT 批量写入，须人闸

### L3 人工归因（未知模式）
- 链：检测 → 告警 → 人工归因（六步流水线）→ 修复 → **模式入库**（降级为 L1/L2）
- 本周实例：ILP 风暴/时刻戳异常（首现时）
- 核心机制：L3 的产出喂养 L1/L2——登记表模式+修复器+定性规则三件同步入库

## 三、组件设计

### 3.1 检测层（补齐分钟表断言）
- 现有：六项巡检+晨间工件+quality_audit 门禁（EpsBackfillGap 同款）
- 补齐：**分钟表断言**（freq 值域/time 锚单值/日跳变代理断言——复用摸底 SQL）
- 新增：#19 云端对等巡检（Trae 域设计中）+ #20 血巡检（Trae 域设计中）

### 3.2 定性规则库
- 形态：`data_quality_rules.yaml`（模式 ID/检测 SQL/定性规则/修复器引用/授权级别 L1/L2/L3）
- 首批规则：本周 17 项技术债+7 起事故全部规则化（每项一规则）
- 匹配：检测命中 → 规则库查询 → 命中已知模式 → 路由 L1/L2；未命中 → L3

### 3.3 修复器库（统一入口+准入）
- 位置：`quantstudio/pipeline/repairers/`（每修复器一文件）
- 准入：四件套断言测试（幂等/可逆/备份/影响面）全绿才入 L1 白名单；缺任一 → L2（人工授权）
- 首批修复器（模式迁移）：
  - `gap_heal.py`（缺口自愈——从 trading-battle-back 迁移接口）
  - `eps_backfill.py`（P-A3 已有，迁入）
  - `time_normalize.py`（P-D14b CLI 已有，迁入）
  - `minute_front_rewrite.py`（#1 新建——SEGMENT-2 ILP 重写模式复用）

### 3.4 L1 自动准入清单
- 形态：`repairers_registry.json`（修复器 ID/准入日期/四件套测试结果/授权级别）
- 审批：入 L1 需总调度审计+用户授权（一次授权长期有效，升级/修改需重新审批）

### 3.5 模式→规则→修复器索引
- 形态：issue_registry 已有模式条目增加 `rule_id`/`repairer_id` 字段
- 用途：L3 归因完成后自动注册规则+修复器，实现降级自动化

## 四、执行编排

- 统一入口：`quantstudio/pipeline/quality_orchestrator.py`
- 调度：挂接现有 daemon 每日巡检后（stage8 之后）+ 晨间工件框架
- L2 授权接口：修复方案生成后写 `pending_repairs/` 目录，总调度守护检测到即呈报用户

## 五、验收标准

1. 三层路由测试：已知 L1 模式自动闭环/已知 L2 模式生成方案等授权/未知模式告警入 L3——各一集成测试
2. 四件套准入测试：幂等/可逆/备份/影响面断言对四个首批修复器全绿
3. 本周 7 起事故模式回放：全部被规则库捕获并路由正确
4. 分钟表断言：摸底 SQL 断点代理归零（#1 A 级修复完成后）
5. 端到端演练：注入一个已知模式脏数据 → L1 自动修复归档全链
