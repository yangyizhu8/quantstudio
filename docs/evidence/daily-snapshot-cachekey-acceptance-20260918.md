## 1. 缺陷（分层归因，证据见 §3）

**现象**：客户项目本地回测慢（单股 8 年 ≈ 1 小时，约 0.35 交易日/秒）。

**直接原因**：`preload_daily_snapshots` 写入内存缓存的键与 `query_daily_snapshot`
查询的键**结构性永不相等**，预取结果 100% 未被消费，每个交易日退化为一次对
`stock_daily`（971 万行）/`etf_daily`（215 万行）的全市场窗口扫描。

**代码缺陷**：`quantstudio/backtest/providers/duckdb_data_access.py:499`

```python
df = df.assign(_day=df['time'] // 86_400_000 * 86_400_000)
```

第 504 行以此 `_day` 作缓存键；消费侧第 412 行以调用方传入的 `date_ms` 取值；
`date_ms` 由 `duckdb_provider.py:15-16` 的 `_start_ms`（`tz='Asia/Shanghai'`）产出。

**算术实质**：`x // 86_400_000 * 86_400_000` 的结果 `mod 86_400_000` **恒为 0**（UTC 日界），
而 `_start_ms` 的结果 `mod 86_400_000` **恒为 57_600_000**（CST 日界）——两集合交集为空。
该错位与库内 `time` 实际存什么时区**无关**，是结构性冲突。

**业务边界**：**是回归，不是预期行为，也不是新需求。**

- 引入点经 `git log -S` 定位为 `bb602f3`（2026-08-27，WP-D P-D14 D3）。
- 该提交**之前**的实现为 `for t, grp in df.groupby("time"): cache[int(t)] = ...`
  （原值键 = 查询键，**命中有效**）。
- P-D14 的目标（把 08:00 异常组并入当日键）正确，但其实现把日界基准从「数据自身日界」
  换成了「UTC 日界」，附带把缓存从 100% 有效打成 100% 失效。

**潜在隐性风险（本件一并处置 / 登记）**：

1. **双键空间**：`query_daily_snapshot:437` 在 miss 后以 `date_ms` 落缓存，与预取的 UTC 键
   混居同一 dict（实测键 mod 集合 = `{0, 57600000}`）→ 同批数据可能双份驻留、
   `_cached_min_ms/_cached_max_ms` 被污染。**随本修复消除**（两键同源）。
2. **验收方法缺陷**：P-D14 的 T6「预取-单日字节级一致」只断言行数与 code 集合、
   **未断言缓存确实命中**，且其比较对象实际是「单日查询结果 vs 同一次单日查询写入的缓存副本」
   ——预取路径从未真正被检验，缺陷由此带病通过。**本件以 T-2 断网取证堵住该漏洞。**
3. **行序差异**：两路径的 `sort_values('time')` 对相同时间戳为不稳定排序，行序可能不同。
   判定**不构成行为变更**（依据见 §3.4）。

1. 缓存失效缺陷**确已修复**：命中率 0% → 100%，快照累计耗时降至约 **1/32**。
2. **但缓存失效不是客户「1 小时慢」的主因**——修前它仅占总耗时的 **3.62%**。
