## 1 B 段（**按裁定修订**）：门槛不动，只改「说清楚 + 给动作」

### 1.1 保持不变的判据

```
need = bundle_bytes × 1.10 + 64 MiB        # 同卷；跨卷另加现存库字节
free < need  ⇒  拒绝（exit 3, refused）      # **不放宽、不告警放行**
```

理由（用户裁定）：安全余量是保护措施，宁可让用户先清空间，也不在半余量下冒 ENOSPC 风险。

### 1.2 唯一改动：拒绝对象从「一串字节数」变成「可执行的清空间清单」

现状文案：`空间不足：需要 81917811916 B，可用 79248240640 B`（用户无法判断差多少、该清哪里）。

改后：

```
空间不足：还差 1.62 GiB
  包体        69.30 GiB
  安全余量    6.99 GiB（1.10× 包体 + 64 MiB，用于复制期临时开销与文件系统碎片）
  门槛        76.29 GiB      当前可用   74.68 GiB
  可清理位置（按收益排序，均为只读扫描后给出）：
    1) data/backup_import_*       共 2 个，合计 12.4 GiB   ← 确认新库正常后可删
    2) data/snapshots/*.bak-*     共 9 个，合计 3.1 GiB
    3) 回收站 / 其他卷             —
  提示：同卷备份是 rename，不额外占空间；清空间只需补足差额，无需准备两份包体。
```

实现要点（纯增量、不改判据）：
- `probe.space_report(need, free, data_root)` 返回结构化明细（新增函数）；
- 扫描 `data/backup_import_*` 与 `data/snapshots/*.bak-*` 的 **大小与数量**（只读 `stat`，不删任何东西）；
- CLI（`import`/`export` 的拒绝路径）与 GUI（结果槽）共用这份明细（与 4 态汇总同款「内核单一真源」）。

### 1.3 明确不做的事（避免误解）

- 不引入"余量不足也放行"；
- 不引入 `--require-safe-margin`（既然默认就是严格模式，该开关无意义）；
- 不自动删除任何备份目录（释放权在客户，符合回滚纪律）。

## 2 A 段（不变，仍待批）：锁的诊断与处置

- **A-1 拒绝即诊断**：`pid=…（存活：否 / 心跳年龄：… / host：一致）` + 处置建议；
- **A-2 自愈扩条**：同 host 且 `pid == 本进程`却未被句柄跟踪的锁 ⇒ 判自身残留并回收；
- **A-3 `qs-deliver unlock [--dry-run] [--force]`**：默认只诊断；`--force` 仅「pid 死/无持有者」可删并写审计；
  不修改 `snapshot_lock`（只用其公开原语）。

> 本轮用户实测「重启 GUI 后锁报错消失」，与 A1 一致；A-1/A-3 的价值在于**下次复发时自解释、可自助**，
> 不改变任何互斥语义。

## 5 风险与回滚

| 风险 | 处置 |
|---|---|
| 扫描备份目录拖慢拒绝路径 | 只 `stat` 顶层目录与一层文件，深度 1；大目录也 < 100 ms |
| 文案列出"可清理"被误解为"程序会自动删" | 文案显式标注「只读扫描，程序不会删除任何备份」 |
| 心跳频率过高影响导出 | 节流 64 MiB / 2 s；实测增幅 > 2% 回退 |
| `unlock --force` 误删活锁 | 仅死锁可删 + 审计行 + 拒绝时打印证据 |
