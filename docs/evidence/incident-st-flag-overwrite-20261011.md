## 三、根因（代码级确认）

**MCP 分片流式入库路径未向 aligner 传 `namechange_df`**：

- 路径：`daemon.py:1372` 的**分片流式循环**（`df_shard` + `_tprobe` 性能跨度，日志对应「streaming … 第一遍逐片注入」）
- 该处调用：`self.aligner.align(df_shard, table, source, adj_factor_df=..., freq=freq, **_qfq_snap)`
  —— **无 `namechange_df` / `valuation_df` 参数** ⇒ aligner 的 `_derive_st_status` 收到 None ⇒ **每行一律 False/`none`**
- ⇒ 每一轮 MCP stock_daily 批次都会**把此前正确的 ST 真值覆盖为 False**（结构性，不依赖数据状态）

**F-1/F-3 覆盖缺口**（`aligner.align` 共 7 个真实调用点，门只接在 3 处）：

⇒ 门未触发的直接原因：**该路径根本没有门**；且即便有门，其 `namechange_df` 为 None 会走 F-1（依赖表缺失）而非 F-3。

## 四、对既有结论的修订（重要）

**P-1 判别修订**：先前结论为「(a) 依赖表未准备/为空」。本次代码级取证表明：
真正的机制是 **该入库路径结构性地从不把 `namechange_df` 传给 aligner**——
推导本身无缺陷（P-1 单元复现 A 例已证），但生产路径**从未给它依赖**。
原「依赖表未准备」为**表层现象**（在 align 路径观察到的等价结果），根因更深一层。

**D-4 验收有效性**：D-4 的回填与验收（V-3）在**当时**成立（残留 0、逐日一致、定点 PASS）；
但其结果**不具备持久性**——下一次 MCP stock_daily 批次即覆盖。
⇒ D-4 的 F-1/F-3 门**覆盖不全**，未能阻止覆盖。
