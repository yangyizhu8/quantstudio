## 一、被测语形

表：32 列（`code VARCHAR, time TIMESTAMP, freq VARCHAR, c1…c29 DOUBLE`），**50,000 行**，主键按臂分为 `PRIMARY KEY(code,time,freq)` 与无主键两组。

| 臂 | 语形 | 事务 |
|---|---|---|
| **A** | `TRUNCATE TABLE t` → `INSERT INTO t SELECT …` | `BEGIN/COMMIT` 包覆 |
| **B** | `DELETE FROM t` → `INSERT INTO t SELECT …` | `BEGIN/COMMIT` 包覆 |
| **C**（现状基线） | `CREATE t__pt_tmp AS SELECT … LIMIT 0` → `INSERT INTO tmp` → `DROP TABLE t` → `ALTER TABLE tmp RENAME TO t` | — |

每组独立新库；事后探测：`duckdb_constraints()` 主键数、`duckdb_indexes()` 索引数、行数、**`ON CONFLICT(code,time,freq) DO UPDATE` 是否仍可用**。

## 三、结论

1. **F2（`TRUNCATE` + `INSERT`，事务包覆）在本实验条件下可用**：主键保留 1→1，冲突探测仍有效，两版本均未触发 ART index-delete FATAL。
2. **`TRUNCATE` 不构成事故语义**——段 A/B 的担忧（「删全表行」与 09-20 事故同族）在 50,000 行 × 32 列 × 两版本 × 带/无 PK 上**未复现**；故 F2 可自「候选」升为**基线**，F1（重建同构 PK）降为**回退方案**（当 `TRUNCATE` 不可用或列集变化时）。
3. **缺陷机理再确认（比原表述更精确）**：`DROP+RENAME` 后 PK 消失 ⇒ 带 `ON CONFLICT` 目标的 upsert **直接抛 BinderException 拒绝**（fail-loud），而非静默插重复行；但无 `ON CONFLICT` 的普通 INSERT 则仍可能插重复 —— 两种后果都要写进 runbook。

## 四、对实现设计的约束（新增，plan 已同步）

1. **列集一致前提**：`TRUNCATE + INSERT` 只能覆盖「列集不变」的情形；若上游新增列，`TRUNCATE` 路径**无法自动加列**，必须走 DDL 路径（`ALTER TABLE ADD COLUMN` 或回退 `DROP+RENAME`）。实现须先比对 df 列集与表列集，按结果选路。
2. **事务包覆是硬要求**：`TRUNCATE` 与后续 `INSERT` 必须在同一事务内，否则中途失败会留下空表。
3. **`write_passthrough_chunked` 另有 staging + ledger 语义**，改道时须保留 ledger 记账（不能只换 SQL）。
4. **文档缺陷（登记不擅改）**：`writers.py:1573-1581` 的 docstring 写「`CREATE OR REPLACE TABLE` 全量覆盖」，实际实现是 `DROP+RENAME`（`:1618-1619`）——实施期一并更正说明文字。**关联补记（2026-10-29 总调度指出）**：该失实 docstring 同时解释了段 A 报告把临时表建法叙述为「`CTAS … LIMIT 0`」的来源——代码中真实存在 CTAS 建临时表步骤，而对外语义描述长期写成 `CREATE OR REPLACE`，两处文本各说各话；实施期更正时应一并核对 `write_passthrough_chunked`（`:1672-`）的同类描述。
