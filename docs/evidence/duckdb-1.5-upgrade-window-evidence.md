#### §7.28.1 独占探针：真实持有者负例（此前只测过本会话句柄，不足）

**方法**：起**独立子进程**，以 duckdb **读写连接**持有合成库（此时 WAL 在位 112 B），再从主进程探测。

| 探测方式 | 结果 | 判定 |
|---|---|---|
| **`.NET [System.IO.File]::Open(..., FileShare::None)`**（v5/v6 采用写法） | **不可独占**（`MethodInvocationException`） | ✅ **正确识别持有者** |
| 同进程 `open(path,'rb')`（旁证） | `PermissionError [Errno 13]` | ✅ 一致 |
| ctypes `CreateFileW` **未设 `restype`** | 返回被截断的句柄值 ⇒ 误报「可独占」 | ❌ **漏检** |
| ctypes `CreateFileW` **设 `restype=HANDLE`** | 返回 `INVALID_HANDLE_VALUE (18446744073709551615)` | ✅ 正确 |
| 持有者退出后（正例） | 恢复「可独占」 | ✅ |

**结论与固化**：
1. **`.NET FileShare::None` 写法可靠**，v6 保持该写法；
2. **若改用 ctypes 必须显式设 `restype`/`argtypes`**，否则返回值被截断为 32 位 ⇒ **静默漏检**（本条非理论风险，本轮首测即踩）；
3. **旁证强化**：持有者存在时**连 `Copy-Item` 都会失败**（实测 `The process cannot access the file ... being used by another process`）

#### §7.28.3 🔴 主库／WAL 一致性复核：发现 v5 **实质缺陷**——WAL 备份命名错误 ⇒ 静默丢增量

**缺陷**：v5 把 WAL 备份写成 `quantstudio.db.wal.bak.<ts>`，而主库备份为 `quantstudio.db.bak.<ts>`。

**实测（合成库，2026-11-15 03:0x）**：构造「主库已 `CHECKPOINT`（含 3 行）+ 后续 4 行仍在 WAL」的现场（子进程写入后强杀模拟崩溃）：

| 命名方式 | 打开备份读到 | 是否报错 |
|---|---|---|
| `q.db.wal.bak.T`（**v5 写法**） | **count=3，sum=6**（丢 4 行） | **不报错 ⇒ 静默** |
| `q.db.bak.T.wal`（**v6 写法**） | **count=7，sum=28**（完整） | 正常 |

另在「表尚未 checkpoint 到主库」的极端现场，v5 命名会直接 `CatalogException: Table with name t does not exist`（连表都看不到），
v6 命名则正常读到 7 行。

**危害定级**：这是**静默数据丢失**型——用户会以为备份完整，直到真正需要恢复时才发现少数据；且**六判据全部通过**也发现不了
（因为①–⑥只校验「备份字节==源字节」，而缺陷在于「打开备份时未重放 WAL」）。
⇒ **判据的盲区由此确认**：六判据保证「拷贝忠实」，**不等于**「恢复完整」。v6 因此补两条：

1. **命名写死**为 `<主库备份全名>.wal`（§2.2，附 ⚠ 实测对照表）；
2. **§2.4 增 WAL 重放判据**：`备份打开后读到的行数/末笔时间不得早于源库关闭前读数`——若明显偏旧，第一嫌疑即 WAL 未重放。

#### §7.32.2 版本绑定机制（工具已实现，exit=4 拒比）

#### §7.32.3 碰撞边界实测（据实声明，不宣称安全）

| 项 | 实测 |
|---|---|
| **求和 vs XOR** | 用 `sum(CAST(hash(...) AS HUGEINT))`。3 行表 vs 同 3 行 + 1 重复行 ⇒ **摘要不等（能检出）**；XOR 在成对重复下**会相互抵消**，故不采用 |
| **位宽** | 三路独立盐 ⇒ **192 位**；生日界约 **2^96 行对** 才出现一次同和 |
| **溢出** | `HUGEINT` 上限 `2^127−1`。实测 3×(2^64−1) = `55340232221128654845`（正确）；62 GB 按 6.2 亿行外推 `sum` 上界 ≈ **2^93**，**不溢出** |
| **顺序无关** | 同表乱序插入 ⇒ 摘要**相等**（集合语义） |
| **⚠ 不抗恶意** | 求和是**加法**结构，理论上可构造 `h(a)+h(b)=h(c)+h(d)` 击穿单盐；三盐把代价抬到 ~2^96，但这是**工程强度、不是密码学保证**。本判据用于发现**意外损坏/漏拷/错配**，**不用于对抗蓄意伪造** |
| 有界搜索验证 | 2000 个值内**未找到**单盐二元组同和（符合预期：生日界 2^64 远大于 2000²，该量级本就搜不到） |

#### §7.33.1 🔴 我方上一轮的 192 位/2^96 是**无依据外推**，已撤回

**审核意见成立，我方原文属越界承诺**。理由已在通知 §2.4 写明：
`hash(x)` 与 `hash(x,'S2')`、`hash(x,'S3')` 是**同一次调用的不同参数形式**，
**没有任何依据证明三者相互独立**。把「同一函数换参数」当作「三个独立 64 位分量」再推算
位宽（192 位）与生日界（2^96 行对）、构造代价，**是把相关性未验证的东西当成独立同分布**——
这正是我此前反复要求自己避免的错误类型（用未证前提推强度）。

**已删除的表述**：「三路盐 ⇒ 独立 192 位」「生日界 2^96 行对」「构造代价 ~2^96」。
**保留并可复核的**（均为实测，非推算）：
- `sum` 非 `bit_xor` ⇒ **对行重复敏感**（3 行 vs 3 行+1 重复 ⇒ 摘要不等）；XOR 在成对重复下相互抵消；
- `HUGEINT` 累加器**不溢出**（实测 3×(2^64−1) 正确；62 GB 按 6.2 亿行外推上界约 `2^93` < `2^127`）；
- 聚合**顺序无关**（乱序同表摘要相等）。
**定位改为**：**工程摘要（engineering digest）**——用于发现意外损坏/漏拷/错配/少行多行，
**不提供密码学或概率强度保证**，**不用于对抗蓄意伪造**。三盐的好处仅表述为「**经验性冗余**」。

#### §7.33.4 全文件 SHA 的正确定位（不替代逻辑验证）

| 手段 | 证明什么 | 抓不到什么 |
|---|---|---|
| **全文件 `Get-FileHash`**（源 vs 副本） | **物理字节一致**（拷贝忠实） | **WAL 未重放 ⇒ 字节一致但打开后少数据**（v5 缺陷恰是如此）；逻辑层任何打开期转换 |
| **七面比对**（本通知默认） | **打开后逻辑内容**在七个面上一致 | 主库中间区域字节被改但逻辑不可见；物理布局差异 |

⇒ **两者互不替代**。通知已明写：默认做七面比对，全文件 SHA 作**可选加强**；需两者都覆盖则**同时做**。
