## ① #1 大表 UPSERT 卡死 —— 维持 partial（env 取值已固定；归因显著收窄）

### 1.1 env 取值（终验关闭条件项①）——已取得

| 项 | 读数 | 来源 |
|---|---|---|
| 进程环境 `QS_UPSERT_SKIP_IDENTICAL` | **空（未设置）** | pwsh `$env:` 读数（2026-10-30 11:39） |
| 进程环境 `QS_DUCKDB_MEMORY_LIMIT` | 空（未设置） | 同上 |
| 全仓配置/脚本命中（`*.json/*.ps1/*.bat/*.sh/*.env/*.cfg/*.ini/*.yaml`，config/ + scripts/ 全域，排除 `.git`/`agent_workspace`/`node_modules`） | **HITS=0** | Select-String 全量扫 |

**判读**：我方与本机运行**一直是 T2 关闭态** ⇒ 生产 SQL 不含 `IS DISTINCT FROM`、**不含 RETURNING**（RETURNING 仅 T2 开启路径存在）。与客户自述「开关默认关闭」一致；**客户 py-spy 冻结行恰是仅 T2 开启才执行的 RETURNING 行**——该互斥在客户现场仍无解释（Open Question 保留）。

### 1.2 沙箱真规模有界复跑（未触碰生产库）

- **复刻对象**：客户 GUI 场景「目标表 447 万行 / 42 列，5 万行/批，全量重拉（89 批＝客户实测卡死批次数）」；
- **生产库不可读**：`data/quantstudio.db` 59.4 GB 被 daemon（PID 32032）独占锁，只读连接与快照拷贝均失败（PermissionError）⇒ 按铁律 19 不介入 daemon，改走沙箱；
- **写入路径**：真实 `DuckDBWriter.write()` → 真实 `ON CONFLICT DO UPDATE`（T2 关＝无 WHERE、无 RETURNING）；447 万行 = 5000 code × 894 day，42 列真 schema。

| 轮次 | 读数 |
|---|---|
| 1 pass（89 批） | head_avg 6.156s → tail_avg 5.811s，**growth 0.944**，总 531.1s（8.85 min） |
| **4 pass（357 批＝客户场景：同一 447 万行被重写 4 遍＝17.85M 次冲突 upsert）** | head 5.539s → tail **4.791s**，**growth 0.865（零退化）**；四 pass 均值 **5.398 / 5.680 / 4.749 / 4.839 s**（无单调增长）；单批中位 ≈4.3–4.5s、峰值 15–18s（抖动，**无冻结**）；总 **1843.4s（30.7 min）** |

### 1.3 T2 收益实测（含**方法学自纠**）

**第一轮（作废）**：T2 ON/OFF 各 89 批，但批次**每批改数值** ⇒ 行非逐位一致 ⇒ **T2 的 skip-identical 路径根本没触发**；差值（460.0s vs 531.1s，−13.4%）只是 WHERE 子句开销/噪声，**不是 T2 收益**（已在 10-30 当轮即公示作废）。另：两臂 growth（0.944 / 1.256）在此批数下属**噪声级**，真实判读以 per-batch 区间（4.3–5.8s）为准。

**第二轮（有效｜identical 重写臂）**：同一 5 万行窗口、**逐位一致**、反复重写 89 批（=4.45M 次重复 upsert，T2 skip 路径真正触发）：

| 臂 | 总耗时 | 均值/批 | 中位 | 峰值 |
|---|---|---|---|---|
| **T2 开**（`IS DISTINCT FROM` skip） | **25.0s** | **0.280s** | 0.274s | 0.441s |
| T2 关（DELETE+INSERT 全走） | 507.2s | 5.699s | 4.432s | 19.824s |

⇒ **开 `QS_UPSERT_SKIP_IDENTICAL=1` 对「重复写逐位一致的行」提速 ≈20 倍（−95.1%）**。此为「100% 一致窗口」的上限效应；混合窗口收益按一致行占比折减。另：T2 关时「一致行」与「变更行」耗时相同（5.699s vs 5.968s）⇒ 关态下二者都走完整 delete+insert，无差别。

### 1.4 归因收窄与运维口径

**新结论**：本机在**同规模（447 万行）、同批大小（5 万行）、同 4 遍重写（17.85M 次冲突 upsert）**下 357 批全程稳定（≈5.2s/批），客户现场 89 批即冻结（≈52s/批）⇒ **「447 万行 + 5 万行/批 + 重叠 upsert」这一组合本身不是卡死主因**；「死元组累积致探测退化」在**无并发、单进程、干净库**条件下**复现不出**。客户侧差异因子指向其现场专有条件：**历史多次全量拉取遗留的巨量死元组未回收**（回收唯一途径＝ATTACH+CREATE TABLE AS 重建，实测 34.3MB→4.3MB）、**daemon 并发写入与计划抖动**、磁盘/内存压力。

**客户侧运维口径（按实测量化，建议随通知下发）**：
1. **开 `QS_UPSERT_SKIP_IDENTICAL=1`**（实测对逐位一致重复写提速 ≈20 倍：507.2s→25.0s／4.45M 次重复 upsert，−95.1%）——客户「2018 起全量重拉」的主体形态正是多数行未变；
2. **重建库回收死元组**（ATTACH+CREATE TABLE AS，实测 34.3MB→4.3MB，降 87%；`VACUUM` 无效）；
3. **单任务串行、禁并发全量重拉**；
4. **批次降至 1 万**；
5. **记录 env 取值**（现场 `QS_UPSERT_SKIP_IDENTICAL` 实际值）。

**引擎侧修复（去 RETURNING + spill 兜底）只降单批物化开销，不是客户卡死的根治项**（诚实声明）。

### 1.5 #1 状态

**维持 partial**：env 取值已固定、T2 收益已量化、沙箱 4-pass 零退化零冻结、防御性修复已入库（`5655fb4`）；但**客户现场卡死未在任何环境复现** ⇒ 关闭判据不变（客户现场回传 ①env 现场值 ②「2018 起」全量重拉复跑**过 357 批不冻结**的进度与耗时）⇒ 达标后 partial → verified。

## ② #8 export vs fetch_page 三一致对拍 —— **verified**

**通道与数据源**：QuestDB MCP 生产同源通道（`qdb.sw_daily`，row_count 1,525,984，ts 2010-01-04 ~ 2026-10-28；与客户清单同域表）；窗口 **2026-09-01 ~ 2026-09-30**。

| 检查 | 读数 | 结论 |
|---|---|---|
| 列集合 | fetch_page 15 列 = export 15 列，集合一致且**列序一致** | ✅ |
| 行数 | fetch_page **8,673** = export manifest `total_rows` **8,673** | ✅ |
| 键集合 | (ts_code, trade_date) 集合完全相同（only_a=0 / only_b=0） | ✅ |
| 逐列逐值 | 日期归一后**零差异**（其余 14 列全等） | ✅ |
| 制品完整性 | export parquet sha256 = manifest sha256 = `844961a0ea15cd41389579da94ce021a25079904174d63468680a23df6b07d86` | ✅ |
| **三一致判定** | 列 ✅ / 行 ✅ / 值 ✅ ⇒ export 通道对本表与分页通道**数据等价** | ✅ **verified** |

### ②-1 两项口径修正（必须入账）

1. **服务端 `fetch_page` 实测支持日期过滤**——`filters=[trade_date>=, trade_date<=]` 生效并返回窗口内数据（next_cursor 正常；page_size 2000 与 50000 两轮返回同 8,673 行）。⇒ 客户实测的「fetch_page 首行 2010-01-04、无法按窗取数」是**引擎侧 `mcp/client.py` 未透传服务端已有的过滤能力**，**不是服务端不支持**。⇒ 更优解候选：引擎侧透传 filters（而非切 export 通道）——**待②审/用户裁定**，本轮不擅改。
2. **export 通道 `trade_date` 为 DATE（datetime64），fetch_page 为 ISO 时间串（object）** ⇒ **切 export 通道后落库列类型可能由 TIMESTAMP 变 DATE**（passthrough 表原样搬运语义）——**真实风险点**：须在写前做日期列归一，或对路由表先做列类型核对。**建议：#8 清单启用与「批量启用」解耦**（先在已核过列类型的表上启用）。
