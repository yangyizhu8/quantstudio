### 4.1 🔴 反直觉发现（必须如实记录，不得夸大收益）

**往返降 250×，但 wall 只快 5%。**

**机理**：两路径的**扫描行数相同**（2000 code × 约 5.4k factor_time ≈ 1,073 万行），瓶颈是 **IO 扫描量**而非往返次数；本地 NVMe + 同机 SQLite 下，建连/往返开销被大查询摊薄。

**⇒ 对方案叙事的修正（诚实）**：
- 「95 min – 16 h」量级来自 **`record_observations` 的逐条写往返**（G1–G4 解决），**不是** `_security_effective_dates`；
- **G5 的价值 = 往返数 250×**，其 wall 收益只在 **高延迟 IO / 远程 SQLite / 连接建立昂贵**的场景才显著；
- **本机实测 G5 的 wall 收益 ≈ 5%（1.05×）**，不足以单独支撑「性能型修复」的墙钟叙事。

**⇒ 建议（呈裁）**：G5 保持默认关（现状已满足），**不单独立项为性能修复**；与 G1–G4 同开关一并评估，或在高延迟部署形态下再测。
