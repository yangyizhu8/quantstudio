# A4 基准写回·两分支判据增补件（②审增补令 · 2026-11-10 15:51）

> 增补对象：`docs/design-a4-baseline-writeback-20261110.md`（A4 基准写回方案件·②审已过）
> 增补依据：用户 2026-11-10 15:51「A4 实施增补两分支判据（运维2 本机证据）：『无基准』走建基准、『有基准但陈旧』走推进——两分支分别给判据，防照搬推进逻辑致永久不检测」
> 性质：**判据增补**，不改变 P0-1/P0-2/P2 实施范围

## 一、实现面澄清（先核后答·避免重复劳动）

**实读 `quantstudio/pipeline/update_detector.py:79-91 save_last_sync`** —— 当前实现是 **upsert（非裸 UPDATE）**：

```sql
INSERT INTO _a4_last_sync (table_name, last_sync_ts, updated_at)
VALUES (?, ?, ?)
ON CONFLICT (table_name) DO UPDATE SET
  last_sync_ts = EXCLUDED.last_sync_ts,
  updated_at   = EXCLUDED.updated_at
```

⇒ **无行时 INSERT（建基准）、有行时 UPDATE（推进）** ⇒ **两分支天然由同一条语句覆盖**。

⇒ **当前不存在「照搬推进逻辑致永久不检测」的实现缺陷**（运维2 担忧的形态是「裸 UPDATE ⇒ 无行时影响 0 行 ⇒ 基准永远为空」；现实现是 upsert，不中此病）。

⇒ **增补令的真实价值在「判据分列」而非「改实现」**：把两分支分别写成可机检用例——一旦未来有人把 upsert 重构为裸 `UPDATE`，A 分支测试立刻失败，从而守住。

## 二、两分支判据（新建 C6·与 C1 分列不混办）

| # | 分支 | 构造 | 期望 |
|---|---|---|---|
| **A-N1** | **无基准** | 新库 / `_a4_last_sync` 无该 table 行 ⇒ 跑一轮成功采集 | `_a4_last_sync` **新增该行**；`last_sync_ts` = 本轮水位对应时刻（**建基准**） |
| **A-P1** | **建后可见** | A-N1 后紧接下一轮 | `load_last_sync` 返回**非 None** ⇒ A4 检测层**不再打「A4 跳过检测」**（转由 C1-P1 正常路径接管） |
| **B-N2** | **有基准但陈旧** | 预置 `last_sync_ts = 30 天前` ⇒ 跑一轮成功采集 | 该行 `last_sync_ts` **被推进**为本轮时刻（**推进**）；`updated_at` 同步刷新 |
| **B-P2** | **陈旧推进效果** | 承接 B-N2 的下一轮 | `repull_dates` 数量较推进前**显著下降**（陈旧基准会捕获 30 天内全部 repair） |
| **X-N3** | **⚠️ 防退化闸（核心）** | 断言 `save_last_sync` 的 SQL **含 `ON CONFLICT`**（或等价 upsert 语义） | **必须含**——若被改为裸 `UPDATE` ⇒ **A-N1 失败** ⇒ **A4 永久不检测**（运维2 本机证据正是此形态） |

## 五、两分支的判读要点（防误判）

| 现象 | 含义 | 处置 |
|---|---|---|
| 日志「A4 跳过检测：X 无 last_sync 基准」**每轮出现** | **A 分支未生效**（基准从未建成）⇒ upsert 被破坏或写回点未到达 | 查 X-N3 + 写回点是否执行 |
| 日志「A4 熔断：X 检出 N 个窗口」**持续** | **B 分支未推进**（基准陈旧）⇒ 推进路径失效 | 查 B-N2 + P0-1 异常隔离是否拦住了写回 |
| 两者**同时**出现同一表 | **矛盾态**（不可能同时"无基准"与"有基准且陈旧"） | 多为**读到了不同的库**（多库陷阱·运维2 证据二） |
