## 一、问题定义（互抢的实测证据，不是推测）

### 1.3 量化根因（口径错配）

每个策略的目标仓位基数取 `context.portfolio.portfolio_value`（**账户总资产**）
⇒ N 个策略各自按「全部资产」算满仓 ⇒ 目标合计 = N×100% ⇒ **必然互抢**（N≥2 即爆）。

⇒ 这不是某个策略的 bug，是**转换管线的口径缺陷**：管线把策略的「本地回测语义（自有 capital_base）」搬到 PTrade 时，**丢掉了资金边界**——本地回测里每个策略天然独占 `capital_base`，上平台后却共享账户。

### 1.4 附带事实（方案必须适配，不能假设单一资金池）

同一策略的持仓分列**两个股东账号**（沪A `A222087012`／深A `0028389333`）⇒ 深A 的 159934 全额成交、沪A 的 511010/512890 受阻 ⇒ **可用资金按市场分账，跨市场不可互用**。隔离方案必须按「**策略 × 市场**」双维度记账，不能只按策略。

### 2.2 「策略仓位隔离」的真相（**更正我先前的说法**）

`D:\Ptrade\ptrade策略仓位隔离.txt` 我 11-06 15:5x 在呈批面里写成「PTrade 官方说明，乙方案有平台侧一手依据（前端开关）」——**该判断有误，现更正**：
该文件**不是**客户端功能说明，而是一份**官方给的代码级隔离模板**（`单账户多策略隔离模块`，10,037 B），通过在**一个策略文件内**维护虚拟资金/虚拟持仓实现隔离。**PTrade 没有策略级资金隔离的 UI 开关，也没有对应 API。**

⇒ **结论：隔离必须在转换管线的注入层实现**（这正是用户本次要求的落点），不能指望平台配置。

### 2.3 官方模板的七条硬机制（照抄其设计，扩展其拓扑）

| # | 机制 | 官方做法 | 我方沿用/改造 |

## 三、目标语义（N 策略通用 · 配置驱动 · 增删不改码）

### 3.1 设计原则

1. **配置即隔离**：每个策略在**自己的** `deploy.yaml` 里声明额度；**增删策略 = 增删 yaml + 机检**，管线代码零改动。
2. **策略源码零改动**（铁律 07）：隔离全部落在管线注入块与包装层。
3. **纯增益**：`isolation.enabled` **默认 false** ⇒ 既有产物行为零变化；开启属「**新增能力型**」（开始按额度约束、开始报告真相），单列验收，不得与纯恢复型混办。
4. **失败方向安全**：任何取数失败 ⇒ **拒单/让行**（fail-closed），不得静默放行成超买。

### 3.2 配置面（`deploy.yaml` 新增顶层段，向后兼容）

```yaml
strategy_id: ETF_f926a7
source: "..."
execution:
  profile: daily_eod_1450
persistence:
  enabled: true
isolation:                      # ★ 新增（缺省 = 不启用，行为与今日完全一致）
  enabled: true
  capital: 100000.0             # 本策略资金额度（元）——验证期终裁 10 万（四象限/F-Score/全球资产轮动各 10 万，合计 30 万 ≈ 账户 3%）
  policy: strict                # strict=超额拒单并告警 / soft=超额告警但让行
  ledger_dir: ""                # 缺省 <research_root>/_qs_isolation
  reserve_buffer: 0.001         # 预扣缓冲（覆盖滑点/费用）
  market_split: true            # 按市场（沪/深）分池记账（§1.4 事实要求）
  account_id: "99005258"        # 同账户策略的归属键（供机检汇总与冲突告警）
output:
  root: ""
  dir_name: "ETF_f926a7"
```

### 3.3 三层隔离的落地映射

| 层 | 语义 | 实现机制（注入层） |
|---|---|---|
| **资金隔离** | 本策略只见自己的额度与虚拟现金；目标市值按额度折算；买入不得超虚拟现金亦不得超真实可用 | **`context.portfolio` 策略视角代理**（§四核心机制）＋ `_qs_iso_budget()` ＋ 预扣/退还/回收 |
| **仓位隔离** | 本策略只见自己名下的持仓；卖出不得超过自己名下（再与真实可用取 min）⇒ **绝不卖别人的** | 虚拟持仓台账 ＋ `_qs_iso_own(security)` ＋ 卖出上限 `min(自己名下, 真实可用)` |
| **逻辑隔离** | 各策略风控/止损/回撤基数均按**自身额度**计算，不被别家波动污染；跨策略同标的冲突可被检出 | 净值高点/回撤基数改用额度；台账按 `strategy_id` 分键；盘后对账行 ＋ 跨策略冲突告警行 |

### 3.4 核心机制：`context.portfolio` 的「策略视角代理」

现状：策略里所有基数都用 `context.portfolio.portfolio_value`／`.cash`（账户级）。
若不改策略源码又要改口径，唯一可行路径是**在注入层把 `context.portfolio` 换成本策略视角的代理对象**：

```python
# 注入块内（示意）
def _qs_iso_portfolio(real):
    return _QsIsoPortfolio(
        portfolio_value = 虚拟现金 + 自己名下持仓市值,   # 本策略总资产
        cash            = 虚拟现金,                      # 本策略可用
        positions       = 只含自己名下,
        _real           = real,                          # 真实对象留底，下单链路仍用它
    )
```

⇒ 一次代理，**所有**读点自动隔离：目标仓位基数、`initial_value`/`high_water` 回撤基数、`_qs_cash_avail()` 现金口径、盘中资产展示——**无需逐点改策略**。
⇒ 先例可循：PD-0017 的 A 修复已用同族手法把 `data` 代理化（`_qs_data_proxy()`），平台接受该形态（实跑通过）。

### 3.5 台账布局（避开并发写冲突）

| 项 | 设计 | 理由 |
|---|---|---|
| 位置 | `<research_root>/_qs_isolation/<strategy_id>.json` | 研究根已被 PD-0017 的 state.pkl 验证可达（策略在券商服务器侧运行，研究根共享） |
| 粒度 | **一策略一文件**（各写各的） | 三进程并发写同一文件必冲突 ⇒ 分文件后**无锁竞争** |
| 内容 | `{version, strategy_id, account_id, capital, cash:{沪A,深A}, positions:{code:amount}, epoch, updated_at}` | 支持 §1.4 的市场分账 |
| 写入 | 临时文件 + `os.replace`（原子替换） | 断电/中断不留半截 |
| 读取 | 启动时读一次 ＋ 每次下单前读自身文件 | 只读自己的，不与别家争 |
| 跨日 | `epoch` 日戳，跨日只重置「虚拟现金」不重置「持仓」；与 PD-0017 E′ 的清空纪律同构 | 避免跨日残留污染 |

> **不做中央汇总台账**（需跨进程锁）：期 3 如需全局视图，另做**只读汇总**（各文件读后合并，不加锁）。

## 六、机检与门禁（新增 3 条，全部 fail-closed）

| 编号 | 机检 | 判据 |
|---|---|---|
| `ISOLATION-CAPITAL-SUM` | 同 `account_id` 下所有策略 `capital` 之和 | 部署前机检：`Σ capital ≤ 账户可用总资产 × (1 − buffer)`，超则**拒部署**（这是把「296%」挡在部署前） |
| `ISOLATION-SURFACE` | 产物是否全部经代理 | AST：`context.portfolio.portfolio_value`／`.cash` 的读取点必须落在代理生效路径；裸读点计数须为 0（白名单可显式登记） |
| `ISOLATION-LEDGER` | 台账机制完整性 | 产物须含：原子写（临时文件+replace）、预扣、退还、回收上限、卖出双 min、对账行 |

```

当日虚拟现金基准 = capital − 隔夜持仓市值        # ★ 非简单 capital

持仓：不清空（跨日保留）
```

## 11.7 实施期设计变更：equiv 判据从「文本标记」改为「AST 特征命名」（2026-11-08/09）

### 11.7.1 事由（实测）

期 1 ③实施切片 A/B 落地后，`isolation.enabled=true` 重转实测：`P3_transform: PASS` 但
**`P4_equiv: FAIL — 白名单外 diff 58 处 + 标记块异常 0 处`** ⇒ `deploy` EXIT=1，P5/P6 SKIPPED。

### 11.7.2 根因（已定位，非猜测）

`equiv` 的等价性剥离依赖**文本标记**：注入块以 `# PTRADE-DEPLOY:{kind} BEGIN/END` 包围，
`_strip_pass` 按行匹配标记并把块内内容还原成原文。既有 GUARD/GATE/PERSIST 块之所以可用，
是因为它们**包裹原有语句**（剥离后能还原原文形态）。

而 `transformer._emit_module` 是**自定义 AST emitter**，Python AST **不保存注释** ⇒ 模板里写的
`# PTRADE-DEPLOY:ISO BEGIN/END` 标记行**不进产物** ⇒ `_strip_pass` 找不到块 ⇒ ISO 的 58 条语句
全部被计入「白名单外 diff」。同时「标记块异常 0 处」说明不是配对错误，而是**标记根本不存在**。

⇒ **ISO 是纯新增块（原文无对等物），无法靠"还原"这条路识别，必须换判据维度。**

### 11.7.3 判据变更（本件照准项）

`equiv._handle_iso` 由「文本标记剥离」改为「**AST 特征命名剔除**」。剔除规则（模块级，四条）：

| # | 节点形态 | 判据 |
|---|---|---|
| 1 | `Assign` | 单目标 `Name`，`id` 以 `_QS_ISO_` 开头 |
| 2 | `FunctionDef` | `name` 以 `_qs_iso_` 开头 |
| 3 | `Assign` | 单目标 `Name`，`id == "_qs_pos_amount_legacy"` |
| 4 | `If` | `test` 为 `Name(id="_QS_ISO_ENABLED")` |

**为何"特征命名"可靠**：这些前缀是本框架的**保留命名空间**（与既有 `_qs_` / `_QS_` 家族同约定），
策略源码不得占用；且该判据建在**结构特征**上，不建在会被管线任意丢弃的**载体**（注释）上——
与 PD-2026-0019「mtime 不可靠 → 改内嵌时刻戳」、本件「注释不可靠 → 改 AST 特征」同源。

### 11.7.4 反向风险与防御（必须同时落地）

**风险**：若策略源码自身定义 `_qs_iso_*` / `_QS_ISO_*` 名字，会被误剔 ⇒ 等价性判据出现**假 PASS**
（把策略自己的代码当成注入内容删掉，从而掩盖真实差异）。

**防御（fail-loud，不静默）**：`normalize_product` 剥离前先扫**源侧**（或产物中不属于 ISO 块的部分），
若发现同前缀定义 ⇒ 记 `anomalies`（「ISO 命名空间被源策略占用」）⇒ P4 直接 FAIL 并指名冲突符号。
**禁止**"发现冲突就放行"。

### 11.7.5 不改 emitter（已裁定）

另一条路是改造 `_emit_module` 保留注释，但那会改变**全部注入块**的输出形态，影响面远大于本项
⇒ 不改（用户 2026-11-08 认可影响面判断）。

### 11.7.6 验收判据补充（照准项）

**P0-2 在 `policy=strict` 下会连"减仓/清仓"一并拒单**——这是 `target_orig` 全禁的**必然结果**，
属**预期行为**，**不得判为缺陷**：

- 期望现象：`QS_ISO_TARGET_ORIG_BLOCKED` 日志出现（`delta<=0` 分支）；
- 期 1 验收只看两项：①虚拟台账记账口径正确（现金/持仓/拒单计数）；②**真实持仓零变动**
  （隔离生效时策略的一切 target 类调用都不应穿透到平台原生）；
- **"策略没能卖出"不是缺陷，而是隔离在工作的证据**——期 2 起再补"隔离下的受控减仓"能力。

## 11.8 教训入册：紧急动作的**账户形态门**（2026-11-09 用户裁定）

**教训（双方同犯 framing 过度）**：⑨ 的既有判据（R19 判据本在）已区分账户形态，
我方在**未先核「账户形态 × 是否有真实资金暴露」两维**的情况下，直接把缺陷升级为
「立即停用」级紧急动作 ⇒ **把「模拟盘缺陷」framing 成「生产事故」**。

**入册判据（新增于本条）**：凡发出**立即停用/立即换装/立即回滚**类紧急动作前，
必须**先核两维并写明结论**：

| 维 | 取值 | 对紧急度的含义 |
|---|---|---|
| 账户形态 | 模拟盘（无真实资金）／实盘（真实资金） | 模拟盘 ⇒ 缺陷按**正常六步节奏**处理（修复→重转→下一交易日取证）；实盘 ⇒ 才 P0 级止血 |
| 资金暴露 | 有无真实委托可能 | 有真实委托可能但账户为模拟盘 ⇒ 记「行为数据照单全收」，把它当 **baseline 对照**而非事故 |

**附带的正确处置形态（本次实际收获）**：现版继续跑 ⇒ 14:50 的「未隔离下单面」行为
（下单标的/金额/台账表现）成为**隔离修复前后的天然对照 baseline**，收盘后回传分析。
⇒ **缺陷不等于必须停机**：在无真实资金暴露时，让它跑完反而产出对照数据。

⇒ 与本件其余判据同源：**先核事实维度，再定动作等级**；**动作强度须与暴露面匹配**。
