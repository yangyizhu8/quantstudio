> 六步流水线**第 1 步（方案）**｜提出：策略线会话｜2026-10-06｜**待总调度②审计**
> 触发：用户 GUI 实测反馈——A/B 落地后**日志已有告警**，但「**GUI 那头看起来一切正常**」，用户无从干预；
> 用户裁定 **D1** 并细化交互：「给出 GUI 弹窗，询问是否继续；继续则仍跑回测，取消则重新设置金额再跑」。
> 前置：A（设计契约本金校验）+ B（零成交诊断）已于 2026-10-06 ④验收 PASS（改动在工作树，等并入主仓批）。
> **本件＝纯 GUI 可见性 + 用户交互门；不改任何引擎数值逻辑。**

## 1. 问题定义（A/B 未覆盖的那一层）

| 层 | A+B 是否覆盖 | 用户体感 |
| --- | --- | --- |
| 日志可诊断性 | **已覆盖** | 告警只在 console 日志里，GUI 不呈现 |
| **GUI 可见性** | **未覆盖** | 回测页只显示进度与结果窗口，**看不到任何告警** |
| **运行前干预机会** | **未覆盖** | 点「开始回测」后必然跑完，用户**没有在开跑前改主意的机会** |
| 结果物提示 | **未覆盖** | 零成交时引擎**不写 `trades.csv`**，结果窗口照常显示「0% 收益、正常完成」，无异常横幅 |

**用户实测（2026-10-06 17:44）**：`init_capital` 仍为 100000、`trades.csv` 缺失（零成交）——A 的告警确实打进了日志，**但 GUI 没有任何可见反馈**。

## 2. 用户裁定（verbatim）

```text
D1（我建议）GUI 可见化：回测结束后，若本次运行产生「设计契约告警」或「零成交诊断」，
在结果窗口/弹窗显式呈现（复用 GUI 既有 QMessageBox.warning 模式）。

```

→ 本方案据此把 D1 拆为**运行前门（主）**与**运行后提示（附）**两块，**运行前门严格按用户交互语义实现**。

## 3. 改动范围（3 处，全部复用既有机制）

### 3.1 件一（框架层·复用式重构）：抽出**纯查询**函数，单一事实源

**落点**：`quantstudio/backtest/run_ptrade_strategy.py`

现状：A 件的 `_check_design_capital_contract(strategy_path, capital)` 把「解析契约」与「打日志」耦合在一起——GUI 需要一个**无副作用**的查询入口。

**做法**：拆为两层，**A 的对外行为与文案逐字不变**：

```python
def resolve_design_capital_contract(strategy_path):
    """纯查询（无副作用）：返回 dict 或 None。
    dict = {"required_initial_cash": float, "sizing_mode": str|None, "design_path": str}
    判据同 A 件：仅 design_metadata 解析 RESOLVED 且 required_initial_cash 非空才返回；
    其余（legacy / null / 解析异常）一律 None。"""

def _check_design_capital_contract(strategy_path, capital):
    """A 件原语义：查询后仅在 capital < required 时打一条 warning（文案/格式**逐字不变**）。"""
```

**理由**：GUI 门与 A 件**共用同一事实源**，杜绝「两处判定分叉」；且 `ROOT` 归属、`try/except` 守卫语义不变。

### 3.2 件二（GUI 层·运行前确认门）——**用户要求的核心**

**落点**：`quantstudio/gui/tabs/backtest_tab.py::_on_run`（`:174`），插入点在 F1 组合校验（`:219-224`）之后、组装 `params`（`:226`）之前。

**复用**：该函数已有成熟模式「校验 → `QMessageBox.warning(...)` → `return`」（`:184`/`:205`/`:211`/`:220`/`:310` 五处先例）。

**交互流程**：

```text
点击「开始回测」
  └─ 其它前置校验（DB 存在 / 保真模式 / F1 组合）依次通过
      └─ 【新增】resolve_design_capital_contract(strategy_path)
          ├─ None（legacy / runtime_total_value / 解析失败） → 静默放行，流程与今天逐字一致
          └─ 有值且 capital_spin.value() < required：
               QMessageBox.warning(
                   self, "初始资金低于策略设计契约",
                   "本策略声明 required_initial_cash=X，当前设置 Y（sizing_mode=fixed_notional）。\n\n"
                   "在资金不足时，本策略可能无法足额建仓，甚至全程零成交（回测结果将不具备参考意义）。\n\n"
                   "【继续】仍按当前资金运行回测；\n【取消】返回修改初始资金后再运行。",
                   [继续] [取消])
               ├─ 取消 → return（**不启动 Worker**，表单与输入保留，用户改金额后重跑）
               └─ 继续 → 继续往下（照常启动 Worker，日志仍含 A 件告警）
```

**实现要点**：
1. 按钮文案用 `QMessageBox.addButton("继续", AcceptRole)` / `addButton("取消", RejectRole)` 定制（默认 OK/Cancel 文案不达意）；
2. 判定值取 `self.capital_spin.value()`（`:230` 已用同一取值），**保证门与实跑用的是同一个数**；
3. 整块 `try/except Exception` 包裹，**异常一律放行**（GUI 门自身绝不阻塞正常回测；与 A 件同款守卫原则）；
4. **取消语义＝用户主动放弃本次运行**，非系统阻断——与已确认的 C1（系统不阻断）**不冲突**。

### 3.3 件三（GUI 层·运行后零成交提示）

**落点**：`quantstudio/gui/tabs/backtest_tab.py::_on_finished`（`:284`），在打开结果窗口（`:297`）之前。

**复用**：`workers.py:435-439` 的 `finished_ok` **已经携带 `trade_records`** → **无需任何日志管道**，直接判空即可。

```python
if not result.get("trade_records"):   # 与 B 件同判据（引擎 result.trade_records）
    QMessageBox.warning(self, "回测全程零成交",
        "本次回测 0 笔成交。可能原因：① 初始资金低于策略设计契约；② 信号未触发；"
        "③ 股票池/数据异常。\n\n回测仍将继续展示结果，但请核对后再采信。")
```

**放置顺序**：先弹提示、再打开结果窗口（保证用户注意力落在提示上）；该块必须与既有 `try/except`（`:297-308`）**并列**，不得改变其异常语义。

## 5. 影响面与「修复前置纯增益审计」三型判定

| 三问 | 件一 | 件二 | 件三 |
| --- | --- | --- | --- |
| ① 影响其他功能 | 否（拆分函数，A 行为/文案逐字不变） | 否（**仅本金不足时新增一次询问**；资金充足/legacy 时流程逐字不变） | 否（**仅零成交时新增一次提示**；有成交时无变化） |
| ② 影响性能 | 否 | 否（一次只读查询） | 否 |
| ③ 影响精度 | **否**（不改引擎） | **否** | **否** |

**类型＝新增检测型 + 用户交互门**：
- 「新增检测型」：新增能力开始报告真相（先前 GUI 无任何反馈）；
- 「**用户交互门**」：本轮**新增了一种既有流程里不存在的交互步骤**（仅在契约不匹配时出现）——按铁律「须在方案阶段单列该形态」，**在此单列**：
  - 触发条件严格限定（仅本金 < 设计契约）；
  - **不阻断**（用户可选「继续」），系统侧无任何强制；
  - 资金充足 / legacy / null 设计时**完全不出现**。

**影响面红线**：diff 只能归因于「新增 GUI 门与提示」；**引擎数值、产物、撮合、日志语义出现任何差异即验收失败回退**。
