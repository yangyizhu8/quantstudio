# 云端数据源头质量审计方案（cloud-source-quality-audit）

| 项 | 内容 |
|---|---|
| 文档版本 | v1.0（2026-08-17） |
| 定位 | **只读审计**（诊断取证，不改云端、不写库、不锁库）——为"全量重拉基线冻结"决策提供依据 |
| 背景 | 用户决策：暂停并行 → **云端源头质量审计** → 全量重拉基线冻结 → 数据管道稳定 → 策略逐个对齐 |
| 已有证据基础 | ① 云端分钟导出参照自身含 **07-01 因子污染**（515050 等 07-01 因子→1.0、07-03 恢复，85 例异常阶变）；② 云端分钟 `is_qfq=True` 与"分钟是不复权原始数据"的**语义矛盾**；③ 本地 front 污染（510020 front=raw×0.1006）疑似云端污染因子烧入 |
| 数据来源 | 本地已落盘的 MCP 全市场导出工件 `data/mcp_landing/exp_etf_minutes_*` / `exp_etf_daily_*`（18.1GB，66 窗，2025-01~2026-08）——**云端导出正本**；必要时 MCP 定点小查询补充 |

---

## 1. 审计目标（4 项判定）

| # | 目标 | 决策价值 |
|---|---|---|
| T1 | 云端分钟 `is_qfq` 语义定论（raw vs qfq） | 决定线1 还原路径正确性；决定重拉后的 raw/front 口径 |
| T2 | 云端因子污染范围（07-01 事件）定论 | 决定重拉是否会把污染重新拉入；是否需要云端修复 |
| T3 | 云端价格数据质量（raw OHLC） | 决定重拉后 raw 层可信度 |
| T4 | 云端数据新鲜度/完整性 + 因子-价格一致性 | 决定"全量重拉"可行性与基线冻结条件 |

## 2. 检查项与方法（全部只读）

### A. is_qfq 语义审计（T1）

| 检查 | 方法 | 判定 |
|---|---|---|
| A1 is_qfq 分布 | 导出工件统计 is_qfq 列 True/False 比例（按表/时间） | 100% True → 云端按 qfq 语义写入（与"raw"陈述矛盾）；混合 → 按行语义 |
| A2 raw 假说检验 | 抽 2-3 只 code（含 520810/510300）：**除权事件日 raw close 是否跳空**（raw 语义）vs 连续（qfq 语义）；对照 `close × adj_factor` 与除权日关系 | 除权日跳空 + 因子不变 → raw；除权日连续 + 因子变 → qfq |
| A3 还原一致性 | 对抽样 code：`close_raw（导出行）` 与 `close_raw × adj_i/adj_latest` 的连续序列对比，除权日两侧比率 | 确定云端存储的真实价格语义 |

### B. 因子污染审计（T2，07-01 事件）

| 检查 | 方法 | 判定 |
|---|---|---|
| B1 尖刺全量扫描 | 全 code：因子序列（日级末值）"回落到 1.0（或 -50%）再恢复"的尖刺（持续 ≤2 日且与前后差 >50%） | 尖刺 code 清单 + 时间分布（集中 07-01/07-02 → 批量写入错误；分散 → 单 code 问题） |
| B2 污染时间窗 | 尖刺时间直方图（全部尖刺的时间分布） | 单一时间点 → 一次批量事故；多点 → 系统性问题 |
| B3 污染与世代 | 尖刺发生前后的因子值特征（是否 1.0 归位） | 判定是否"世代切换残留"或"写库事故" |

### C. 因子阶变合理性（T2 补充）

| 检查 | 方法 | 判定 |
|---|---|---|
| C1 大阶变清单 | 因子相邻日变化 >50% 的 (code, date, old, new) 全清单 | 份额折算（整数倍）/真实事件 vs 异常（与 etf 历史事件交叉核验） |
| C2 阶变方向 | 因子应随分红递增（>1）——下降阶变清单 | 下降 = 份额合并（合理）或污染（需个案判定） |

### D. 价格质量（T3）

| 检查 | 方法 | 判定 |
|---|---|---|
| D1 基础合法性 | 每表全量：close/open/high/low ≤0、high < max(o,c)、low > min(o,c)、volume/amount <0 | 违规行计数（全量 SQL） |
| D2 量价一致性 | amount/(close×volume) 偏离 [0.5, 2] 的行 | 单位/字段错配嫌疑 |
| D3 零量 bar | volume=0 的 bar 分布（按 code/时间） | 513100 类零量缺口范围 |

### E. 新鲜度/完整性（T4）

| 检查 | 方法 | 判定 |
|---|---|---|
| E1 时间覆盖 | 导出工件 min/max 时间 vs 预期（2025-01-01~2026-08-16）；每 code 行数分布 | 缺口 code 清单（用交易日历核对缺失日） |
| E2 交易日缺失 | 每 code 每日 bar 数=0 的交易日（对照 trade_calendar） | 数据缺口清单 |

### F. 因子-价格一致性（T4，front 公式在云端正本验证）

| 检查 | 方法 | 判定 |
|---|---|---|
| F1 front 连续性 | 抽 3-5 只：`close × adj_i/adj_latest` 序列在除权日两侧的连续性（无跳变 = 因子与价格同源正确） | 跳变 → 因子或价格其一有误 |

## 3. 判定标准（审计结论输出）

1. **T1 定论**：云端分钟 = raw / qfq / 混合（附证据）；
2. **T2 定论**：07-01 污染 = 批量事故（范围 X code / 时间窗）或个案（清单）；污染是否影响"重拉"（若云端因子表本身含污染 → 重拉需先修云端因子）；
3. **T3/T4 结论**：价格质量可接受度 + 缺口清单 + 新鲜度状态；
4. **最终判定**：云端源头是否满足"全量重拉基线冻结"前提：
   - 满足 → 进入全量重拉基线冻结流程；
   - 不满足 → 云端修复清单（另走流程：云端修复方案 → 审计 → 实施 → 验收）。

## 4. 范围边界

- **只读**：仅读 `data/mcp_landing/` 导出工件 + MCP 定点查询（如需要）；不改云端、不写本地库、不锁库；
- **覆盖表**：本次导出工件覆盖的 `etf_minutes` / `etf_daily`（G2a 相关优先）；`stock_minutes`/`stock_daily` 工件未导出 → 列为后续补审（或先审计 ETF 侧，股票侧待云端导出后补）；
- 审计过程不触发任何写操作（含临时表仅内存/SQL 只读）。

## 6. 与当前轨道的关系

- 审计结论直接影响：①"全量重拉基线冻结"是否启动；②G2a 111 只重锚的处置（重拉若成功 → 合并；重拉若被污染阻断 → G2a 独立执行以修复当前漂移，13 只挂起仍挂起）；
- 本审计**不阻塞** G2a 执行决定（等待"全量重拉"决策期间，G2a 可独立先执行——但按用户"暂停并行"指示，暂挂起等待）。
