## 一、④ 深夜窗排查结论（**两案实测不同型，须先纠正派单假设**）

### 1.1 10-25 案（pid 52232）：**宿主连续重启致死（被动死亡）**

系统事件（源：`Get-WinEvent` System/Application，10-25 00:40–01:50）：

| 时刻 | 事件 | 含义 |
|---|---|---|
| 00:53:09 | `User32 id=1074` StartMenuExperience 发起 | **关机开始** |
| 00:53:12 | `winsrvext` WARN：CodeSetup/wps/wpscloudsvr **延迟系统关闭** | 关机中 |
| 00:54:08 | `EventLog id=6006` 事件日志服务停止 | 已停 |
| 00:54:52 | `EventLog id=6005` 事件日志服务启动 | **开机** |
| **00:54:58** | **`Application Error` questdb.exe 崩溃** | QuestDB 被强杀 |
| 00:55:13 | `User32 id=1074` **TrustedInstaller.exe** 发起 + `VSS 0x8007045b 系统正在关机` | **Windows Update 发起关机** |
| 00:55:13 | `EventLog id=6006` 停止 | 已停 |
| 01:42:00 | `EventLog id=6005` 启动 | **开机** |
| **01:42:06** | **questdb.exe 崩溃** | — |
| 01:42:24 | `User32 id=1074` **winlogon.exe** 发起 | **又关** |
| 01:45:24 | `EventLog id=6005` 启动 | **开机**（此后稳定） |
| 01:45:30 / 01:49:31 | questdb.exe 崩溃 ×2 | 共 **4 次** questdb 崩溃 |

**⇒ 结论**：10-25 00:53–01:45 期间**宿主连续 3 次关机/重启**（StartMenu → Windows Update → winlogon），daemon 随宿主被终止。**daemon 自身无缺陷可修**——它没有机会写日志、没有机会写 status、也没有机会"自报"。

### 1.2 10-22 案（pid 14476）：**不同型！窗口内无关机事件**

- 10-22 00:40–01:20 System/Application **无 id=1074/6006/41 任何关机或非正常关机记录**；
- 10-22 **全天无 questdb.exe 崩溃**（Application Error 全是 `TdxW.exe` 通达信客户端，10 次）；
- 该窗仅见：00:41:01 `Tcpip` WARN「**全局 UDP 端口空间耗尽**」、多起 DCOM 权限 WARN。

**⇒ 结论**：**派单假设「两案同型、同深夜窗」经实测不成立**。10-22 案的真实死因**无法从现有证据确定**——这正是 W-2 ②（stderr 不落盘）造成的可观测性缺口：**进程死亡瞬间无栈、无 stderr、无 exit code**。

### 1.3 ④ 对方案件的影响（重要）

| 派单项 | ④ 排查后的判断 |
|---|---|
| **① 外部心跳巡检** | **论证被强化**：宿主重启场景下进程内任何自报机制都失效（来不及写），**唯一可行手段就是外部观察者** |
| **② stderr 捕获落盘** | **价值被削弱但不否定**：对"宿主重启"场景无效（SIGKILL 无机会 flush）；对「10-22 那种进程自身异常退出」**仍然有效**——那是唯一能拿到栈的场景 |
| **③ status.json 陈旧自愈** | **论证被强化**：重启后 status 残留旧 pid ⇒ 任何"读 status 判活"的消费者都会被骗 |

## 二、① 外部心跳巡检方案（纯增量 · 不改 daemon 任何代码）

### 2.1 定位与边界

- **形态**：独立 Windows 计划任务 + 只读探测脚本；**不 import、不修改 daemon 任何模块**；
- **职责**：**发现**（存活真相）+ **告警**（飞书）；**是否自动拉起留待 §四③ 评估后定**（见 2.5）；
- **对标**：云端 R-7 watchdog 模式（外部观察者 + 周期探测 + 告警）。

### 2.2 判据（三条，全部只读）

| # | 判据 | 实现 | 为什么必须三条一起看 |
|---|---|---|---|
| **H1** | **进程存活** | 按命令行匹配 `quantstudio.pipeline.daemon`（**不能用 `pipeline.daemon` 子串**——历史两次误判均因匹配式过窄漏掉文件路径启动形态） | 唯一真相源 |
| **H2** | **status.json 与进程一致** | 读 `data/daemon_status.json` 的 `pid`，用 `Get-Process -Id` 校验该 pid **当前是否存活且命令行匹配** | 宿主重启后 status 残留旧 pid ⇒ 只看文件存在/只看 mtime 会假阳性判活 |
| **H3** | **心跳新鲜度** | status `create_time` + 日志 mtime 双龄 | 进程在但假死（挂住不写日志）——H1/H2 看不出来 |

**判级**：

| 组合 | 判级 | 动作 |
|---|---|---|
| H1 活 + H2 一致 + H3 新鲜 | **OK** | 静默（不产生推送噪声） |
| H1 活 + H3 超龄（> 3× 轮询间隔） | **WARN 疑似假死** | 告警（含日志末行 + status 内容） |
| H1 死 或 H2 不一致 | **FAIL 静默死亡** | 告警（含「宿主是否在期间重启」的**事件日志旁证**，见 2.4） |

### 2.3 关键设计：把「宿主重启」与「daemon 自身崩」区分开

这是本方案与普通 watchdog 的差别，也是 ④ 排查带来的直接产物：

巡检在判 FAIL 时，**同时查该时段 `System` 日志有无 `id=1074/6006/41`**：

- **有重启事件** ⇒ 告警文案标 `[宿主重启所致]` ⇒ 不触发任何"重启 daemon"的自动动作（重启了也会被下一次关机杀掉，且没必要）；
- **无重启事件** ⇒ 标 `[daemon 自身异常退出 · 需 ②stderr 取证]` ⇒ 这才是需要人介入的信号。

⇒ 这样告警**自带归因提示**，避免收到告警的人重复我们这几天做过的排查。

### 2.4 轮询间隔与成本

- **间隔建议 10 分钟**（不是 5 分钟）：daemon 的 `check_interval=300s`，但巡检目标是"死亡发现"，10 分钟延迟对采集影响可接受；更密的间隔只增加噪声与开库次数（**注意：巡检脚本必须只读，绝不能 `create_writer`/`init_schema`，否则会与 daemon 抢 DuckDB 单写锁**）；
- **成本**：每次 3 次只读系统调用 + 可能的 1 次事件日志查询（仅 FAIL 时）⇒ 可忽略。

### 2.5 「自愈」范围（明确留给③，本文不做）

总运维口径「**自愈仅启动时**」——即当前不存在运行期自动拉起。本方案**默认只告警不拉起**，理由：
1. 宿主重启场景拉起无意义（会被再次杀掉）；
2. 自动拉起会与「daemon 生命周期跨会话占用纪律」冲突（外部脚本擅自启停 daemon 是纪律禁区）；
3. 若确认要拉起，须先解决 **status 陈旧互斥**（③）——否则新进程会与残留 status 打架（历史已有抢登现象）。

### 2.6 改动范围（精确）

| # | 文件/对象 | 性质 |
|---|---|---|
| 1 | `scripts/check_daemon_alive.ps1`（新建，只读探测 + 告警） | **纯新增** |
| 2 | Windows 计划任务 `QS_DaemonHeartbeat`（每 10 分钟，`schtasks` 登记；提供 `register` 脚本） | **纯新增** |
| 3 | **不触碰**：`quantstudio/pipeline/**`、`data/quantstudio.db`、任何 daemon 状态文件（只读） | — |

### 2.7 验收标准

1. **负向对照**：手动停 daemon（在声明窗口内）⇒ 10 分钟内巡检报 FAIL 且告警含 `[daemon 自身异常退出]`；
2. **宿主重启对照**：以 10-25 00:53–01:45 事件为样本回放判级逻辑 ⇒ 必须判 `[宿主重启所致]`（可用合成输入单测，不真重启机器）；
3. **零干扰**：巡检运行期间 daemon 的 DuckDB 写操作零失败（证明未抢锁）；
4. **噪声控制**：健康态连续 10 轮零告警（静默设计生效）。

### 2.8 回退条件

删除计划任务 + 删脚本即完全回退；因**不改 daemon 任何代码、不写任何数据**，回退零风险、零残留。

## 三、与既有纪律的关系

- **19 号铁律（daemon 生命周期占用）**：本方案**只观察不启停** ⇒ 不触碰该纪律；若将来纳入拉起，须回归该纪律（声明窗）。
- **08 号铁律（框架问题立即解决）**：①是「新增检测能力」，按 **18 号铁律的「新增检测型」** 定性——开始报告真相不算行为漂移，但**必须单列**，不得与纯恢复型混办。
- **24 号铁律（schema 指纹）**：巡检**只读**，不 `create_writer` ⇒ 不触发 schema 安全闸，但**这是硬约束**，须写进脚本注释与验收项。

## 四、②③ 二期分列（**不与①捆一笔**）

| 项 | 为什么单列 | 依赖 |
|---|---|---|
| **② stderr 捕获落盘** | 改 daemon 进程启动方式（`2>` 重定向到独立文件）或改 `main` 入口 ⇒ **触 daemon 代码**，须六步完整流程 + 专门窗口；④ 显示它对宿主重启无效，但对「10-22 型」是唯一取证手段 | 无（可独立推进） |

**②③ 建议合并一次 daemon 改动窗口**（同域，可共享一次受控窗与一次回归），但仍须各自走六步的方案与审计。
