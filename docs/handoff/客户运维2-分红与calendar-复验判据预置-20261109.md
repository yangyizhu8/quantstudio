# 第一部分：分红全表重扫（方向 A · legacy 分支集合化）

## 1.1 分工层定性（勿混谈）

| 层 | 定性 | 依据 |
|---|---|---|
| 「每轮全表重扫 `stock_dividend`」 | **设计如此**（有意取舍） | `qfq_event_discovery.py:8`（模块 docstring）、`:149`（函数 docstring）：「全表扫描，不依赖日期 cursor —— **防晚到修订漏检**」。分红公告的 `record_date`/`ann_date` 可晚于 `ex_date`，按日期游标过滤会**永久漏检**历史行的后续修订 |
| 「每行 2 条 SQL ＋ 逐行 autocommit」 | **缺陷** | `_scan_dividend_legacy`（`:372-408`）每行 1 次 `_trigger_exists`（`:388`）+ 1 次单行 `INSERT OR IGNORE`（`:389-398`），且该分支**无 `BEGIN/COMMIT`**（对照 `_scan_dividend_v2_rowwise` 的 `:235/:266/:268` 有事务）⇒ 31,834 行 × 2 ＝ **63,668 条 SQL**，每行一次独立事务+WAL 提交 ⇒ **耗时与写入量无关**（写入 100% 被 IGNORE 仍跑 19~49 分钟；我方历史实测「零写仍 12.10 min」见 `docs/qfq-post-ingest-discovery-nplus1-design.md:53-56`） |

**客户为何落在未优化路径**：分支闸 `:200-207` 按 `identity["source_generation"]` 分流，`pre_cutover_qfq_identity` **恒返回** `xtquant-legacy`（`qfq_schema_contracts.py:1332/1355/1359`）⇒ 批量路径 `_scan_dividend_v2_batch`（`:279-367`，2026-09-27 已实施并逐位等价验收）对客户身份**不可达**。

## 1.3 两条明确否决（防走错方向）

| 方案 | 否决理由 |
|---|---|
| **加 cursor 下界**（客户曾建议） | 会**从设计上取消「防晚到修订漏检」**＝用正确性换性能。若确需增量窗口，须**独立立项**（行为变更型）并配「低频全量对账」兜底，不与本次性能优化捆绑（铁律 02：性能与正确性必须拆分） |
| **直接切 `_scan_dividend_v2_batch`** | v2 用 `trigger_id_v2`（含世代列、版本 2）+ `qfq_discovery_baseline` 集合 CAS，而 legacy 用 `trigger_id_of`（v1，`:396` 硬编码 `1`）且无 baseline 语义 ⇒ **trigger_id 口径变更＝可观察结果变更**，且会与库中既有 v1 trigger 产生双份 ⇒ **只借鉴其批量化结构，不切换实现** |

| # | 构造 | 期望 | 性质 |

# 第二部分：`trade_calendar` 任务顺序前置

## 2.1 现象与根因

客户实测（11-05）：
```
08:45:00 ERROR [qfq_orch] 159331 apply 异常: trade_calendar 未缓存 1793548800000（未知日期，无 provider 不可判定）
08:45:44 ERROR [qfq_orch] 180102 apply 异常: 同上
```
`1793548800000` ＝ 2026-11-02（北京）。根因：**任务顺序** —— `mcp_stock_daily` 在第 8 位、`mcp_trade_calendar` 在第 **13** 位，qfq 在 08:44:37 就进入 apply，日历任务尚未执行 ⇒ 新交易日无法判定。

## 2.2 落点与现状（11-09 实读）

| 项 | 实测 |
|---|---|
| 文件 | `config/profiles/mcp_only/collector_tasks.json` |
| 上游 HEAD 位置 | **`mcp_trade_calendar` 第 13 位**（总 88）；`etf_daily` 第 2、`index_daily` 第 3、`stock_daily` 第 8、`stock_daily_valuation` 第 9 |
| 工作树位置 | **第 14 位**（因他线 `mcp_etf_daily_backfill_20260907_20261016` 插到第 2 位，整体后移 1）⇒ 工作树该文件的 M **不是** calendar 改动 |
| 分钟任务位置 | `etf_minutes` **第 87**、`stock_minutes` **第 88**（「分钟任务最后」约定成立） |

## 2.3 判据

| # | 判据 | 期望 |
|---|---|---|
| **C1** | 位置 | `mcp_trade_calendar` 移到**第 1 位**（最低要求：早于所有 `COORDINATED_PRICE_TABLES` 任务，即早于现第 2 位的 `etf_daily`） |
| **C2** | **不违反既有约定** | 「分钟任务最后」约定不被破坏（calendar 非分钟任务，移前无冲突）；须确认不违反用户既有裁定「日线/非分钟先，分钟任务最后」 |
| **C3** | 配置合法 | `config_lint` **0 错误 0 警告**（客户侧实测 `[ConfigLint] 校验通过（0 错误，0 警告）` 为基线） |
| **C4** | 构造正常 | `QFQOrchestratorConfig` 构造成功，`max_units_per_cycle` 仍为**默认 60**（客户曾试改 8 并按要求撤回，**不得**顺带改动配额） |
| **C5** | 逐字节等价 | 除 calendar 整块位置搬移外，文件与改动前**逐字节等价**（客户侧验证方式：剔除 calendar 整块后逐行比对，2718 行 vs 2718 行全等） |
| **C6** | 客户侧不冲突 | 上游化后客户 `git pull` 不再需要 `git checkout --` 该文件；**下发通知须含 pull 步骤与验证清单**（铁律 12） |

## 2.4 副作用提示（非阻塞）

- 顺序前移后，**日历任务失败会阻塞后续价格任务**（原来它排后面，失败影响小）⇒ 建议同时确认 `mcp_trade_calendar` 的失败重试策略足够（否则前移会把「日历偶发失败」放大为「全线停摆」）——**这一条请节点1 在实施时评估**，我域只提示风险，不代为决定。
