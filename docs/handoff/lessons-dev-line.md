## L-20261109-01 · 探查正则须与生产解析正则同源

- **现象**：探查脚本报「registry 无机读块 / 字段缺失」，结论为「产物缺陷」；实际产物正常、生产解析也正常。
- **真因**：探查脚本自带正则 `r"```(?:json)?\s*\n(.*?)```"` 只涵盖空标注与 ```json，而产物围栏标注为 **```alias-map** ⇒ 漏匹配 ⇒ **假阴性被当成产物缺陷**。
- **生产侧正确做法**：`docs/handoff/dispatch/graph-lint.py:335` `RE_ALIAS_FENCE = re.compile(r"```alias-map\s*\n(.*?)```", re.S)`；直调 `load_registry_alias_map` 得 `source=registry / aliases=23 / note=''`，`check_registry_consistency` findings=0 ⇒ 三重实证产物无缺陷。
- **硬动作**：
  1. 任何「探查/自检脚本」解析结构化产物时，**必须复用生产侧的解析常量为唯一实现**（import 或同源复制并注明出处行号），**禁止自写近似正则**；
  2. 探查结论为「缺陷」前，先做**正向对照**（构造应命中样本，验证探查器本身能命中）；
  3. 探查器与生产解析器**不同源**时，两者结论冲突**以生产解析器为准**，探查结论标「待核」不得直接上报为缺陷。
- **代价实例**：2026-11-08 据此误报「registry 需补机读块」，导致 DSH 侧一轮核查与指令撤回（`R7→R1` 两轮）。
- **来源**：用户 2026-11-09 01:12 澄清 + 我方 01:18 三重直调自我更正。

## L-20261110-01 · 申报「已补/已完成」前必核三证

- **事故**：2026-11-10 01:38 我方申报「归因件三条件已补」为**失实**——实测文件 mtime 00:19:13 未变、§七 仍为「待⑪ 补参数节」、§五.1 阈值仍待；被审核方打回。
- **双重根因**：
  1. **单位混读**：把「3,807 字符」与「6,435 B」当作「补前 / 补后」两个读数，实为**同一文件的两个单位**（中文 UTF-8 约 1.67 B/字符）；
  2. **脚本未执行而未核**：该轮 Python 脚本因 heredoc 引号冲突 **SyntaxError 整脚本未运行**（patch 未执行），仅凭尺寸数字推断已补。
- **硬动作（三证，缺一不得申报）**：
  1. **mtime 前后对照**（证明文件真被写）；
  2. **目标串机检**（预期出现的 3–8 个关键字符串逐一 `in` 判定并打印 ✓/✗）；
  3. **双单位对照**（字符数与字节数**同时**给并标明换算）——**禁止以单侧尺寸变化代替内容核验**。
- **附加**：凡用 heredoc/内嵌脚本批量改文件，**先确认脚本 exit=0 且无 stderr**；脚本报 SyntaxError 时**产物一定未变**。
- **代价实例**：2026-11-10 02:30 被打回，02:32 真补后 8 串机检全 ✓ 才过审。
- **来源**：用户 2026-11-10 02:30 打回 + 02:56 采信「建议入你线常驻判据」。
