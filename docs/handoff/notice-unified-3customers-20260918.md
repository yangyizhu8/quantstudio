**【修复完成】数据停更已修复，请按 4 步更新（约 5 分钟）**

原因：采集程序写库时异常结束，留下了一把未释放的「写锁」；旧版本对这种残留锁只告警、不清理，之后每次写库都在等待 30 秒后失败 → 数据停更。**数据库没有损坏，已有数据完整可用。**

修复：系统现在会先判断「持锁进程是否还存在」——**已不存在**则安全回收并恢复写入（留审计与告警）；**仍在运行**则一律不回收（防止两个写入者同时写库）。同时修好了 7 张宽文本表（AI 研报快照 / 研报文本 / 新闻等）此前必然失败的问题。

**更新 4 步**（先**停止采集程序**；以下命令在 Windows 的 PowerShell 与 macOS 的终端中同样可执行）：

```bash
cd <你的安装目录>        # Windows 例："D:\quantstudio"    macOS 例：/Volumes/ssd/quantstudio
git pull
git log --oneline -1     # 应看到 7192017 或更新
# 然后重新启动采集程序，观察一个采集周期
```

**更新后核对 3 项**

1. 启动日志**不再出现**「写锁被持有」；
2. 数据目录 `snapshots/` 下没有残留 `.write_lock`；若出现 `write_lock_reclaim.log`，**1 条属正常**（首次启动回收了历史遗留锁的审计留痕）；
3. 一个采集周期后，任务出现 `raw=... written=...` 的成功行 → 数据恢复更新。

**若仍未恢复（重要）**

重启后**超过 10 分钟**仍持续出现「写锁被持有」→ 请把日志发我们，并**保持 `data/snapshots/.write_lock` 原样（不要删除、不要改名）**。日志会写明判定结论：

- 「**持有者进程仍存活**」→ 请把进程检查输出发我们（Windows：`Get-Process -Id <该 pid>`；macOS：`ps -p <该 pid>`）；
- 「**持有者进程已不存在**」却仍未恢复 → 请立即联系我们。

请勿在采集运行中删除锁文件（可能导致两个写入者同时写库）；如确需清理，请先停止采集程序。

**口径桥接（若此前收到过详版速查卡）**：若您此前收到过详版速查卡中的「改名」四步处置，请注意——该四步**仅适用于更新到 7192017 之前的旧版本应急**；**更新后请以本通知为准**（保持锁文件原样、发日志即可，无需改名）。

**预期行为（如实说明）**

正常情况仍是「谁先拿到谁写」、等待上限 30 秒，不改变数据口径与使用方式；异常情况（强制结束/断电）锁**不会立即释放**，而是在心跳过期**约 10 分钟后自动回收**——即最坏**约 10 分钟写入等待**，而不再是**永久停更**。我们**不宣称**已解决所有锁相关问题（强杀/断电的「瞬时」释放属另一项底层改造，已在计划内）；本次确保的是：**进程确实已经终止后，系统能自己恢复**。
