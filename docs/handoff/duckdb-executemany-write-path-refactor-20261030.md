# 立项件：消除 duckdb 1.5.x `executemany` 批量写时延劣化（RSK-DUCKDB-001 解除路径）

- **日期**：2026-10-30｜**归属**：主仓维护线｜**关联**：spec 002-duckdb-1.5-upgrade（T051「改写入形态单独立项」、A-14 风险登记 `RSK-DUCKDB-001`、KB `DB-2026-0001`）
- **状态**：**立项（本件只立项，不实施）** —— 实施须另起六步流水线（方案 → ②审 → 实施 → 验收 → ⑤用户确认 → ⑥双仓推送），并按窗口纪律处理主库写入

## 一、目标

把本项目**唯一**走 `executemany` 的写者落点改为**零拷贝注册路径**，消除 duckdb 1.5.x 上的 4–6 倍时延劣化；**内容与口径逐位不变**。

## 二、落点（单点，禁止扩面）

| 项 | 内容 |
|---|---|
| **文件** | `quantstudio/pipeline/index_constituents_meta.py` |
| **行** | `:125`（`executemany` 调用处） |
| **目标表** | `index_constituents_snapshot_meta`（PK `(index_code, time)`） |
| **改动形态** | `executemany` 逐行绑定 → DataFrame 零拷贝注册（`duckdb.register` / `con.register`）+ `INSERT INTO … SELECT`（**该形态在 1.5.6 上实测不受劣化影响**） |
| **明确不改** | 表结构 / 列集 / PK / 行序语义 / 其他任何写者 / 主库读写纪律 / 其他表 |

## 三、判型与验收（铁律 18 纯性能型）

> **纯性能型**：可观察结果不变 —— 黄金结果逐项一致（仅允许既有测试契约明确的浮点容差）。

| 验收项 | 判据 |
|---|---|
| ① 内容逐位一致 | 同一数据集经改前/改后写入后：**列集一致 + 行数一致 + 内容 sha256 逐位一致**（与 PT-01a 的双写比对同一套读数法） |
| ② 性能达标 | 三个批次量级（300 / 1000 / 5000 行）**倍数 ≤2× 且绝对值 ≤5s**（1.5.6 相对 1.4.5）；5000 行**须在 90s 内完成**（当前为超时未完成） |
| ③ 回归零衰减 | 既有测试全绿（含 `tests/test_passthrough_pk_preservation.py` 等框架层用例）；主库相关黄金结果零 diff |
| ④ 窗口纪律 | 若验证需写主库：**停 daemon + 按铁律 19 声明占用窗**，窗口内禁一切会 `create_writer` 的入口；优先用**独立临时库**验证 |
| ⑤ 双端对等 | 若新增 CLI 入口，须同时提供 PyQt 等价入口（铁律 20/单模块双端对等） |

## 四、不在本期（首跳）的理由

- 首跳（1.4.5 → 1.5.6）的唯一目的是**维持受支持状态**（1.4 线 2026-11-17 EOL），不是性能优化；
- 写入形态改动属**纯性能型新范围**，擅自并入会**扩面**并把「升级风险」与「性能优化」混在一笔里（铁律 02/18 要求拆分）；
- 该路径为**辅助表刷新**，300 行量级 3.9s 不影响正确性与主链时延（已在 `RSK-DUCKDB-001` 登记 + 客户通知量化提示）。

## 五、风险与回退

| 项 | 内容 |
|---|---|
| 改后风险 | 零拷贝注册路径的**类型/列序/dtype 映射**与 `executemany` 不同，可能产生**隐式转换差异** ⇒ 必须由验收①（sha256 逐位）拦截；若不一致即**回退**（单文件、单落点 ⇒ 回退成本 = 还原该函数） |
| 回退条件 | ①内容逐位不一致；②性能未达标；③既有测试回归；④出现新 FATAL |
| 回退点 | 改动前按铁律 03 四步建零副作用回退点（`git stash create` + `store` 持久化）；单落点 ⇒ 亦可单文件定向还原 |
| 依赖 | 若上游修复 `executemany` 劣化（`duckdb#23645` 关闭或新补丁发布）⇒ **先复核上游是否已解**，再决定是否仍需本立项（避免重复投入） |
