## 一、为什么需要三态（两态会漏）

只写「已完成 / 未收尾」两态，会漏掉第三种：

| 态 | 判据 | 典型成因 | 漏判后果 |
|---|---|---|---|
| ① 已完成 | `status=completed` **且** `scheduled_date=目标日期` | 正常 | — |
| ② 未收尾 | `status=running` 或 `finished_at` 为空 | 轮次还在跑 | 误判失败 |
| **③ 未启动**（易漏） | `status=completed` **但** `scheduled_date=前一日` | **daemon 不在**（无人触发） | **把昨日读数当今日交**——最严重的假绿 |

**核心纪律**：报读数必须标注**数据归属日期**；字段齐全 ≠ 是今日。

## 二、模板正文（直接复制改写）

```text
<任务名>取数。

**第 0 步：判轮次态（三态，缺一不可）**
读 `data/daemon_run_state.json`：
- 态① 已完成：`status=completed` 且 `scheduled_date == <目标日期>` ⇒ 进第 1 步；
- 态② 未收尾：`status=running` 或 `finished_at` 为空 ⇒ **只报进度 + ok/fail，不判失败**，
  重挂 60 分钟后再取；
- 态③ 未启动：`status=completed` 但 `scheduled_date == <前一日>` ⇒ **如实报「目标日轮次未启动」**，
  **不判失败、绝不用前一日读数冒充**，并报请调度决定是否补跑（**不盲目重挂**）。
  （态③ 常见成因：daemon 未运行 ⇒ 顺带核 daemon 是否存活，判据见第 3 步）

**第 1 步：报读数（A/B/C 三分类，不得混报）**
- A 预期绿：<列出期望值>
- B 意外但有用：<列出「看着像故障其实是数据」的项>（例：skipped_oom/timeout > 0 ⇒ 阈值调参数据）
- C 真异常：<列出真故障判据>
每条读数**必须标注归属日期**（哪一轮）。

**第 2 步：变形判据**
<该任务特有的边界态，例如 gap_snapshot 缺失 ≠ 我方问题>

**第 3 步：形态判据（判 daemon 是否运行）**
**必须核命令行 `--mode`**：`--mode forever` = 守护；`--mode once` = 单任务。
只看「有 python 进程」或 `daemon_status.json` 会误判（2026-11-01 实证）。

**纪律**：全程只读；跑前查占用板三件套（`data/snapshots/.write_lock` 的 pid/task/心跳、
`daemon_status.json`、是否有他线在跑窗口）；不启停 daemon；不触碰 aux 写入。
```

## 三、附：占用板三件套（每次触主库脚本前）

| # | 动作 | 命令/文件 |
|---|---|---|
| 1 | 查锁 | `data/snapshots/.write_lock`（`pid` / `task_id` / `heartbeat` / 存活） |
| 2 | 查 daemon | `data/daemon_status.json` + **命令行核 `--mode`** |
| 3 | 声明自身连接形态 | 脚本里显式 RO（`duckdb read_only=True`；`sqlite3` 用 `mode=ro` URI）；RW 则先声明窗口 |

**判据**：脚本跑完必须能回答「我有没有对生产库持有任何写句柄」；回答不了就是没做对。
