# 知识条目同 id（duplicate_id）族级兜底设计（待审 · 交付窗口 2026-11-20T20:56:50+08:00 前）

> **来源**：2026-11-15 R3 审核指示「试点后兜底方案须列**覆盖范围、责任人和撞 ID 负例**」。
> **性质**：**设计稿**（不改实现、不接线、不改档位、不改计数与回 `off` 条件）。
> **问题源**：`kb_hook` 的 `duplicate_id` 检测**仅在本次 `--files` 展开且成功解析成功的集合内**比对 ⇒ **全族撞 id 目前没有发现路径**（试点期靠每日人工全量兜底，试点结束后该盲区仍在）。
> **交付时点**：**2026-11-20T20:56:50+08:00 前**（＝试点窗止；到期须有承接方案，否则全族撞 id 无发现路径）。

## 1 覆盖范围（三种方案，**建议乙**）

| 方案 | 覆盖范围 | 成本 | 结论 |
|---|---|---|---|
| **甲 全库一次展开** | 一次 `--files` 传全库四族 glob（qd+pd+db+ops 共 93 件） | 单次 parse 93 件 | 可行但**跨族同 id 语义未定义**（见 §4 N4），且把无关族带入同一比对集合 |
| **乙 按族展开（建议）** | **每族一次** `--files "knowledge/<族>/<PREFIX>-*.md"`（ops 5／db 44／qd 22／pd 22），**族内**全量 | 4 次调用，每次 parse 一族 | **一次 glob 展开即覆盖该族全部条目 ⇒ 查重范围自动=全族**；族内 id 唯一性语义清晰；与现行每日扫描命令同形 |
| 丙 仅 ops | 只覆盖试点族 | 最小 | 不解决 qd/pd/db 的同族撞 id ⇒ **不足** |

**建议：乙。** 落地形态＝一条命令族（每族一次），由责任方按每日频次执行；**不新增钩子、不接 CI/pre-push**（与试点期边界一致）。

**范围口径三句话（写入族 README 的判据面）**：
1. 查重**只在同一次 glob 展开且成功解析成功的集合内**进行（`kb_hook.py` L334 打点 / L347-358 比对）；
2. **同族**全量 glob ⇒ 同族撞 id **必被发现**；
3. **跨族同 id 不算冲突**（见 §4 N4，待裁）。

## 3 撞 ID 负例（三例已实测，2026-11-15；沙箱内，**真库零改动**）

| # | 构造 | 期望 | 实测读数 |
|---|---|---|---|
| **N1** | 同一次 glob 展开出 `X.md` 与 `X.draft.md`（**同 id**） | **报 duplicate_id**（两件都进 `bad`） | `total=2 checked=2`，`duplicate_id` 命中 **2 件**，错误文案含对方文件名 |
| **N2** | 同 id 两件**分两次调用**（不在同一展开集合） | **不报**（批内限定成立） | 单件A `bad=0 duplicate=0`；单件B `bad=0 duplicate=0` |
| **N3** | 同 id 两件，其一 front-matter **不可解析** | **不报**（范围＝成功解析的集合） | `duplicate_id=0`（该件未进 `id_seen`；**注**：实测中该坏件既未报 `duplicate_id` 也未报 `parse_fail`——解析器对损坏 front-matter 返回空记录而非抛异常，故它**静默不入比对集合**） |

**N3 的附带发现（须在方案中处置）**：损坏 front-matter 的条目**既不报结构错误、也不参与查重**，等于"静默漏检"。⇒ 兜底设计应附带一条**解析失败显式化**要求（待另审，不在本件实施）。

## 4 待裁口径（不自行决定）

| # | 事项 | 我方建议 | 理由 |
|---|---|---|---|
| **C1** | 跨族同 id（qd 与 db 各一条同 id）算不算冲突 | **不算冲突**（仅同族），可打印提示不阻断 | 各族 `id_pattern` 是族内唯一性约定；跨族同 id 不构成下游"同 id 多条"消费问题 |
| **C2** | 兜底频次 | **每日 ≥1 次全四族**（与试点期同频次），加**条目/判据/配置变更后复核** | 变更后不立即扫，撞 id 会滞到次日 |
| **C3** | 撞 id 件的处置权（保留/移出/删除） | **内容判定归⑫、执行归⑥、判据变更归审核方**；**不得为清零直接删他线条目** | 与试点期同纪律 |
| **C4** | 解析失败条目是否显式阻断 | **先显式报 `parse_fail`（不阻断）**，再议是否阻断 | 现状"静默漏检"比"报了但不断"更危险 |

## 5 验收判据（方案获批并实施后）

1. 四族各跑一次全量 glob ⇒ `checked` 与该族条目数**逐一相等**；
2. 任一族内造同 id 两件 ⇒ 两件**都进 `bad` 且含 `duplicate_id`**（N1 复现）；
3. 同 id 两件分两次调用 ⇒ **不报**（N2 边界保持）；
4. 未启用族（qd/pd/db）的 payload 与实施前**逐位一致**（纯增益）；
5. 每日读数入台账，缺日如实登记；**确认无法履行即按已批条件仅 ops 回 `off`、清 `since`、留证**（不回退此项兜底义务本身）。

## 6 边界（不因本件改变）

- **不改试点档位**（qd/pd/db `off`、ops `warn`、各自 `since`）、**不改每日计数口径**、**不改人工回 `off` 条件**；
- **不新增自动任务/接线**（不接 pre-push/CI/kb_draft）；本件只是**设计**；
- 不改 `kb_hook.py` 实现（除 C4 若获批另议）。
