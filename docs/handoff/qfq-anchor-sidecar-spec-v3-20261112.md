## 二、消费方判定矩阵：**接口由本件定义，内容由 ⑱ 供给**

### 2.1 权责划分（复合 R13 裁定「⑱ 转消费方复核角色，勿互改语义」）

- **⑱** 出矩阵**内容**（其 v3 所附矩阵）：哪些消费方读哪条路径、需要何种锚、容差等级。
- **㉑** 出矩阵**接口与执行规则**（本节）：维度定义、取值集合、判定输出、未到位时的默认行为。
- **禁止**：本线不代 ⑱ 填矩阵行、不改其语义；⑱ 不代本线改 sidecar 协议语义。**双向禁越界**。

### 2.2 矩阵接口（⑱ 按其 v3 填行）

| 维度 | 取值集合 | 语义 |
|---|---|---|
| `consumer_id` | 自由标识（如 `AQ-DW`／`L2-replay`／`MCP-export`／`GUI-minute`） | 消费方主体 |
| `read_path` | `source_mirror` ／ `delivery_front` ／ `mixed` ／ `none` | 实际读哪一侧（用于 §1.2 判据 12 条件） |
| `anchor_need` | `as_of_ratio` ／ `current_ratio_only` ／ `none` | 是否需要**写时**锚（as-of）／只需当前比值／不需锚 |
| `tolerance_class` | `strict` ／ `bounded` ／ `report_only` | 锚不符时的处置强度 |

### 2.3 判定输出三值（**必须显式区分，不得以空集/truthiness 混判**）

| 判定 | 条件 | 消费方义务 |
|---|---|---|
| `anchor_required` | `anchor_need=as_of_ratio` | 必须命中 `anchor_origin='write_time'` 段；命中 `legacy_unverified` ⇒ **reject 该段并报告**（不得静默降级） |
| `anchor_degraded` | `anchor_need=current_ratio_only` 或 `tolerance_class=report_only` | 可用 inferred 段，但**输出须带 `degraded=true` 标记与段清单** |
| `anchor_irrelevant` | `anchor_need=none` | 不读锚，不参与判据 |

### 2.4 未到位默认行为（fail-closed 取向）

**⑱ 矩阵文本未并入前**，本线实现与验收一律按**最严假设**：所有消费方视为 `anchor_required ∧ read_path=source_mirror ∧ strict`。
⇒ 效果：**legacy 段默认对一切消费方 reject**，只认写时登记段。矩阵到位后**只放宽不放宽到不报告**（放宽必须留 `degraded` 记录）。
**理由**：默认放行的错误不可观测；默认拒绝的错误可观测且可修。

## 三、存量段 `legacy_unverified`（R21 第二项并入）

### 3.1 定义

sidecar 上线前**已写入**分钟/日线表的那些段，其**写时因子值从未被登记**。三类：

| 类型 | 状态 | 处置 |
|---|---|---|
| **L1 有写时登记** | 上线后新写入批 | `anchor_origin='write_time'`，**可信集** |
| **L2 回补批登记** | 上线后为缺口补登记 | `anchor_origin='backfill_inferred'`，批次 `state='legacy_unverified'`，**不可信集** |
| **L3 无任何登记** | 上线前存量且未回补 | 缺口清单条目；进 9a 计数器 |

### 3.2 硬规则：回补批**必然**是 `backfill_inferred`，不得声称写时值

回补批的 `factor_asof` 只能取**回补时刻**的因子快照，而写时因子快照**已不可复原**（上游 Tushare 会 retroactive 更新全历史 `adj_factor`——
这正是 `get_tushare_data.py` L7230-7236 注释所述「尺度断层」成因）。
⇒ 回补批若声称 `anchor_origin='write_time'` 即构成**事后反推**，违反 v2 既定硬规则「落库前随行登记、**禁事后反推**」。
⇒ **故 L2 类必须显式标 `backfill_inferred` 且批次 `state='legacy_unverified'`，永久不升级为可信集**（除非发生该段真重写并随行登记）。

### 3.3 对 v2 判据 9 的修订：**覆盖 ≠ 写时锚可信**

v2 判据 9 原写：「active 段并集 ∪ 回补缺口清零 ⇔ 分钟表全键覆盖；三点样本吻合不算覆盖证据」——**覆盖判据本身正确，但容易被误读为「可信」**。v3 拆为**两个独立计数器**：

| 计数器 | 定义 | 判据 |
|---|---|---|
| **9a `coverage`** | 全键覆盖（active 段并集 ∪ 缺口清单清零 ⇔ 分钟表全键） | 必须清零 |
| **9b `writetime_verified`** | 仅计 `anchor_origin='write_time'` 的段所覆盖键量 ÷ 全键量 | **必须分列上报**，不设通过阈值；9b 未达 100% 时**任何 as-of 结论须标覆盖边界** |

**禁止**：以 9a 清零推导 9b；以 9b 低于 100% 为由否决 9a 清零（两者回答问题不同）。

### 3.4 字段增量（v2 的 18 字段 ＋ 2）

| 新字段 | 类型 | 语义 |
|---|---|---|
| `anchor_origin` | TEXT 枚举 `write_time`／`backfill_inferred` | 段准入可信集的唯一开关 |
| `inferred_reason` | TEXT（可空） | `backfill_inferred` 时必填（如 `pre_sidecar_stock`／`gap_repair`） |

批次表 `state` 枚举由 v2 的 `pending／committed／aborted` **扩充**为 `pending／committed／aborted／legacy_unverified`。
**`schema_ver = v3`**；因**尚未入生产库**（schema 闸未过、11-14 仅条件排队），本增列不触发铁律 24 的既有表契约变更，但**入生产库时按六件套一次性带上**（不得二次加列）。

⇒ **登记为配置漂移**，须其维护方更新后再作为路由判据引用；**本线不改他域名配置**。
（本轮所有矩阵结论均**未引用**该 `authority` 字段，仅引用其 `adj_rule`／`adj_policy`／`write_rule`。）

## 八、四项补审（按指示：版本溯源／段替换／实际键集与内容摘要／提交可见性）

### 8.1 版本溯源 —— 发现 v2 的**关键缺口**：`factor_asof` 不可复现

**缺口**：`factor_asof` 记的是因子记录自身的 `trade_date`，但**上游 Tushare 会 retroactive 重写全历史 `adj_factor`**
（`get_tushare_data.py` L7230-7236 注释明载此机理，且它正是「尺度断层」成因）。
⇒ 同一 `(ts_code, factor_asof)` 在不同**观测时刻**可能取到**不同值** ⇒ **只记 asof 无法复现 `a_write`**。

**修订（新增 2 字段）**：

| 字段 | 类型 | 语义 |
|---|---|---|
| `factor_observed_at` | TIMESTAMP | 该 `a_write` 值的**观测时刻**（本批取因子动作发生的时刻），与 `factor_asof` 分列 |
| `factor_probe` | TEXT | **可机检溯源探针**：`sha256(factor_source｜factor_asof｜adj_factor值｜count(*)｜query_sha256[:16])[:16]` |

⇒ `factor_version`（v2 的文本字段）**降级为展示用**，**判据只认 `factor_probe`**（文本不可机检、无法判定「同版本」）。
**验收增补**：构造「同 asof 两值」夹具（模拟 retroactive 改写）⇒ 两批 `factor_probe` 必须不同，且 `factor_observed_at` 递增。

### 8.2 段替换 —— 发现 v2 的**真缺陷**：`seg_id` 缺 `anchor_end`，切分后 id 与区间不再一一对应

**缺陷**：v2 定义 `seg_id = sha256(ts_code|freq|anchor_start|write_batch_id)[:16]`。
部分覆盖切分时，**保留侧**的 `anchor_start` 与 `write_batch_id` **均不变**，但 `anchor_end` **被裁剪**
⇒ **同一个 `seg_id` 先后对应两个不同区间** ⇒ 历史对账、`superseded_by` 解析、重放定位**全部会串**。

**修订**：

1. `seg_lineage_id = sha256(ts_code|freq|write_batch_id|原 anchor_start|原 anchor_end)[:16]`——**批次落库时一次性定死，永不因切分而变**（血统锚）。
2. `seg_id = sha256(seg_lineage_id|anchor_start|anchor_end|seg_version)[:16]`——**版本锚**，切分/重写后必然新值。
3. 切分产生的保留侧与失效侧**共享同一 `seg_lineage_id`**、各持不同 `seg_id`；
   `superseded_by` **只指 `seg_id`**（版本级），血统级关系由 `seg_lineage_id` 直接可查。
4. **链式终止解析**：`superseded_by` 可链式（B 被 C 覆盖）⇒ 消费方解析「当前可见」须**沿链到尾**并做**环检测**（链长上限如 64，超限报错），
   禁止只跟一跳（跟一跳会读到已被再次覆盖的中间态）。
5. `tombstone` 使用规则（v2 只列枚举未给规则）：**仅用于「整段因标的下市/数据下架而清除」**；
   tombstone 段**保留 `a_write` 与 `anchor_*` 作历史**，`seg_state='tombstone'` 且 `superseded_by=NULL`（不指向任何后继）。

### 8.3 实际键集与内容摘要 —— 单摘要不足以证明「实际键集」

**缺口**：v2 批次表只有 `key_lo/key_hi + n_bars + content_sha256`。
区间端点＋行数**不能排除区间内空洞**（停牌半日、分片漏写），即「实际键集」未被证明。

**修订（新增 2 字段）**：

| 字段 | 语义 |
|---|---|
| `key_sha256` | **键序化键串**（仅键列 `ts_code,freq,bar_time`，行间 `\n`）的 sha256——与内容摘要**并列**，独立校验键集 |
| `key_gaps` | 本批区间内**应有 bar 数 − 实际键数**（停牌/半日/无成交的可解释缺口计数；非零须附理由分类） |

**规范化单一事实源（重要）**：`content_sha256` 的规范化串（列序固定、浮点 `round(6)`、NULL 记 `|N|`）
**必须与 §七之五 全量黄金工具（`scripts/golden_fingerprint.py`）共用同一实现**。
否则会出现「sidecar 声称重放逐位一致、黄金工具给出不同摘要」的**双口径分叉**，且两边各自自洽、极难定位。
⇒ 落点：抽出 `qfq_serialize.py`（单一函数），sidecar 与 golden 工具**同时 import**，禁各自复制实现。

### 8.4 提交可见性 —— 必须**表层保证**，不能只靠消费方 join 约定

**缺口**：v2 写「段表只对 `committed` 批可见（**消费方 join 批次表过滤**）」。这是**约定**，不是**保证**：
现存/将来的任意 SQL 直查基表即可读到 `pending` 批的段；且 QuestDB 的可见性以 **commit** 为单位，
若批次行与业务行**分两次 commit**，中间态对读者可见。

**修订**：

1. **视图强制**：建 `qfq_anchor_sidecar_v`（内含 `join batches where state='committed' and seg_state in ('active')`），
   **对外只公开视图**；基表名加受限前缀/文档标注「禁直读」，并在消费方契约中写明「只读视图」。
   判据 13 增一例：**直读基表须被评审拒绝**（代码评审规则，非运行期闸）。
2. **commit 粒度**：`pending` 批次行与业务行**同批 commit**；段行与 `state='committed'` 更新**同批 commit**。
   ⇒ 任一时刻读者只可能看到「业务行无锚」或「业务行有 committed 锚」，**不可能**看到「锚指向未完成批」。
3. **可见性判据（可机检）**：构造两阶段夹具，在 `pending` 提交后、`committed` 提交前读取视图 ⇒ 该批段**必须不可见**；
   `committed` 后 ⇒ 可见且 `seg_state='active'`。此条并入判据 11（部分失败恢复）。

## 十一、因子版本必须实体化（R22 第 2 项）

**审核判定成立**：`factor_probe`（值/行数/查询摘要）只是**摘要**，摘要**不可取回** ⇒ 无法据此重算 `a_write`；
`factor_observed_at` 是**时间**，不是**版本实体**。v3.1 的修订不足以支撑「可复现」。

**修订：引入可取回的快照实体**

| 字段 | 语义 |
|---|---|
| `factor_snapshot_id` | 一次因子抓取的**落盘对象标识**（如 `fs-20261112T2300-a1b2c3`），**可寻址** |
| `factor_snapshot_uri` | 该快照的绝对路径 / 库内表名（**落盘实体**，非摘要） |
| `factor_snapshot_sha256` | 快照文件内容 sha256（判「同版本」的唯一依据） |

**快照内容（决定可复现的最小集合）**——必须含三项，缺一即不可复现：

1. 本批涉及的 `(ts_code, trade_date)` → `adj_factor` 的**全量行**（含未被使用的行，因选择逻辑本身要可重放）；
2. **所选 `latest_adj` 值及其选择路径**（`db LATEST ON` / `tushare_increment 窗口末值` / 当日回退），带行号级来源；
3. 抓取 SQL 原文（不是指纹）+ 抓取时刻 + 上游响应行数。

**复现判据（可机检）**：给定 `factor_snapshot_id` ⇒ 载入快照 ⇒ 按 §十 表第 N 行的**同一函数**重算 ⇒
结果必须**逐位等于**该批 `a_write` 与实际落库价格。**跑通即"版本可取回"；跑不通即该批不可复现，须标 `unreproducible`。**

`factor_probe` 保留但**降为快查索引**（快速判「疑似同版本」），**不得**作为版本判据。
**成本**：快照按批增量（仅涉及码×日），非全表；落点与 sidecar 同库表或同目录 parquet（过 schema 闸时一并定）。

## 十二、expected universe 必须补齐成 bar 规则（R22 第 3 项）

**审核判定成立**：`key_gaps` 的「应有集合」若只按区间端点算，等于**假设区间内每格都应有 bar**，这假设未经证成。
补齐六维（每维须给数据来源，缺来源即该维为 `unknown`）：

| 维 | 规则 | 来源 | 现状 |
|---|---|---|---|

  **完整性**由 `key_completeness` + `expected` 计算式共同承担。两者职责分离，禁互相顶替。

## 十三、跨表可见性：旧锚失效与失败恢复（R22 第 4 项）

**审核判定成立**：两次 commit + 过滤视图仍有 **「新业务行 + 旧 committed 锚」** 窗口——
业务行先落（读者可见新价）而锚仍是上一批的 `committed` 段 ⇒ 读者拿**新价配旧锚**，视图过滤对此**无效**（旧锚状态合法）。

**主案：旧锚先失效（write-ahead invalidation）**

```
① invalidate：将本批将覆盖的 active 段置 seg_state='superseded_pending'
               （与「批次 pending 行」同批 commit；此刻读者已看不到旧锚）
② 业务行落库（新价）
③ 落新段 + 批次转 committed（同批 commit）→ 新锚可见
④ 旧段转 superseded 并回填 superseded_by（与 ③ 同批或紧随其后）
```

⇒ 任一时刻读者状态只有两种：**「旧价 + 已失效锚（读不到）」** 或 **「新价 + 新锚」**；
**不存在**「新价 + 旧锚」。代价：覆盖窗口内该段**暂时无锚**（fail-closed，符合既定取向）。

**备案**：业务行带 `anchor_epoch`，读侧要求 epoch 匹配（需改业务表 schema，成本高，仅当主案不可行时启用）。

**技术限制（承认「文档禁直读 ≠ 技术限制」）**——须给出**实际手段**，按强度排序：

| # | 手段 | 强度 | 备注 |
|---|---|---|---|
| 1 | **权限收口**：基表只授写方，读方仅授视图 | 强（技术强制） | QuestDB 若支持表级权限则首选；不支持则退 2/3 |
| 2 | **单写入口**：所有读经 MCP server / 统一查询层，直连被网络层拒 | 中强 | 依赖部署面，须运维配合 |
| 3 | **同 commit 原子发布**（主案）| 中 | 不阻止直读，但使不一致态**不可观测** |
| 4 | 文档/评审禁直读 | 弱（仅约定） | **不得单独作为保证** |

**失败恢复证明（须补的判据）**：崩溃发生于 ①与③之间 ⇒ 旧段停留 `superseded_pending`、新业务行可能已落部分
⇒ 恢复时**不得直接复活旧锚**：须按内容对账——业务行与目标批一致则续走 ③；不一致则回滚业务行并**把旧段转回 active**
（须记录回滚事件，不得静默）。判据 11 增此向；判据 13 增「`superseded_pending` 不得对任何消费方可见」。

# v3.3 补审（2026-11-13 01:5x · 应 R23 审核五项）

## 十七、锚差异：报告但**不等同**数据损坏（R23-1）

审核采信我方撤回，并加关键限定。判据 12 由「不等即报告」细化为**三级分类判定**：

| 级 | 判据 | 定性 | 处置 |
|---|---|---|---|
| **L-A 版本差** | 两侧 `factor_snapshot_sha256` **不同** | **版本差异，非损坏** | 报告并列两侧 `snapshot_id`；**不计入损坏** |
| **L-B 快照失效** | `snapshot_sha256` 相同但 `observed_at`／值不同 | **快照未真正固化**（同一 snapshot 应给同一值） | 报告为快照机制失效，冻结该 snapshot 复核；计入缺陷 |
| **L-C 真损坏** | snapshot 相同、`observed_at` 无差、同键**仍不等** | **数据损坏** | 进缺陷流程；**唯一计入损坏计数**的级别 |

⇒ 判据 12 报告必须带**级别字段**；「差异数」与「损坏数」**分列两个计数器**，禁合并。

## 十八、锚与快照必须先于 pending 耐久化；**禁补锚**（R23-2）

审核判定成立：「内容对上」≠「写时锚可恢复」。v3.2 顺序（业务行→段→committed）把锚放得太晚。改为**四段顺序**：

```
① 抓因子 → 立即落 factor snapshot 实体 → durable 校验（回读 sha256 一致 + 落盘确认）
② 同批 commit 落 pending 批记录（含 a_write 实际锚 + snapshot_id + 键/内容摘要）
   ← ①② 未完成不得进 ③
③ 写业务行
④ 落段 + 批次转 committed（同批 commit）
```

**硬规则（三条，均 fail-closed）**：

1. **禁补锚**：进入 ④ 时**禁止再取任何因子**；③/④ 阶段发现 `snapshot_id` 缺失或不可回读 ⇒ 该批 **abort**，
   **不得**取「当前因子」回填后提交（即审核点名形态）。
2. **durable 定义**：写入后必须**回读校验**（sha256 与写入值一致 + 落盘/commit 确认）；「调用返回成功」不算 durable。
3. **缺锚即不写**：①②未完成时业务行**零写入**（现实现是「先写业务行、后补登记」，须倒置）。

**判据新增（可机检）**：三夹具——快照落盘失败／快照回读 sha 不符／pending 缺 snapshot_id
⇒ 均须 **abort 且业务行零行写入**（强于现状：现状允许业务行已落）。

## 十九、回滚四要件与恢复闸（R23-3）

write-ahead 失效只解决「新价＋旧锚」窗口；**回滚**另需四要件，缺一不得回滚：

| # | 要件 | 落地要求 |
|---|---|---|
| 1 | **旧业务前像 before-image** | 覆盖前把将改动旧行**全量留存**（独立表/parquet），**全精度原值**，非摘要 |
| 2 | **精确覆盖键** | 明列 `(ts_code,freq,bar_time)` **键集合**（键数＝行数），禁只记区间端点 |
| 3 | **排他／版本保护** | 单写者 lease（键区间互斥）＋`row_version` 递增；并发写同键**拒绝**而非后写覆盖 |
| 4 | **幂等恢复** | 恢复带 `recovery_id`；重复执行结果一致（按 before-image 重放，不追加行） |

**恢复闸（严于 v3.2）**：恢复 `active` 前须**完整复验旧内容**——①行数 ②键集摘要 ③**全精度**内容摘要，
三项与 before-image 登记值**全等**方可恢复。**任一不等或证据缺失 ⇒ 保持不可见**
（停 `superseded_pending`／`tombstone_pending`），报人工，**禁猜恢复**。

**判据新增**：构造「before-image 少 1 行」夹具 ⇒ 恢复**必须被拒**、状态保持不可见、不产出 active 段。

## 二十、摘要精度：低精度规范化**不得**用于证明逐位一致（R23-4）

审核点名成立——v3.2 的 `content_sha256`（round(6)）**不足以证明逐位一致**。拆两列，职责硬分离：

| 列 | 精度 | 允许用途 | 禁止用途 |
|---|---|---|---|
| `content_sha256_full` | **全精度无损**（浮点 `repr`／`format(x,'.17g')`，round-trip 须还原原值） | **唯一可用于「逐位一致」证明** | — |
| `content_sha256_r6` | round(6) | 跨源对拍、人读定位、差异初筛 | **不得进一致性判据**（含黄金对比、重放一致性、恢复闸） |

同理 §七之五 黄金工具规范化**必须改用全精度**串；`round(6)` 仅保留在「对拍报告」层。

**expected 与完整性同步加严**：
- 任一维 `unknown` ⇒ `key_completeness` **上限 `bounded_by_unknown_rule`**；
  并**判据化**一句：**`key_gaps = 0` 不得作为 `proven` 依据**——它只说明「按区间应有集合」无缺，而**应有集合本身未证成**。
- `proven` 需三条独立证据同立：① expected 计算式输出可复现 ② `key_sha256` 同批重放一致 ③ gap 分解为零且**每维来源可指**。

# v3.4 补审（2026-11-13 02:2x · 应 R24 审核五项）

> **总纲（审核原话）**：「仍是规格，不是已验证机制。」本件据此**降级一切未验证表述**：
> 本章只写契约、判据与前置门，**不含任何「已具备」主张**。

## 二十三、差异判定：分类是**复现测试**的结论，不是 SHA 比较的快判（R24-1）

**承认实质错误**：v3.3 用「两侧 snapshot SHA 不同 ⇒ 仅版本差、非损坏」作**互斥快判**。
审核指出两者**可能共存**——成立：版本不同时，某一侧自身也可能已损坏，SHA 不同**掩盖**而非**排除**损坏。

**改为两命题独立验证**：

- **P1（版本差）**：两侧 `snapshot_sha256` 不同，且**各自实体可回读**。
- **P2（该侧损坏）**：某一侧**无法用其自称的 snapshot 复现自身值**（重放结果 ≠ 登记值）。

| P1 | P2 | 定性 | 处置 |
|---|---|---|---|
| 否（同 snapshot） | 否（两侧均可复现） | **不可解释**：同一实体给两值 | 判 **L-B 快照失效**（非 L-C），冻结该 snapshot |
| 否 | **是** | **L-C 损坏** | 进缺陷流程 |
| **是** | 否 | **纯版本差** | 报告，**不计损坏** |
| **是** | **是** | **版本差与损坏共存** | **两类同时记录**，禁合并为「仅版本差」 |

**必备证据（缺一即分类未证）**：两侧 `snapshot_id`／`uri`／`sha256`；**实际采用的因子值**；
**选择路径**（`db LATEST ON`／`tushare 增量窗口末值`／当日回退）；**重放命令与输出 sha**；`observed_at`。

**硬规则**：任一证据缺失 ⇒ 标 `classification_incomplete`，**不得**归入任何单一级别，**不得宣称分类完备**。
判据 12 输出改为 **`(P1,P2)` 二值对 + 证据完整性**，**不是**单枚举。

## 二十四、位级规范化契约（R24-2）

**承认**：`repr`／`.17g` round-trip **不自动等** IEEE 逐位一致（不同格式化路径可给不同串、`-0.0`/NaN payload 等语义分叉）。改为**位级编码，不用文本 repr 作一致性判据**：

**每行 = 按固定列序的定长字段序列 → 拼接字节 → sha256**。浮点 `struct.pack('<d', x)`（8B，或其物理 dtype `<f` 4B），整数 `<q`/`<i`，时间 `int64 epoch_ms UTC`。

| 项 | 规范化契约 |
|---|---|
| **SQL NULL** | 类型 tag 字节 + `\x00` 哨兵；与字符串 `"None"`／`"nan"`／`""` **严格区分** |
| **float NaN** | IEEE quiet NaN **位模式原样保留**（不归一化 payload）；与 NULL **分开编码** |
| **±Inf** | 位模式原样保留 |
| **负零** | **保留符号位**（`-0.0` ≠ `+0.0` 按位），**不归一化** |
| **dtype** | 列 dtype 白名单（float64／int64／str）；运行期不符 ⇒ **报错**，禁静默转换 |
| **列序** | 按 schema 契约固定列序；**禁**按名排序或按出现序 |
| **时间单位** | 统一 `epoch_ms UTC` int64（实测依据：`aligner.py:943` `pd.to_datetime(..., unit="ms")`；分钟表 time 为 ms） |
| 文本字段 | UTF-8 + 长度前缀，避免分隔符歧义 |

两摘要并存：`content_sha256_full`（上述**位级**，唯一一致性判据）／`content_sha256_r6`（人读对拍）。

## 二十五、五段顺序：旧锚失效**不得在修订中丢失**（R24-3）

**承认真遗漏**：v3.3 的四段顺序（快照→pending→业务行→committed）**把旧锚失效步骤弄丢了**——这是修订过程中的回归，非表述问题。恢复为**五段**：

```
① 抓因子 → 落 snapshot 实体 → durable（须达 L3，见 §二十六）
② 同批 commit 落 pending 批（实际锚 a_write + snapshot_id + 位级摘要）
③ 旧锚失效：将本批将覆盖的 active 段置 seg_state='superseded_pending'
   （与 ② 同批 commit —— 此刻起旧锚对消费方不可见）
④ 写业务行
⑤ 落新段 + 批次转 committed + 旧段转 superseded 回填 superseded_by（同批 commit）
```

**不变式（可机检）**：任一时刻**不存在**「可见的 active 锚 + 已被本批改动而未提交的业务行」。
**判据**：在 ②后／③后／④后 三个时刻抽样读**消费视图** ⇒ 三次均应为「该键区间无可见锚」；仅 ⑤ 后新锚可见。

## 二十六、durable 三层：回读 SHA 不证明存储耐久（R24-4）

| 层 | 证据 | 证明力 |
|---|---|---|
| **L1** | 写入调用返回成功 | 弱，**不算 durable** |
| **L2** | 回读 sha 一致 | 中——仅证明**可读**，**不证明已落持久介质** |
| **L3** | 平台级持久性证据：`fsync`/`fdatasync` 返回、WAL commit 落盘确认、**崩溃/掉电后回读仍一致** | **唯一算 durable** |

⇒ 本规格 `durable` **只认 L3**；L1/L2 为必要条件而非充分条件。
**平台能力待证（不假设）**：① QuestDB WAL commit 的持久性语义与**可观测确认点**；② 本机（Windows）`fsync` 语义与 Python 可达性。
（弱证据仅可标注：进程被强杀后回读一致——**不等于**掉电耐久。）⇒ **D-20**。
