## 一、这次要做什么

QuantStudio 的数据库组件（duckdb）从 **1.4.5 升级到 1.5.6**。
项目对 duckdb 设有**启动闸门**：版本不在放行集合内时程序会**拒绝启动**并打印修复指引——这是**预期保护行为，不是故障**。

### 1.1 先明确一件事：什么组合会被拒启（本版更正）

> **上一版写法有误**（原文「只升依赖不升代码、或只升代码不升依赖都会拒启」），本版更正如下。

| 代码版本 | duckdb 依赖 | 结果 | 说明 |
|---|---|---|---|
| **旧代码**（本次升级前） | **1.5.6** | **❌ 拒绝启动（退出码 3）** | 旧门只认 `1.4.x`（举证见 §二·附） |
| 旧代码 | 1.4.5 | ✅ 正常 | 维持现状 |
| **新代码**（本次升级后） | **1.5.6** | ✅ 正常 | 本次目标状态 |
| **新代码** | **1.4.5** | ✅ **正常（允许）** | **新门放行集合同时包含 1.4.x 与 1.5.6** |

⇒ **唯一的强制顺序**：**要升依赖到 1.5.6，必须先（或同批）把代码升到新版**；
反过来「只升代码、依赖先留在 1.4.5」是**允许**的，程序可正常运行，不构成拒启。

## 二、允许的版本集合（门禁判定源）

| 版本 | 是否允许 |
|---|---|
| 1.4.5 ～ 1.4.x（`1.4.5 ≤ x < 1.5`） | ✅ 允许（维持现状亦可） |
| **1.5.6** | ✅ 允许（本次目标版本） |
| 1.5.0 ～ 1.5.5 | ❌ 不允许 |
| 2.0.x 及以上 | ❌ 不允许（本次不含首跳以外的跨大版本） |

判定源：`quantstudio/pipeline/duckdb_version_policy.py`（门禁 / 双平台巡检脚本 / 测试契约三面同源）。

> **关于上游缺陷 `duckdb#23645`（本版限定表述）**：
> 1.5.x 存在该上游缺陷（索引删除在特定条件下触发致命错误），**在 1.5.6 仍未修复**，只是不再静默出错。
> 本项目**在已执行的核验范围内**未观察到暴露（详见 §六·2 的限定说明）；据此把 1.5.6 纳入放行集合。
> **该结论不代表所有路径、所有数据分布下均无暴露面**——若您遇到 §七 第 4 行的日志文本，请立即反馈。

### §二·附：旧代码是否接受 1.5.6（单独举证）

| 项 | 内容 |
|---|---|
| 断言 | **旧代码不接受 1.5.6，会 `SystemExit(3)` 拒启** |
| 取证命令 | `git show fdca384^:quantstudio/pipeline/duckdb_version_gate.py` |
| 取证读数 | 该版本常量 `REQUIRED_SERIES = "1.4"`，校验语义为「必须 `1.4.x`」；错误文案即「不在钉版区间（需 1.4.x，pyproject: duckdb>=1.4.5,<1.5）」 |
| 结论 | 旧门的放行面仅 `1.4.x` ⇒ **1.5.6 必被拒**；新门（`fdca384` 起，判定源下沉单文件）才把 `1.5.6` 纳入 |
| 复现 | `git show fdca384^:quantstudio/pipeline/duckdb_version_gate.py \| Select-String 'REQUIRED_SERIES'` |

## 三、升级步骤（建议在非交易时段执行）

1. **停止采集进程**：关闭 GUI，并停止 daemon（Windows 计划任务名：`QS_DaemonForever`）。
2. **升级代码**：拉取最新版 QuantStudio 代码（`git pull`）。
3. **再升级依赖**（顺序不可颠倒——见 §1.1）：

   ```bash
   pip install "duckdb==1.5.6"
   ```

   > 请**使用显式版本命令**；不要用 `pip install -U duckdb`（会装到未纳入放行集合的最新版本）。

4. **自检**（一条命令，输出即结论）：

   ```bash
   python -m quantstudio.pipeline.duckdb_version_gate --check
   ```

5. **恢复采集**：重新启动 daemon（Windows：`schtasks /Run /TN QS_DaemonForever`）。

## 四、自检输出怎么读

| 输出 | 含义 | 您需要做什么 |
|---|---|---|
| `PASS 1.5.6`（退出码 0） | 版本在放行集合内 | 无需操作，可恢复采集 |
| `PASS 1.4.5`（退出码 0） | 仍在 1.4.x，**同样在放行集合内** | 可正常运行；如要升级请按第三节执行 |
| `FAIL <版本>`（退出码 1） | 版本**不在放行集合** | 升到 1.5.6（§三第 3 步），或按 §五 留在 1.4.5 |
| `ERROR …`（退出码 2） | 依赖缺失或版本串不可读 | 报运维，附**输出原文** |

若程序启动时提示「拒绝启动」并打印 duckdb 版本与修复指引（退出码 3），按提示执行即可。

## 五、如果您希望继续留在 1.4.x

```bash
pip install "duckdb==1.4.5"
```

**新版代码允许 1.4.5**（见 §1.1 第 4 行），因此「先升代码、暂不升依赖」是可行路径。
降级同样需要**先停采集**；降级后请再跑一次第四节的自检确认 `PASS 1.4.5`。
> 注意：**1.4.x 线的上游支持于 2026-11-17 结束**，长期留在该线将不再获得上游修复。

## 六、性能提示（**限定到实测环境与实测路径**，本版重写）

### 6.1 实测条件（缺一不可外推）

| 项 | 实测条件 |
|---|---|
| 机器 | **本机单台物理机**（同一磁盘，两侧不同 venv） |
| OS / 解释器 | Windows；**Python 3.11.9**（1.4.5 侧与 1.5.6 侧同为 3.11.9） |
| duckdb | 1.4.5 vs 1.5.6（仅此一项不同） |
| 数据库 | **合成库**（非生产库；建表 DDL、语句、PK 结构逐字复刻真实路径） |
| 表与语句 | 表 `index_constituents_snapshot_meta`（10 列，`PRIMARY KEY(index_code, time)`）；语句 `executemany("INSERT … ON CONFLICT (index_code,time) DO UPDATE SET …")`（9 个 SET 列） |
| 取样 | 每档 **3 次取中位**，各档独立新库、独立子进程；单档 >90s 记超时并终止 |

### 6.2 读数（中位）

| 单批行数 | 1.4.5 | 1.5.6 | 倍数 |
|---|---|---|---|
| 300 行 | 0.642 s | **3.943 s** | **6.14×** |
| 1000 行 | 3.314 s | **13.396 s** | **4.04×** |
| 5000 行 | 15.436 s | **≥90 s（超时，未测到完成）** | **≥5.83×** |

- 两版 `row_count` 与主键校验均正确（`row_count` = 输入行数、`PK = 1`）⇒ **只有耗时差异，写入结果无差异**。
- 1.4.5 首档首次 3.499s → 0.619s（预热明显）；1.5.6 首次 2.677s 未被预热放大 ⇒ **差距非预热造成**。
- 「5000 行 >90 秒」是**超时上限下的下界**，**真实完成时间未知**（未继续等待）。

### 6.3 影响面与建议

**仅影响上述 `executemany` 写入形态下的该辅助表刷新时延**，不影响数据正确性。
**本实测未覆盖**：其它表、其它写入形态（如 `INSERT … SELECT`）、生产数据分布、其它 OS/解释器组合。
若您的采集批次达到千行量级，建议放宽该任务调度超时，或观察首日采集耗时，必要时拆分批次。

## 七、常见问题

| 现象 | 原因 | 处理 |
|---|---|---|
| 启动报「duckdb 不在放行集合」 | 依赖已升到 1.5.x 但**代码仍是旧版**（旧门只认 1.4.x） | 停采集 → `git pull` 升级代码 → 重新自检 |
| 自检命令报「无法导入 duckdb」 | 解释器选错 | 用**项目实际使用的那个解释器**执行自检（如 `C:\...\Python311\python.exe` 或项目 venv 的 python） |
| 升级后某个表刷新变慢 | 见 §六（仅 `executemany` 形态实测） | 调超时或拆批次；如影响主流程，请反馈 |
| 采集正常但日志出现 `Failed to delete all rows from index` | 命中 1.5.x 上游缺陷（`duckdb#23645`） | **立即反馈并附日志片段**；必要时按 §五 降级 |

## 八、需要您反馈的情况

- 自检命令输出与第四节表格**不一致**；
- 升级后采集报错、重复写入，或出现第七节第四行的日志文本；
- 您的部署环境使用了**我们未覆盖的 duckdb 版本、解释器或 OS 组合**（请附 `python -c "import duckdb;print(duckdb.__version__)"` 输出）。

请在反馈中附上：自检命令的完整输出、Python 与 duckdb 版本、以及报错日志片段。
