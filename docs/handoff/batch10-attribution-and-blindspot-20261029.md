## 三、判据盲区机制化方案

### 3.1 盲区定义

我方 #9 采用的「逐笔 ⊆ 已批池」判据，**只防「推未批内容」**（把不该推的笔混进本批），**不防「内容绕过批次被推」**（他线直接 `git push` 把内容推到远程，不经任何统推批）。
本次 #9 实态即为此例：`origin/main` 已在他线自行推进 7 笔，我方清点只剩 6 笔——**若非我恰好在清点时发现 `origin/main ≠ 76e9e50`，这 7 笔的绕过行为不会被任何判据捕获**。

### 3.2 机制化判据（写进统推执行卡第 0 步）

```
统推第 0 步（每轮必做，先于四查）：
  1. git fetch origin
  2. 读上批留痕锚：从 docs/handoff/push-bundle-rulings.log 取最近一条 commit=<SHA>
  3. 比对：git rev-parse origin/main  vs  上批锚
     · 相等   ⇒ 正常，继续（预期推进量 = 0）
     · 不等   ⇒ 🔴 非预期推进
         a) 列 git log <上批锚>..origin/main --format="%h %s" 逐笔取证
         b) 判定每笔是否在「已批池」内
         c) 无论是否在池内 —— **停推，上报归因**（不经我方批即达远程，属程序事件）
         d) 获总调度裁定后方可继续本批
```

### 3.3 两档落地方式

| 档 | 方式 | 优点 | 缺点 | 建议 |
| --- | --- | --- | --- | --- |
| **A（推荐）** | **执行卡固化＋独立巡检脚本** `scripts/check_remote_advance.py` | 不拖慢推送；可随时手跑/定时跑；不误拦他线正常提交 | 依赖执行方遵守 | ✅ 采 A |
| B | `pre-push` 钩子内 `ls-remote` 对比基线文件，不一致 exit 9 | 强约束、无法绕过 | 每次推送多一次网络往返；**多线并发时他线正常提交也会触发误拦**；基线需维护 | ❌ 不采（误拦成本 > 收益） |

### 3.4 候选脚本接口（A 档，待批后实现）

```python
# scripts/check_remote_advance.py
# 用途：统推第 0 步机检——远程是否发生「非预期推进」
# 用法：python scripts/check_remote_advance.py [--expect <SHA>] [--json]
#   --expect 缺省时自动从上批留痕 push-bundle-rulings.log 取最近 commit=<SHA>
# 退出码：0=一致（正常）  2=非预期推进（须停报）  3=无法判定（fetch/ls-remote 失败，fail-closed）
# 输出：一致时打印 expect==actual；非预期时逐笔列 <expect>..origin/main 的 commit（含 subject/author/时间）
```

> **判据三形态对齐**：①输入形态门——先验 `origin/main` 与上批锚都是 40 位 SHA，非 SHA ⇒ 报「无法判定」不报「不一致」；②单值比对——不做区间/前缀模糊比较；③判定失败分报——ls-remote 失败报 exit 3，不与「非预期推进」混一。
