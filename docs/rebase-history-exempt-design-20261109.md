> v1 标题：rebase「历史缺行豁免区间」判据扩展方案（同日起草，假设已被实测证伪，保留于文末附A）

## 零、重大修订说明（为何 v1 必须废弃）

**v1 的核心假设是**：「窗口外死信多为『上市日之前的伪缺口』，可用『早于上市日豁免』解掉」。

**实测（2026-11-09 23:35，`q2q3_probe_v2.py`）将其彻底证伪：**

| 资产 | 死信总数 | 早于上市日（可豁免） | 晚于上市日 | 无 list_date |
|---|---|---|---|---|
| STOCK | 16,044 | **0（0.0%）** | **16,044（100%）** | 0 |
| ETF | 2,081 | **0（0.0%）** | **2,081（100%）** | 0 |

**⇒ 「上市日之前」的样本一条都没有。豁免路径无效。**

**⇒ 但同一次探测发现了真正的原因：这些缺口在 QuestDB 侧有完整数据。**

```
抽查 8 个 STOCK 死信：
  002223 2026-09-01  QuestDB=241 行  错=缺 2 行    → ✅ 源有数据
  000423 2026-08-31  QuestDB=241 行  错=缺 32 行   → ✅ 源有数据
  002462 2026-08-28  QuestDB=241 行  错=缺 964 行  → ✅ 源有数据
  002521 2026-08-28  QuestDB=241 行  错=缺 964 行  → ✅ 源有数据
  小结：可补 8 / 无源 0
ETF 抽查 5 个（2025-12-31）：3 个 QuestDB 有 241 行（可补），2 个无源
库内该日：513820 @ 2025-12-31 = 0 行（真缺）
```

**⇒ 结论：不是判据误伤，是「库内真缺、但源端有」⇒ 正确解法是**回填**，不是**豁免**。**

## 一、问题定义（修订后）

### 1.1 现象

```
11:49:24 [qfq_orch] B 观察期：factor_equivalent=0  blocked=60  units=4164  放行率=0.0%
11:49:26 [DaemonLifecycle] status=finalized_held  held=4（水位按 hold_until_consistent 保持）
```

60 个 QFQ 单元全 blocked，四表水位 gap：21 / 28 / 64 / 63 天。

### 1.2 缺口规模（实测量化）

| 资产 | 死信行数 | 去重 (code+日期) | code 数 | **不同日期数** |
|---|---|---|---|---|
| STOCK | 16,044 | **14,125** | 891 | **3,608** |
| ETF | 2,081 | 2,081 | 13 | **243** |

### 1.3 错误族（决定分类处理）

| 错误族 | 样本量 | 处理路径 |
|---|---|---|
| `rebase 日线覆盖不全：缺 N/多 0 行` | 7,509（缺32:5,527 + 缺1:1,982） | **日线回填** |
| `rebase 分钟 覆盖不全：缺 N/多 11 行` | 3,355（缺964:1,807 + 缺482:1,548） | **分钟回填** |
| `raw OHLC 与库内不一致（\|Δ\|>1e-9）` | 1,207+ | **不在本方案范围**（裁②：不扩 factor_equivalent） |

**⇒ 关键：错误分「日线缺」与「分钟缺」两类，回填目标不同（`stock_daily` vs `stock_minutes`）。**

## 二、技术可行性（已实测验证）

### 2.1 QuestDB 支持定向查询（关键前提）

**实测 SQL（本日验证通过）：**
```sql
SELECT count() FROM stock_minutes
WHERE ts_code = '002223.SZ'
  AND trade_time >= '2026-09-01'
  AND trade_time < dateadd('d', 1, '2026-09-01')
```
**⇒ 返回 241（完整一天）⇒ 可按 (code, 日期) 精确定向取数，无需拉全市场。**

### 2.2 成本对比（决定方案形态）

| 方案 | 批次数 | 每批耗时 | 总耗时 | 评价 |
|---|---|---|---|---|
| **按日全市场回填** | 3,608 | ~8 分钟（11-06 实测 496s） | **≈ 480 小时（20 天）** | ❌ 不可行 |
| **按 (code,日期) 定向** | 14,125 | ~2 秒（单 code 单日 241 行） | **≈ 7.8 小时** | ⚠ 勉强可行 |
| **按日批量定向**（推荐） | 3,608 | ~3-5 秒（一天的多个 code 一次查） | **≈ 3-5 小时** | ✅ 可行 |

**⇒ 推荐「按日批量定向」：对每个死信日期，把当天所有死信 code 合成一次 `ts_code IN (...)` 查询。**

## 三、改动范围（不碰判据，只补数据）

### 3.1 本方案不改 `qfq_reanchor_engine` 的任何判据

**⇒ 与 v1 的本质区别：v1 想放宽判据，v2 是补数据让判据自然通过。**

**⇒ 这是**纯数据修正型**（铁律 18 分类），不是判据扩展。fail-closed 语义完全保留。**

### 3.2 新增工具（1 个脚本）

| # | 产物 | 作用 |
|---|---|---|
| 1 | `scripts/backfill_qfq_gaps.py` | 读 `qfq_trigger_queue` 的 dead_letter，按日期分组，从 QuestDB 定向取数，写 `stock_minutes`/`stock_daily`/`etf_*` |
| 2 | `tests/test_backfill_qfq_gaps.py` | 单测：日期分组、SQL 构造、去重、幂等 |
| 3 | `docs/evidence/qfq-gap-backfill-<date>.json` | 每次运行的证据（补了哪些、补了多少、失败哪些） |

### 3.3 关键设计约束

| # | 约束 | 理由 |
|---|---|---|
| **C1** | **必须复用已修的时区处理**（剥 `Z` + `tz_localize('Asia/Shanghai')`） | 昨夜刚修完的 8 小时 bug，绝不能重犯 |
| **C2** | **写前先 DELETE 该 (code, 日期) 旧数据**（或幂等 UPSERT） | 昨夜教训：纯 INSERT 会重复 |
| **C3** | **按日期分批 + 每 N 批 CHECKPOINT** | 防 ART 索引膨胀（铁律 23 第四形态） |
| **C4** | **单线程 + `preserve_insertion_order=false`** | 唯一验证可行的导入路径（昨夜实证） |
| **C5** | **补完必须验证**：full-scan = GROUP BY 计数一致 | 防索引损坏静默 |
| **C6** | **`data_source` 统一填 `questdb`**（与既有回填一致） | 口径一致 |

## 四、影响面评估（铁律 18 纯增益三问）

| 问 | 答 |
|---|---|
| **影响其他功能？** | 否。只往 `stock_minutes`/`stock_daily`/`etf_*` 补缺失行，不改 schema、不改判据、不改其他表 |
| **影响回测性能？** | 补数据后表变大（+约 4.1 万行/STOCK 日线 + 约 340 万行分钟？需实测），但这是**恢复应有数据**，不是引入额外负担 |
| **影响回测精度？** | **提升**。补的是缺失的 K 线，复权计算才有完整输入。属「准确度只升不降」 |

**⇒ 定性：铁律 18 的**「数据修正型」**——diff 只能归因于补入的行集；出现任何其他 diff 即验收失败回退。**
