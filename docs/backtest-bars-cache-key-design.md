# 回测 bars 缓存键改造方案（六步①，2026-09-26）

- 性质：**纯性能型**（可观察结果不变），落点 `quantstudio/backtest/providers/duckdb_data_access.py`（框架层）
- 立项动因：断板反包策略 **19.3 s/日**，实测 **SQL 仅占 6%、Python 占 94%**
- 快照 / 回退：改动限单文件内缓存键逻辑，**单 commit revert** 即可

## 一、背景与动机（全部实测）

### 1.1 瓶颈定位
| 口径 | 实测 | 占比 |
|---|---|---|
| wall（5 交易日） | 96.5s ⇒ 19.3 s/日 | — |
| SQL（≥20ms，27 次） | 5.4s | **6%** |
| Python + 其他 | 91.1s | **94%** |

cProfile（3 日 124.4s）：**8,100 万次函数调用**；`isinstance` 1,610 万次；`duckdb_data_access.py:75(<dictcomp>)` 4,003 次（3.0s）；pandas `Series.__init__` 10 万 / `Index.__new__` 8.4 万 / `sanitize_array` 19 万。

### 1.2 调用链取证（1:1 证实）
```
query_bars_by_count_batch 共 4,003 次（3 日）⇒ 单码 4,002 / 多码 1
_build_trade_date_map 调用 4,003 次（1,334 次/日）⇒ 与单码调用 1:1 对应
传入 code 总数仅 5,002（1,667/日）⇒ 大量「同批 code 被逐个单独调用」
_use_sql_path = True 的调用数 = 0 ⇒ M1 单码聚合未被旁路
```
⇒ **每个交易日对池内每只 code 单独取数一次，每次重建一次日期映射**。

### 1.3 族键诊断（M1 聚合结构性失效之因）
单码调用族键仅 5 种组合，主力为：
```
×1000  count=5   before_ms=当日  use_qfq=True
×1000  count=27  before_ms=当日  use_qfq=True
```
⇒ **同日内 count=5 与 count=27 交替调用** ⇒ M1 族键 `(before_ms, count, use_qfq)` 每次切换即整体重置 ⇒ `_agg_single_seen` 永远达不到阈值 50 ⇒ **批量永不触发** ⇒ 逐码执行、逐次重建映射。
⇒ **选项②（提高聚合阈值）判定无效**（问题在族键交替，非阈值）；多码族键 `(count=1, 当日)` 与单码族键**无交集** ⇒ **选项①需扩键**（由 count 维度改为时间窗维度）。

## 二、范围与边界

**改**：bars 缓存键维度 —— 由「按 `(before_ms, count, use_qfq)` 分族 + 逐码」改为
**按 `(code, before_ms, use_qfq)` 缓存足量窗口 + `count` 内存切片**（先例：`_ensure_bars_in_cache` 的「time<=before_ms + tail(count) 惰性按需加载」）。

**不改**：公共 API 签名/返回字段/列序/dtype/**index 契约**；日期边界与 PIT 语义；复权口径；分钟路径；**策略源码零改动**（评审③选项已排除——框架层先行）。

### 3.1 T1 预证实录（本轮完成）
- **首次预证 = FAIL**（799 项不一致）⇒ 按纪律**禁止改框架、退回方案修订**；
- **差异定性（单例诊断）**：唯一实差为 **index**（逐次 SQL 为 0-based，宽窗切片保留 `[55,56,57…]`）；值层面 `turn/peTTM/pbMRQ` 的"差异"为 **NaN≠NaN 假差异**（预证实现缺陷，非真实差异）；
- **方案修订**：切片后 **`reset_index(drop=True)`** 对齐 index 契约；
- **修订版预证 = PASS**：400 codes × {count=5, 27} ⇒ **12,799 行比对，不一致项 0**（列序/dtype/值/行数全等）。
