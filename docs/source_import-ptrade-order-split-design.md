## 1. 问题定义

### 1.1 现象（真实平台证据）

- 2026-08-19 测试456：反转月建仓 5/5 提交，创业板 300029.XSHE 笔数超限被撤
  （`市价单下单超过交易所规定最高50000股限制，取消下单`）→ positions=4、现金留存 ~20%；
- 2026-08-22 测试908 探针二跑钉死分板上限：

| 板块 | 实测上限（市价单） | 证据 |
|---|---|---|
| 创业板（300xxx） | **50,000 股** | 51,000 拒 / 50,000 未触发（资金不足路径） |
| 科创板（688xxx） | **50,000 股** | 51,000 拒 / 50,000 未触发 |
| 沪深主板 | **≥ 86,900 股**（精确上限未知） | 000004 5.4万 / 002808 8.69万 / 002898 5.71万全部成交 |

- 触发人口：反转/小市值类策略选中低价股（<0.5 元）时，20,000 元/格 × 低价 → 单笔 8~13 万股 → 超限整单取消。

### 1.2 根因

真实 PTrade 平台对市价单实施**分板单笔申报上限**（创业板/科创板 50,000，主板更高），超限**整单取消**（无订单号、无部分成交）；本地 QuantStudio 引擎未建模该约束，双端行为分叉（本地 5 仓 vs PTrade 4 仓、双端订单序列不一致）。

### 1.3 为什么选择「转换管线注入拆单」而非「引擎建模」或「策略手写」

| 路线 | 问题 |
|---|---|
| B 引擎建模 | ① 需精确复刻平台分板阈值（主板精确上限仍未探明）；② 引擎改动 → 触发规则的策略黄金基线全部漂移、需快照/基线重验；③ 平台阈值随版本漂移、维护成本高；④ 复用「整单取消」语义会放大回测亏损（真实实盘可拆单） |
| 策略手写拆单 | ① 平台差异知识泄漏进策略层；② 每策略重复实现、写法漂移；③ 易做成"仅 PTrade 拆"导致双端订单序列不一致 |
| **A' 转换管线注入** | 本方案：转换器注入通用拆单 helper，**策略零改动**；本地注入同一语义 → **双端订单序列一致**；引擎不动 → 基线不漂移 |

## 2. 改动范围（最小增量，先例= trade_date 门控扩展）

### 2.1 转换输出侧：`_QS_ORDER_SPLIT_EXT`（source_import 注入模板，新）

仿照 `_QS_HISTORY_TRADE_DATE_EXT`（2026-08-19 已实施）门控模式：

- **注入条件**：策略源码调用任一订单 API（`order_target_value` / `order_target_percent` / `order_value` / `order_percent` / `order`）时注入；
- **注入内容**：`_qs_split_order(security, value_or_amount, ...)` helper + 对订单 API 的包装（在 wrapper 层统一收口，不改写策略内的调用语句——策略代码零改动）；
- **拆分逻辑**：
  - helper 内先取现价 `px`（复用 `g.last_close`→`get_history(count=1)` 三源取值链，见 vol_regime `_current_raw_price` 同款）；
  - 估算股数 `n_shares = value / px`；若 `n_shares > _QS_MAX_ORDER_SHARES`（**默认 49,000**，常量可配置），
    拆为 `ceil(n_shares / 49,000)` 笔，每笔 `order_target_value(security, value / 笔数)`（或直接 `order(amount=段股数)`，实施时二选一，以平台实测的最小成交粒度为准）；
  - 边界：段内金额 < 1 手价（100 股 × px）时按平台"资金不足降量"语义自然收口（不额外处理）；`px<=0` 时回退下单不拆（与现行为一致）。
- **门控纯增益**：不使用订单 API 的策略（只读策略）注入前后逐字节不变；使用订单 API 的策略输出仅新增 helper 块，主体代码零变化。

### 2.2 本地侧：ptrade_api 注入等价 helper（同语义）

本地引擎注入与 PTrade 输出**逐字同构**的拆分函数与常量（`_QS_MAX_ORDER_SHARES` 同一常量），
使本地与 PTrade 的**订单序列逐笔一致**（拆单数、顺序、段金额全同）→ 双端对齐审计（QS_REBALANCE_AUDIT/QS_FILL_AUDIT 逐日配对）不受影响。

### 2.3 明确不纳入

- 回测引擎撮合/cash/费用评估：**不动**（黄金基线零漂移的直接保证）；
- 平台"资金不足三态"（D4-S4）：不建模（策略预算预筛已在源头规避；需求方确认可接受）；
- 主板上限精确值：不需要（49,000 阈值全板安全）。

## 3. 影响面

| 对象 | 影响 |
|---|---|
| source_import 转换输出 | 使用订单 API 的策略新增 helper 块（纯增量）；只读策略逐字节不变 |
| 本地注入 API（ptrade_api） | 新增等价 helper，策略源码零改动 |
| 回测引擎 | 零改动 |
| 存量已转换策略 | 重新转换即获得能力；不重转则保持现状（无回归） |
| 策略源码 | 零改动 |
| README/docs | strategy_toolbox.md 订单 API 章节补充一句"自动拆单"说明（实施时同步） |

风险点：拆单引入的**费用按笔影响**（若平台/本地佣金有"最低 X 元/笔"，拆 N 笔多计 (N-1) 笔最低佣金）——实施前必须实证双方费用模型（本地 `DEFAULT_TRADE_COST` 语义 vs PTrade 回测费用）；若存在最低佣金，需评估是否保留拆单或改用限价单/其他口径，作为审计决策点。

## 4. 验收标准

1. **单元测试**：注入门控（订单 API→注入 / 无订单 API→不注入）；拆分算法边界（恰超阈值 49,001 / 恰等于 49,000 / 倍数额 / px=0 / value 不足一手）；结构化断言 helper 输出段数与段金额；
2. **转换 round-trip**：`vol_regime_mom_rev` 重转 → 含 helper 块、策略主体零 diff、`py_compile` 通过；
3. **双端订单序列一致性**（关键）：本地回测与 PTrade 转换产物在**同一模拟输入**下，拆单段数、顺序、每段目标值**完全一致**（单元级与 run-level 各验一次）；
4. **费用实证**：确认两端费用模型对"拆单"无额外最低佣金差异（见 §3 风险点），或有审计确认的处理；
5. **回归**：`tests/test_source_import.py` + `tests/test_ptrade_contract_compliance.py` 全绿（存量用例零回归，新增用例覆盖拆单）；
6. **真平台冒烟**：用户重跑 vol_regime 测试456 → 预期 `buy_submitted=5` 全部成交（300029 拆分后 4.9 万×~3 笔），`positions=5`，现金留存 ~0；双端净值差异按既有类别归因（D3 数据差 + D4-S4 三态），零新增不可解释项。

## 5. 回退条件

- 任一验收项失败：
  - source_import 改动：撤销 `_QS_ORDER_SPLIT_EXT` 注入块（门控保证存量不重转策略输出不变，回退面最小）；
  - 本地注入 helper：同步删除即可，策略源码无指纹残留；
- 基准回退点：实施前 `git stash create -u -m "baseline-order-split-<ts>"` 并记录 hash。
