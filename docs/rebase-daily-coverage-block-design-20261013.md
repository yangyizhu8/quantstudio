## §1 问题定义（已定位到代码级）

**现象**（重启后首周期实测·审计表 249 行）：`blocked 220` / `skipped 27` / `committed 2`，
其中 **219/220 共享同一原因**：`rebase 日线覆盖不全：缺 2/多 0 行（要求全历史严格一致）`；另 1 例为分钟形态
（`000668 rebase 分钟 raw OHLC 与库内不一致 |Δ|>1e-09`）。

**机制**（`qfq_reanchor_engine.py:786-808` `_check_daily_coverage_strict`）：

```
target_count = COUNT(*) FROM stock_daily WHERE code=?        # 库内全历史
staged_count = COUNT(*) FROM <fresh df view>                 # 云端 fresh 行
matched      = stock_daily ⋈ fresh ON (code,time)
missing_target = target_count - matched    # **库里有、fresh 没有 ⇒ 「缺」**
extra          = staged_count - matched    # fresh 有、库里没有 ⇒ 「多」
若 missing/extra ≠ 0 ⇒ ReanchorBlocked
```

⇒ **「缺 2 行」＝库内 daily 表有 2 行不在 fresh 云端返回内**（**不是**库内缺数据）。

**系统性证据**：219 个不同 code **全部恰为 2 行** ⇒ 不是随机数据缺口，而是**同一边界条件**；
且受影响集含股票(`000001…000852`)与 ETF(`159110/159596/159816`)⇒ 与代码段无关。

**成功面对照（裁②价值兑现）**：
| 面 | code | adj_factor 覆盖 |
|---|---|---|
| committed | **000016** | 2010-01-04 ~ **2026-10-09** |
| committed | **000638** | 2010-01-04 ~ **2026-05-29** |
| blocked（219） | 000001/000848/000852 | 2010-01-04 ~ **2026-10-12** |

⇒ **两者的尾部不同**（committed 的因子止于 10-09 或更早；blocked 延伸到 10-12）
⇒ **领先假设（未证实）**：**库内 daily 的 2 行尾差（如 2026-10-12、10-13）不在 fresh 窗口内**
（fresh 重取窗口上界晚于/早于库内写入的日期 ⇒ 尾差 2 行）。
本假设可在**不占库**的条件下被证伪/证实——见 §2 第一段。

## §2 改动范围（**两段分离：先补证据，后修口径**）

**第一段（即做·纯增量诊断增强，不改判定）**：把 `_check_daily_coverage_strict` 的
`ReanchorBlocked` 消息**带上差集样本**（`missing` / `extra` 各取前 N 条 `(code, time)` 并附 ISO 日期），
落入既有 `qfq_deep_audit_item.last_error` + WARNING 日志 ⇒ **下一个单元即可指名"缺哪 2 行"**。
- 只增消息内容，**不改任何判定/阈值/写路径**；查询可复用（在既有 `matched` 查询上加 `EXCEPT` 差集，限 N 条）。

**第二段（**待**第一段证据确认根因后另批·六步再走）**：按证据修正比较口径。候选方向（**均不放松"严格一致"语义**）：
- 若证实为**窗口上界差**：把 `target_count` 限制在 **fresh 的 [min(time), max(time)] 区间**内（like-for-like），
  并对区间外的库内行**另行显式标注**（不静默忽略）；
- 若证实为**库内多出的 2 行为历史补入行**：在 fresh 侧**显式补齐或豁免登记**（登记而非忽略）；
- 若证实为**源端错漏**：转数据源线（非本线）。
