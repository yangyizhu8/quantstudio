## 1 问题与修复（客户可见口径）

1. 缺因子致整批失败（原「任一行缺因子即整批 raise」）：现改为**按比例隔离**——整列缺失仍硬失败；占比不超过阈值（默认 1%，可配）时**按行隔离跳过 + 登记**，其余行照常写入；超阈值仍硬失败。
2. **整码全缺**（如某只票整批不可还原，比例上可能很小）：**新增强制告警 + 明示登记**，**不得被全局比例阈值吸收**——不会出现「悄悄少一只票」。

4. 隔离区顶格：由**静默丢弃**（返回成功但 0 行入库）改为**显式背压信号**，批次会**明确失败并上报**，不再假装成功。
5. **隔离登记落在哪里（新增）**：上述「跳过/整码全缺」的登记写入 **`qfq_aux.db:qfq_d1_isolation_log`**——**一码一行、全量码不截断**，该库为纯检测辅助库、**可只读打开且不占用主库窗口**，故您无需停服即可自查（SQL 见 §3.2）。

1. 在**含上述构建**的环境重跑原场景 ⇒ 期望：**整批不再失败**；若遇瞬时缺因子，可见「按行隔离跳过 + 登记」；
2. **免库窗自查登记**（新增·替代原「检查 meta 键」表述）：只读打开 `data/qfq_aux.db` 后执行——
   ```sql
   -- Q1 今天有没有漏？漏了哪些码？漏了几次？
   SELECT code, kind, whole_code_missing, skipped_rows, hit_count, updated_at
   FROM   qfq_d1_isolation_log
   WHERE  round_no = CAST(strftime('%Y%m%d','now','+8 hours') AS INTEGER)
   ORDER  BY whole_code_missing DESC, skipped_rows DESC;

   -- Q2 所见是否完整？（truncated=1 表示码列表被截断，missing_codes_total 才是真值）
   SELECT round_no, listed_codes, missing_codes_total, truncated
   FROM   qfq_d1_isolation_log
   WHERE  truncated = 1
   GROUP  BY round_no;

   -- Q3 复算占比是否与引擎一致（自查跳过的合法性）
   SELECT table_name, freq, total_rows, missing_ratio, max_ratio, truncated
   FROM   qfq_d1_isolation_log
   WHERE  round_no = CAST(strftime('%Y%m%d','now','+8 hours') AS INTEGER)
   LIMIT  1;
   ```
   期望：`kind` 只出现 `row_skipped` / `whole_code_missing`；同一 code 同一业务日若重复命中，`hit_count` 累加（不会因后一次成功而抹掉「曾漏过」的记录）；

## 5 `truncated` / `listed_codes` 读法（新增）

- `listed_codes`＝**实际成功落盘**的码行数；`missing_codes_total`＝该批缺因子的**全量码数**（不受任何截断影响）；
- `truncated`＝**写时计算**：正常全量落盘恒 **0**；**部分写失败**（`listed_codes < missing_codes_total`）时置 **1**；
- ⇒ 判断「所见是否完整」只看 `truncated`：为 1 时以 `missing_codes_total` 为真值，并可对照日志中的 ERROR 审计行。
