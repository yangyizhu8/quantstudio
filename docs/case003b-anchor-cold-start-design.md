> 状态：v2（E2E 证据修订版）——原自播种设计被更小的时序修复取代（B4 实证：既有冷启动机制有效，缺口仅流式路径快照新鲜度）

## 1. 问题与根因（机制已勘察定谳）

**现象**：全新机拉 K 线表 → `[QFQ] _apply_qfq 未收到 adj_latest_map/adj_earliest_map 全局锚` fail-fast（C4 模拟实证，18:41 etf_daily）。

**根因（鸡生蛋闭环）**：

```
MCP 云端存前复权价（qfq）→ 客户端还原 raw_i = qfq_i × adj_latest_global / adj_i
adj_latest_global = qfq_aux 因子表（stock=adj_factor / ETF=fund_adj）MAX(time) 处的因子
aux 因子表由观测机制（EventDiscovery.observe_*）在数据入库过程中填充
→ 全新机 aux 空 → 锚缺失 → 首拉 fail-fast → 观测永远没机会填充 aux
```

我方机器无此问题：迁移期 bootstrap 已灌 aux。**客户全新机天生无此历史**——且门 2 的
“播种 completed 空基线”恰恰跳过了 bootstrap 因子冷灌（该跳过对既有迁移语义正确，
但全新机的锚需要另一条冷启动路径 = 本案）。

## 2. 修复设计：首拉自播种（方案 A，三选一中择优）

**关键事实**：MCP 拉回的 raw_df **自带 adj_factor 列**（还原公式的 adj_i 即来自它）。
锚的定义 =“已知最大时点的因子”——全新机首拉窗口必到当前日（full_range/incremental
语义），**窗口内 max(time) 处的 adj_factor 就是全局最新锚**，无需任何额外网络调用。

**改动点**（单文件 `mcp_adapter.py`）：

1. `_get_adj_latest_global` 新增**源粒度全新分支**（复用 `is_fresh_source_for_qfq`
   同款谓词思想，但判据为 **aux 因子表该 asset_type 零行**——更精确）：
   - aux 零行 且 窗口终点在近端（`window_end ≥ today − 7 天`）→ 从本批 raw_df 的
     adj_factor 列取 max(time) 处因子为锚（每码），返回锚映射；
   - **同时播种 aux**：把本批观测到的 (code, time, adj_factor) 写入 aux 因子表
     （等价观测机制的一次性冷灌），后续拉取走正常 aux 锚路径；
2. **窗口护栏**：aux 零行但窗口终点非近端（如历史窗 full_range 到 2024）→ fail-fast
   带明确指引（"全新机请先执行至当前日的全量/增量拉取建立锚基线"），防历史窗自播种
   产生错误尺度锚；
3. 既有机器（aux 非空）：**原路径逐字不变**（零影响红线）。
