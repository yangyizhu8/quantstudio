# 全池共享 bars 缓存方案（六步①，2026-09-26）

- 性质：**纯性能型**（可观察结果不变）；落点 `quantstudio/backtest/providers/duckdb_data_access.py`（框架层）
- 前置：T1 已落地（`d7539d5`）——单码路径已达池规模理论下界（重建 1,334 → 1,001 次/日）
- 两项设计定案（总调度裁定）：**预取触发 = 首个单码请求到达时按当日池预取**（无侵入，不动引擎时序）；**池范围 = `g.universe`**（策略 PIT 池 = 真实需求面）
- 回退：单 commit revert

## 一、背景与动机（实测）

| 项 | 数值 |
|---|---|
| 断板反包 wall（T1 后，3 交易日） | 55.1s ⇒ **18.4 s/日** |
| 每 code 每日首次建窗的 SQL | **1,000 次/日**（池规模；T1 后的唯一单码 SQL 来源） |
| 其余候选构成 | 策略自身逐码 numpy 计算、引擎每日固定开销 |

⇒ 本立项只针对**「每 code 一次建窗 SQL」**：改为**每日一次全池批量 + 按 code 切片共享**，预期单码 SQL **1,000 次/日 → 0 次/日**。

## 二、设计（含定案）

### 2.1 池范围通道（**定稿：通道 A**）
数据访问层不感知 `g`；池范围经**框架层内部通道**传入，不触策略代码。**总调度裁定取通道 A**：

- **A（定稿）**：`ptrade_api` 在 **`set_universe(...)` / `attach_day`** 处把**当日池**写入 `DuckDBAccess`
  （新增一行 hook + 数据访问层一个 setter；改动仅框架层内部，语义最清晰、命中率确定）；
- **B（过渡备选，仅当 A 不可用时）**：以策略**首个多码请求**的 code 集作为池（零 hook，但依赖策略
  先发多码请求——断板反包每日确实先发一次 `count=1` 的全池调用；不保证所有策略如此）。

行为细则：
- 首个单码请求到达时，若池已就绪且当日未预取 ⇒ **触发全池预取**（多码批量一次）；
- 池未就绪（策略未调 `set_universe` 等）⇒ **退化为 T1 按需建窗路径**（不报错、不阻塞）；
- 池写入时机若晚于首个单码请求（时序差），同样按退化路径处理，待池就绪后的下一请求触发预取。

### 2.2 缓存层级与单一真相源（硬验收）
- **池即唯一 bars 缓存**：键 `(before_ms, use_qfq)` → `{code: 窗口}`；
- 池命中：`tail(count).reset_index(drop=True)` 返回（沿用 T1 契约，逐位一致已证）；
- **非池 code**：走**直连 SQL 且不缓存**（罕见路径）——以避免出现第二个缓存真相源；
- **T1 的 per-code 窗口缓存退役**（池落地后不得并存）；退役前须证明池路径覆盖原 T1 路径的全部请求形态。

### 2.3 窗口 W：动态 + 保底（须在预证中量化扩窗成本）
- 定案：按当日请求 `max(count)` 动态设定；
- **保底 W_min**：建议 `W_min = 30`（覆盖本场景实测最大 `count=27`）⇒ 首次预取即取够，**绝大多数情况无扩窗**；
- 若后续请求 `count > W`：**扩窗 = 以新 W 重新批量一次**（代价 = 1 次全池批量）；预证须量化「每日扩窗次数 × 单次成本」；
- **退化条款**：若实测扩窗频繁（例如每日 >2 次）或单次扩窗成本接近收益 ⇒ **改用固定上界 W=60**（T1 现行值）。

### 2.4 PIT 隔离（沿用 T1）
`before_ms` 变化（新交易日）即**整体清空池**——与 `ptrade_api._query_cache` 每日清空的 PIT 纪律同构，绝不跨日复用；天然按日释放内存。

### 4.1 预证实录（2026-09-26，全部实测）

| 预证 | 结果 | 数据 |
|---|---|---|
| **P1** | ✅ **PASS** | 200 codes × {count=5, 27}，**6,400 行比对，不一致 0**（行数/列序/dtype/index/值 全等，NaN 安全） |
| **P2** | ✅ **PASS** | 同上口径，池 W=60 切片 vs 逐码取数，**6,400 行，不一致 0** |
| **P3** | ✅ **PASS（量级主张）** | 池内存 **10-15 MB / 1000 codes**（W=30：15.3MB/29,983 行；W=60：11.0MB/59,889 行）；全池批量耗时 **0.783s(W=30) / 0.987s(W=60)** ⇒ **全池预取固定成本 ≈0.8-1.0s/日** |
| **P4** | ✅ **PASS（且暴露 B 通道缺陷）** | 池就绪日命中率 **99.9%**（1,001 单码请求 / 池 1,000 / 命中 1,000）；`count` 取值 {2,5,27} ⇒ **count>30 请求数 = 0（无扩窗压力）**；扩窗成本 ~1s/次（若发生） |

**P3 测量口径说明（如实标注）**：首测出现 W=30(945.5MB) > W=60(12.3MB) 的反序——系**首次调用吸收一次性开销**
（连接/缓冲池/表元数据/路由缓存）；修正为「预热 + gc + 两档独立测」后两档收敛到 10-15MB。两档仍存在
W=60 < W=30 的轻微反序，属**RSS 增量噪声**（进程 RSS ~1GB，分配器/释放行为影响）——
故本预证只主张**量级**（10-15MB/1000 codes 可忽略），**不主张两档精确差**。

### 4.2 P4 的额外设计价值（**通道 A 由"偏好"升级为"必需"**）

- 实测：第 1 日命中率 99.9%，**第 2 日池为空 ⇒ 命中率 0%**；
- 机理：池信号来自策略的**多码请求**（通道 B），而该请求在次日**未到达数据访问层**（被上层缓存吸收）
  ⇒ **B 不可靠**；
- ⇒ **定稿采通道 A（`ptrade_api` 在 `set_universe(...)`/`attach_day` 处显式写入当日池）**；B 仅保留为
  A 不可用时的过渡（且必须接受"池缺失 ⇒ 命中率 0 ⇒ 退化为 T1 路径"的行为）。
- ⇒ **`W_min=30` 保底被数据支持**（本场景无 >30 请求）⇒ §2.3 扩窗条款降级为**防御性条款**（非日常路径）。
