## 1 问题定义

分钟数据任务（`mcp_stock_minutes`）单次运行耗时约 **5.4 小时**（实测 19534.6s），
每日 06:00 起跑的采集链里分钟任务排在后面，导致**到次日 06:00 仍未消化完**，
下一轮继续排队 ⇒ 数据更新持续滞后 ⇒ 实盘/模拟盘信号计算取到的是过期数据。

## 2 根因（实测读数，非推断）

### 2.1 阶段时延拆分（来源：`data/logs/daemon.log` 阶段时延行 + 历史实测）

| 任务 | rows | total | write | write_share | write_split |
|---|---|---|---|---|---|
| `stock_minutes` | 11,450,498 | 19,534.6s | 17,972.0s | **92.0%** | copy=1.0s / **invariant=12,067.8s** / sqlwrite=5,902.6s |
| `stock_daily` | 205,371 | 1,190.3s | 891.2s | 74.9% | copy=0.0s / **invariant=850.6s** / sqlwrite=40.5s |

⇒ 分钟任务的 **62%**（12067.8/19534.6）花在 `invariant` 桶；日线任务同一桶占 **71.5%**（850.6/1190.3）。
`invariant` 桶 = `_qfq_invariant_after_align()` 全流程（`daemon.py:3601-3606` 探针区间）。

### 2.2 该桶内部成本结构（只读量测，本机 aux 库 `data/qfq_aux.db`）

| 项 | 读数 |
|---|---|
| aux 库体积 | **11,177.7 MB** |
| `adj_factor` | **31,467,772 行** |
| `fund_adj` | **12,514,155 行** |
| 索引 | 存在（`idx_adj_factor_code_time` / `idx_fund_adj_code_time`）；`EXPLAIN QUERY PLAN` 确认 `SEARCH ... USING INDEX (code=?)` |
| 555 个 code 的 `WHERE code IN (…)` | `adj_factor` 返回 **3,275,402 行 / 25.4~38.8s**；`fund_adj` 返回 **2,591,439 行 / 56.1~66.6s** |

**索引不是问题，行数才是问题**：`_load_factor_lookup()`（`qfq_invariant.py:276-309`）的 SQL
**不带任何时间范围**，把每个采样 code 的**全历史因子行**拉进 Python，只为算
`(code, bar_day) → time 最大的一条` 因子。

数学核对：`stock_minutes` 233 shards × 每 shard 约 50s ⇒ **≈11,650s**，
与实测 `invariant=12,067.8s` 吻合（残差为批次/表类型差异）。

> 代码自身的历史注释已记录同类问题（`qfq_invariant.py:294-297`）：
> 「stock_minutes 时间切片批次抽样 ~555 code × 全历史 ~150 万行 → ~24 分钟/片」——
> 前次修复只向量化了「时间转换」，**未消除「取全历史」这一根因**。

### 2.2b 决定性实测：单批次 7 小时未完成（2026-11-04 16:38 现场取证）

同一批次 `mcp_stock_minutes_mcp_20261104_092849_a3c0d4`：

| 项 | 读数（日志原文节选） |
|---|---|
| 起始 | `09:28:49 === START task=mcp_stock_minutes table=stock_minutes/1min ===` |
| 重放标记 | `10:09:31 短路判定：skip=False 理由=a4_verdict=3（有 repair/full 或熔断 ⇒ 照常重拉）forced_replay_days=1` |
| 写冲突 | `10:09:32 ~ 10:13:30 write-write conflict`（每 80s 一次，共 4 次后越过；`cross_process_candidate=True` 但 `peers_n=0`） |
| 稳态写入 | 每批 `wrote 50000 rows (**新增 0 + 更新 50000**) 防重复 upsert` |
| 批间间隔 | 16:21:06 → 16:23:44 → 16:26:40 → 16:29:32 → 16:32:33 → 16:35:31 → 16:38:49 ≈ **175s/批** |
| 16:38:55 状态 | **仍在写，已持续 7h10m，未结束** |

**推算**：1145 万行 ÷ 5 万行/批 ≈ **229 批** × 175s ≈ **11.1 小时/轮**
（比历史读数 5.4h 更长，因本轮叠加了历史重放 `forced_replay_days`）。

⇒ 这正是用户所述「到次日 6:00 仍消化不完」的**量化机制**：单轮 > 24h 窗口的一半以上，
且下一轮 06:00 必然与上一轮尾部重叠。

**两个独立放大因子**（都可纯等价优化）：
1. **每个 50k 批次都对 ~数千 code 做全历史因子查询**（§2.2）⇒ 175s/批中的大头；
2. **批次间 code 集几乎不变，查询完全重复**（229 次冗余）⇒ 缓存可再降一个数量级（§3 P2）。

> 另注（不在本方案实施）：该批次 229 批全部为「新增 0 + 更新 50000」——
> 即数据已在库内、属重放。`skip_unchanged` 未使其短路，属**另一独立议题**
> （数据修正/短路语义面），须单独立项，不得与本性能方案捆绑（铁律 02：性能与正确性拆分）。

### 2.3 量测：加时间范围过滤的收益（同一 555 code，单位实测）

| 表 | 全历史（现状） | ≥最近 90 天 | ≥最近 30 天 |
|---|---|---|---|
| `adj_factor` | 3,275,402 行 / 25.43s | 1,039,345 行 / 12.24s（**2.1×**） | 249,595 行 / 2.49s（**10.2×**） |
| `fund_adj` | 2,591,439 行 / 66.58s | 518,708 行 / 5.47s（**12.2×**） | 125,729 行 / 0.55s（**121.3×**） |

实际收益取决于**每个 shard 的 bar_day 跨度**：shard 越窄，收益越大（按「本批 bar_day ± 冗余 1 天」过滤时，
窄切片可降 2~3 个数量级）。若 shard 覆盖全历史，则收益退化为 2× 量级。

## 3 改动方案（分三级，P1 与 P2 需分别裁定）

### P1（建议立即做）· 因子查询加时间范围，语义逐位等价

**改动**：`_load_factor_lookup(aux_conn, adj_table, codes, *, day_lo_ms=None, day_hi_ms=None)`
→ SQL 追加 `AND time >= ? AND time < ?`；`check_qfq_invariant()` 由本批 `df["time"]` 计算
`[min_bar_day 00:00, max_bar_day +1 天 00:00)`（**冗余 1 天**，覆盖因子行 time 落在同日任意时刻的情形）。

**等价性论证**（铁律 02 要求）：
- 原逻辑 = 候选集全历史 → 按 `(code, bar_day)` 取 `time` 最大者；
- 新逻辑 = 候选集限定在本批 bar_day 的**整个自然日闭区间**内 → 同一 `(code, bar_day)` 键的**全部**候选行仍在集合内
  ⇒ 取最大者结果不变；本批未出现的 bar_day 本来就进不了结果（`df` 无该日行）。
- 边界冗余 1 天使「因子行 time 与 bar grain 不一致（如 T 日盘后发布）」仍被覆盖。
- **回退开关**：`QS_QFQ_INVARIANT_FULL_FACTORS=1` ⇒ 走原全历史路径（逐位回退）。

**影响面**：仅自检候选集；不改写入、不改水位、不改告警判据、不改 `sampled/bad/skipped` 语义。
**预期收益**（按 §2.2b 实测 175s/批校准）：单批 invariant 约 150s → 5~15s
⇒ 229 批由 **11.1h 降至约 1.6~2.5h**；叠加 P2 缓存后可再降至 **0.6~1.0h 量级**。
**验收标准**：①同一批输入下 `sampled/bad/skipped/unknown_rows` 与改前**逐位一致**（用真实 batch 回放）；
②`invariant` 桶耗时下降可测；③既有 pytest 全绿 + 黄金回测结果零差异。

### P2（需单独裁定）· 周期内因子 lookup 缓存

同一次协调周期内，多个 shard 反复查询**同一批 code**（全市场）⇒ 建议按
`(adj_table, code 集指纹, day_lo/day_hi)` 在**单次 `run_once` / 单周期**内缓存。

- 收益：233 次查询 → 个位数次，可再降一个数量级；
- **风险（铁律 25）**：复权因子是可变第三方量。缓存生命周期必须严格限定在
  **单周期**且写明失效边界（跨周期必失效）；`reanchor` 后必须清缓存；
- 需明确：缓存只用于**自检观测**（不参与写入/复权计算），故即使因子在本周期内被上游微调，
  影响的也只是「自检读数口径」而非数据正确性 —— 但**必须**在方案里写明这一点，避免被误读为"允许缓存复权计算"。

### P3（另立项，属调度/引擎面，不在本方案实施）

用户提到的「分钟数据顺序靠后」是**排班问题**，与本次性能问题正交：
- 选项：分钟任务前置 / 分钟与日线并行 / 分钟按日推进的流水线化；
- 但均触及**引擎行为与水位推进语义**，须按铁律 02 单独立项评估，不得与 P1/P2 捆绑。

### 2.4 待补量测（决定 P1 是否足够）

需要一条实测：**分钟数据的日增量 vs 现有吞吐**。
- 若积压是**历史欠账**（一次性回补），P1 完成后即可自然收敛；
- 若**每日新增量本身超过吞吐**，则 P1 不够，必须先定「降范围（如分钟只采必要股票池/必要字段）」
  或 P3 调度改造。
- 量测方法（只读）：`stock_minutes` 按 `bar_day` 的**日增量行数分布** + 单批吞吐（行/分钟）。

## 4 回退条件

- P1 任一批次 `sampled/bad/skipped` 与改前不一致 ⇒ 立即回退（`QS_QFQ_INVARIANT_FULL_FACTORS=1`）并归因；
- 出现 `unknown_rows` 占比异常升高（>20% 告警线）⇒ 视为候选集被过度收窄，回退并检查范围计算；
- 黄金回测/既有 pytest 任一零衰减退化 ⇒ 回退。
