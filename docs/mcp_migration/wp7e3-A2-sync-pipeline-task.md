> A2 由本地 Trae 解决）
> 关联：QuantStudio WP7-E3 bootstrap 的 postcheck 暴露云端分钟线数据截断
> （A1 已批准：QuantStudio 引擎侧对缺 15:00 bar 的天跳过检查，**A2 不阻塞
> bootstrap，但必须修复**——影响所有分钟线消费者：回测/策略/估值）。

## 0. 背景与问题证据

QuantStudio bootstrap 重锚时 postcheck 拦截：
- 2026-07-10 分钟线末 bar 仅到 **13:34**（该日只有 126 根 bar），其 close_front=10.42
  与日线 close_front=10.45 差异 0.287% > 0.1% 容差；
- 取证（000001 近 20 交易日）：**80% 的天有完整 15:00 bar，20% 的天缺失**
  （3 天仅缺末 2-3 根 bar：14:57/14:58；1 天严重截断到 13:34 仅 126 bars）；
- 影响：日线 close 含 15:00 集合竞价，分钟线末 bar（<15:00）是连续竞价最后价——
  分钟线不完整时两者天然不一致。**数据源（云端）分钟线不完整**，根因在
  **本地同步管线的分钟线采集/推送环节**（云端数据由本地推送，非云端主动采集）。

## 1. 任务目标

修复本地同步管线的分钟线数据完整性，使云端每个交易日分钟线达到
**240 根 bar 完整（含 15:00 收盘 bar）**，并补齐历史缺失数据。

## 2. 任务步骤

### 2.1 定位同步管线与截断根因
1. 找到本地同步管线代码（采集 xtquant/tushare 数据 → 复权计算 → 推送云端 QuestDB），
   定位分钟线采集/推送模块与任务调度（cron/脚本/常驻进程）；
2. 复现/分析截断原因，候选方向（需验证）：
   - 采集器提前结束（尾盘 2-3 根缺失 → 采集结束时间早于 15:00，或 15:00 bar 被过滤）；
   - 严重截断天（126 bars）→ 当天采集异常中断/重试失败未告警；
   - 推送环节丢行（分批推送边界/去重/覆盖逻辑 bug）；
   - 上游 xtquant/tushare 分钟接口本身缺 15:00 bar（需与上游行为对照验证）。
3. **产出根因结论**（证据：对应日期日志/推送记录/云端与本地源数据对比）。

### 2.2 修复（当前采集，确保 240 bar/日完整）
1. 采集器：每个交易日必须采到 15:00 收盘 bar（含集合竞价语义），结束时间覆盖
   15:00:00 后留余量；缺失自动重试；
2. 推送侧：增加**完整性校验**——每证券每交易日的 bar 数（预期 240）与末 bar 时刻
   （预期 15:00）校验，不完整**拒绝推送或标记告警**，不允许静默入库；
3. 截断告警：异常中断/重试失败必须显式告警（日志 + 状态表），不能静默。

### 2.3 历史重采（2025-01-01 至今）
1. 统计缺失清单：`SELECT code, day FROM ... WHERE 日 bar 数 < 240 或末 bar < 15:00`
   （按云端分钟表逐证券逐日核对）；
2. 对缺失天补采 + 推送（复用修复后的采集器；严重截断天专项重采）；
3. **只补缺失行，不改写已正确的行**（幂等，避免扰动现有数据）；
4. 重采完成后的云端验证：缺失清单归零。

### 2.4 联动确认（与 QuantStudio 侧）
1. 云端数据修复后，通知 QuantStudio 侧：受影响证券（有缺失天的）可在
   T-B1（分片化改造包）完成后扩窗口重灌时自然补齐（QuantStudio 引擎 A1 已
   批准跳过缺 bar 天的 postcheck，bootstrap 不阻塞）；
2. 交付"缺失天清单"（code + day + 缺失 bar 数），供 QuantStudio 侧核对。

## 3. 交付物

1. 根因结论（同步管线截断原因 + 证据）；
2. 修复代码 diff（本地，按所在项目铁律/流程提交）；
3. 历史重采结果：缺失清单 → 归零的验证记录（云端查询）；
4. 完整性校验上线证据（新采集数据 240 bar/日 通过率）。

## 4. 验收标准

1. 云端分钟表：2025-01-01 至今每个交易日 240 根 bar（含 15:00），缺失归零
   （对全部存量证券抽查 + 缺失清单核销）；
2. 新采集（修复后）连续 5 个交易日 240 bar 完整率 100%；
3. 完整性校验生效：构造不完整数据 → 拒绝推送/告警（测试证据）；
4. 不影响既有正确数据（重采前后正确行逐值一致）。

## 5. 红线

- ❌ 不修改云端 MCP server 的读服务（它是只读消费端，问题在推送侧）；
- ❌ 不改写已正确的分钟行（只补缺失）；
- ❌ 不以"数据差不多"为由降低 240 bar/日标准（15:00 bar 是硬要求）；
- ✅ 修复优先保证"新的采集正确"，历史重采其次（重采量大可分批，但必须有
  完成时限与进度可见性）。

## 6. 时间建议

- 根因定位：≤1 天；采集修复 + 校验上线：≤2 天；历史重采：分批，≤1 周
  （重采量：~20% 天 × 全证券，与 QuantStudio 侧 T-B1 重灌窗口并行不冲突）。
