## §1 D1 · fail-fast 判据粒度（首批）

**现状**（移交件 + 本案双证）：

| 项 | 位置 | 现状 |
|---|---|---|
| 判定 | `mcp_adapter.py:2110-2133` | `valid = adj_i.notna() & (adj_i>0) & adj_latest.notna() & (adj_latest>0)`；`bad = ~valid`；**任一行 bad ⇒ raise** |
| 开关 | `:300` | `_RESTORE_MISSING_FACTOR_FAIL_FAST = True` **模块级硬编码**，客户不可切 |
| 既有能力 | `:2125-2126` | `skipped_rows_no_factor` / `missing_factor_codes` **已备却被 raise 分支丢弃** |
| 同族阻断点 | `:2066`（缺 adj_factor 列）/ `:2083`（缺 code 列） | 同为硬 fail（列级缺失） |

**量级实证**：客户 8/50,000 = **0.016%** 终结 35.4h 批次；本案 241/45,790 ≈ **0.53%**（单 code=300457）。

**方案（判据分层 + 阈值可配 + 开关配置化）**：

| 情形 | 处置 | 理由 |
|---|---|---|
| **整列缺失**（无 `adj_factor`/`code` 列） | **保持硬 fail**（不变） | 属**云端契约变更**，放行即全批双重复权风险 |
| 行级缺失 **占比 ≤ 阈值**（默认 **1%**，可配） | **按 code 隔离跳过 + 登记 + 计数告警**（复用既备字段 ⇒ 落 `qfq_deep_audit_item`） | 跳过的行**不写入** ⇒ 无双重复权风险；其余行正常还原（**正确性不降**） |
| 行级缺失 **占比 > 阈值** | **硬 fail**（保安全网） | 大规模缺失指向系统性问题，不应继续 |

**开关配置化**：`QS_RESTORE_MISSING_FACTOR_FAIL_FAST`（env）+ 配置项（`data_config.json`），**默认保持严格**（`strict`），客户可按场景切 `threshold`。

**判型**：**纯恢复型 + 新增能力型混合**（移交件 §6.4 预判一致）——
恢复"已备却未启用"的隔离登记能力（纯恢复），新增阈值/开关维度（新增能力）；**份额变化须显式声明影响面**（见 §3）。

| 面 | 声明 |
|---|---|
| **写入份额** | D1 阈值内跳过的行**不再进入主库**（客户案 0.016%、本案 0.53%）⇒ **份额减少**，但**这些行本就无法正确还原**（原逻辑=整批不写）；⇒ **净效果：从"整批零写入"变为"绝大部分正确写入 + 少量跳过登记"** |

## §4 验收标准（**双环境**，照移交件 §6.1）

**我方环境（回归）**：
1. 既有测试全绿 + 黄金结果零回退（纯恢复型要求）；
2. 构造三态单测：整列缺失 ⇒ 硬 fail（不变）｜占比 ≤ 阈值 ⇒ 隔离跳过 + 登记（新增）｜占比 > 阈值 ⇒ 硬 fail（新增）；
3. **默认 strict 下行为与修复前逐位一致**（开关不动的路径）；
4. 隔离登记**可外部只读查**（`qfq_deep_audit_item`，免库窗）。

**客户环境（复验口径，随修复通知下发）**：
1. 客户在**同一 fail-fast 场景**（单 code 缺因子）下复跑 ⇒ **批次不再整体失败**，且隔离登记可见；
2. 客户自查：跳过行数/涉及的 code 与 `skipped_rows_no_factor` 一致；
3. 客户侧**无需改配置**即得零行为变化（默认 strict）——**切 threshold 须显式**。
