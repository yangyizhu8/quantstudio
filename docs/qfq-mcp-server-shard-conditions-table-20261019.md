## C1 禁止改变 `row_limit` 的「保留集合」语义

### 条文要点（复述，不改写）
1. 不得把 `ORDER BY` 从「时间优先」改为「码优先」——那会让 `LIMIT` 的截断轴变成**码的字典序**，**静默丢掉 600/601/603/688 及北交所全部数据**；
2. 被保留的那 N 行集合**必须与现状一致**，以**定界 `t_cut` 复现**，而非改 SQL 语义轴；
3. **违反即否决。**

### 我方回应：**接受，无保留**

**理由（我方独立得出同一结论）**：我方应答件附 A 已把 F2 登记为**封死路径**——「不得以改 `ORDER BY` 轴作为优化手段（会静默丢沪市）」。**C1 与我方 F2 是同一条约束**，两侧从不同侧面（云端：契约侧；我方：静默丢数据侧）独立得出同一结论。

**我方承诺**：
- 我方在**任何**后续方案/实施中**不得**提议或接受「改 `ORDER BY` 轴」作为提速手段；
- 我方对「保留集合」的验收要求**只看结果**：改造后保留的 N 行集合须与现状一致（以 `t_cut` 定界复现）；
- 我方**不因性能收益而要求放宽 C1**。

### C1.3 为何不影响 41× 可达性

41× 的来源**不是**改变 `LIMIT` 的截断轴，而是**让客户端少触达分片**（每码只需 1–2 个分片）。C1 约束的是**保留集合**（哪些行进入结果），与**分片触达次数**（读几个文件）是两件事。
⇒ **满足 C1 的前提下 41× 仍可达**，前提由 C2 的 manifest 每码索引提供。

### C1.4 对 T1 新事实的确认

云端实测 **QuestDB 不支持 `OFFSET`** ⇒ `t_cut` 定界只能走 **`min(subq LIMIT N)` 变体**（已入云端 T3 规范）。

**我方确认**：接受该约束。我方**不在客户端侧假设 `OFFSET` 可用**；若我方应答件或后续方案提及「定界实现」，一律注明此约束。当前我方应答件（`88a3916`）**未涉及定界实现细节**，无需修订。

## C3 内存峰值不高于现状基线（硬门槛）

### 条文要点（复述，不改写）
1. 服务端现有宽表防 OOM 取舍（文本列走 `WIDE_SHARD_ROWS=10000` / `WIDE_FETCH_SIZE=2000`）**不得被绕过**；
2. 改造后**同一 job 的峰值内存不得高于改造前**；
3. **违反即否决。**

### 我方回应：**接受，无保留**

**与我方 INV-1 同向**：我方此前已把「内存字节预算不得突破」列为**一等约束 INV-1**——实测全市场帧 `stock_minutes` **p50 59.96 MB / mean 46.40 MB / max 71.63 MB**，191 条目需 **8.9–13.7 GB**，故我方**自己就否决了「缓存全市场帧」方案**（候选 (b) 出局），并规定新增缓存上界 **≤ 64 MB**。

⇒ **两侧内存约束同向，不存在冲突**；我方**从未要求**服务端以放宽内存取舍换取性能。

**我方承诺**：若 41× 的实现需以**提高服务端内存峰值**为代价，**我方宁可不做**——C3 优先于性能收益。
