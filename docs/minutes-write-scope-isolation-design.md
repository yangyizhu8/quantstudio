## 1. 背景与动机

### 1.1 现象（客户可观察）

06:00 日轮与补跑中，分钟表任务**整批失败**并落 `write-write conflict on key`；止点冻结，10-30 收口硬阻断。

### 1.2 证据链（实弹，均为 2026-10-22/23 复核读数）

| 观测 | 证据 |
|---|---|
| 冲突 key 恒定 | etf `159512, 1789090200000, 1min`（2026-09-11 09:30）；stock `000055, 1788744600000, 1min`（2026-09-07 09:30）——共 19 次 |
| **不是瞬时并发** | A6 有界重试实弹 3 次（10-22 21:23 stock、10-23 07:34 etf、10-23 08:17 stock）：`写冲突重试 1/3→2/3→3/3` **全败**，冲突持续 >6s 且不可重试化解 |
| 冲突者**在同进程** | 3A 写锁 holder = daemon 自身（pid 53256，task=mcp:1217）；进程清单无第二个 DB 写者 |
| A1 指认**误报** | 失败槽 `peers_n=0 cross_proc=True`（同进程无 peer ⇒ 跨进程候选）——但持锁者即 daemon 自身 ⇒ 登记表把**同进程长事务写者**判没了 |
| 登记表剪除机理 | `_REGISTRY_TTL_S=300.0` 固定 TTL；而 QFQ 引擎单元事务常 **>300s**（10-22 14:00 实测 1 单元=63min）⇒ `price_write_enter` 登记被 TTL 剪除 ⇒ peers 恒空 ⇒ cross_proc 恒 True |
| DuckDB 语义 | A5 负向对照实证：**单语句写内部串行；两事务同时改同一行 ⇒ 第二个确定性失败** ⇒ 冲突必然是「**重叠事务**」，而实弹形态 = 引擎长事务 × 任务写 |

### 1.3 根因定谳（四层）

1. **现象**：分钟表整批写失败（commit 期 write-write conflict）。
2. **直接原因**：任务写的 upsert 事务与 **QFQ 引擎在程 apply 事务**在**同一批 key** 上重叠。
3. **代码缺陷**：写锁与写者登记的**作用域是「语句级」**——`table_write_lock` 只覆盖一次 upsert；而引擎在**整个 apply 单元**（分钟~小时级）内持有一个写事务，其作用域远超锁的保护范围 ⇒ 锁无法互斥（RLock 同线程可重入、跨线程只串行化**锁持有期**而非**事务期**）。
4. **业务边界问题**：分钟表**双写者**（采集任务写 vs QFQ 引擎 rebase 写）本就重叠在同一批历史 key 上（原止点冻结 43 天的家族同源）；框架未定义「谁在何时可写哪段 key」。
5. **潜在隐性风险**：A1 因 TTL 误报 `cross_proc=True` ⇒ 若据此立「跨进程锁」方案会**修错对象**（真实持锁者是同进程引擎）；B 放行率 0%（因子等价 E1 在 `high` 列不成立）⇒ 水位不前进 ⇒ 重锚与任务写**持续同 key 交叠**。

## 2. 范围与边界

### 2.1 改动范围（文件级）

| 文件 | 改动性质 |
|---|---|
| `quantstudio/pipeline/writers.py` | 登记表升级（A1b：心跳刷新 + (pid,thread) 存活判活，取消固定 TTL）；新增**作用域登记/检测/让行**原语（`price_scope_enter/exit`、`price_scope_conflict`、`wait_for_scope`） |
| `quantstudio/pipeline/qfq_reanchor_engine.py` | apply 单元期间**持有写作用域**（scope 覆盖整个单元事务），并在单元提交后释放 |
| `quantstudio/pipeline/daemon.py` | 任务写前**让行**（检测到重叠在程作用域 ⇒ 等待，超时降级为 A6 重试）+ 观测计数 |
| `quantstudio/pipeline/daemon_lifecycle.py` | run_state 观测字段扩 `write_scope`（在程作用域数/让行次数/等待时长） |
| `tests/test_minutes_write_scope.py`（新增） | B1-B7 单测 |
| `docs/evidence/minutes-write-scope-2026xxxx.md`（新增） | 验收证据件 |

### 2.2 不改动范围

- 采集任务的水位推进口径、validator、字段规范化、调度时序；
- QFQ 引擎的**判据层**（E1-E4 因子等价、raw 对齐阈值）——**B-1 取证另案**，本方案不碰；
- schema 契约（2.1/2.2）、`source_watermark` 结构；
- 其他业务线代码（backtest / gui / strategy_compiler）。

### 2.3 口径约束（来自 KB 已知错误-ST数据层-对齐回填缺口）

时间域比较**必须按表分口径**：`stock_minutes.time` = CST 墙钟-as-UTC；`etf_minutes.time` 口径需单列确认（实施前以 `DESCRIBE`+样本核对为准，**不得默认同口径**）。作用域键采用 `(table, code, time_window)`，其中 `time_window` 以**表自身口径**表达。

### 2.4 兼容边界

- 新原语**默认开启**（作用域让行），但**可逐位回退**：`QS_PRICE_WRITE_SCOPE=0` ⇒ 退化为现状（语句级锁 + A6 重试）；`QS_PRICE_WRITE_SCOPE_WAIT_S`（默认 120s）控制让行上限，超时⇒走 A6 重试链（不静默丢批）。
- A1b 判活改造**只影响观测**（登记表内容），不改变任何写行为。

## 4. 风险描述

| 风险 | 表现 | 规避 |
|---|---|---|
| 让行延长轮次 | 任务写等待引擎单元 → 轮次变慢（引擎单元可达 63min） | 等待上限 120s + 超时降级重试；观测累计等待秒；必要时以 `max_units_per_cycle` 降吞吐换收敛 |
| 作用域过粗（未带 code/时间域） | 整表互斥 ⇒ 引擎期间任务写全让行 | 作用域必带 code+时间域；单测负向：异码/异段不阻塞 |
| epoch 口径混用 | 同段判定失真 → 假冲突或漏判 | §2.3 口径约束（按表口径；实施前实测核对，不默认） |
| 登记内存增长 | 长时间运行累积 | B1 判活剪除 + 硬上限（沿用 `_REGISTRY_MAX`） |
| 回归面 | 改 writers/引擎/daemon 核心路径 | 既有 19+8 单测全绿 + 新增 B 单测；`test_writers_rw_backoff.py` 零衰减；收尾 WAL 收敛复核（KB WAL 族） |
| 与 B 专项叠加 | B 放行率恢复后引擎提交变多 ⇒ 交叠更频繁 | B6 观测先行；若让行计数 >90% ⇒ 回查「作用域是否过粗」 |

## 5. 验收要点

- **功能验收**：B1-B7 单测全绿（含每点负向对照）；既有 19+8 回归零衰减。
- **场景验收**：① 引擎在程时任务写让行后成功；② 引擎不在程时任务写零等待（**零衰减**：正常路径不引入等待）；③ 作用域超时后如实失败不静默；④ 回退开关=0 逐位旧行为。
- **边界验收**：异表/异码/异段不阻塞；`QS_PRICE_WRITE_SCOPE_WAIT_S=0` 退化为直败；epoch 口径按表（负向：错口径不误判）。
- **实弹验收**：B8（生产 06:00 轮）+ `write_scope` 观测首现 + 止点推进（`verify_minutes_recover.py` 不再 GAP）。

## 6. 质量判据

1. **问题彻底修复**：分钟表任务不再因「重叠事务」丢批——判据=连续 2 轮 06:00 日轮分钟任务 success 且 `write_retry.exhausted=0`。
2. **无回归**：既有 19+8 单测全绿；新 B 单测全绿；daemon 轮次收尾 WAL 收敛为 0（KB WAL 族复核）；06:00 轮次总耗时无显著劣化（对比本窗基线：任务段 72/73、轮次 06:04→11:03）。
3. **符合工程标准**：纯增益（不减少既有功能）+ 防回归设计内置（B 单测 + 回退开关 + 观测字段）+ 口径纪律（epoch 按表）。
4. **可证伪**：每个功能点有独立可复跑判据与负向对照；实弹结论写证据件。
