## 一、问题定义（病根·运维2 已定谳 + 我方实读确认）

**基准写回被「任务成败」绑架**：`_a4_last_sync` 只在增量任务**完整成功**时才写；任务失败（写冲突 / 窗口 poison / **A4 子段自身异常**）就永不推进 ⇒ 基准冻结 ⇒ 云端批量 repair 被一次捕获 ⇒ 熔断（987 > 20）。

**我方实读补充的关键发现（与建议件表述的差异·须记录）**：

建议件称「把 `save_last_sync` 从『批次成功返回前』移到『水位推进成功之后』」。实读 `daemon.py:1429-1436` / `1678-1685` 显示：**`save_last_sync` 已经在写入完成之后（`batch_audit.record` 成功行之后、`return True` 之前）**——即**位置本身没错**。

⇒ **真正的缺口是：A4 子段（`_check_cloud_updates_and_repull`，L1149）的任何异常会使整个 `execute_task` 走 `except` ⇒ 批次 FAILED ⇒ 到不了 L1429/L1678 ⇒ 基准不推进**。

⇒ **故 P0-1 的正确实现 = 「A4 子段异常隔离」+「基准写回保持在水位推进之后」**，而非移动写回位置。这一点是本件对建议件表述的**修正**，请②审重点核。

## 二、落点清单（实测行号·HEAD=4b295e8）

### P0-1 A4 子段异常隔离（纯恢复型）

| 项 | 实测落点 | 改法 |
|---|---|---|
| 调用点（非流式） | `daemon.py:1147-1149`（`_a4_verdict = 0` / `if mode != "full_range":` / `_a4_verdict = self._check_cloud_updates_and_repull(...)`） | **包 try/except**：异常时 `logger.warning`（含 table + 异常类型 + 摘要）+ `_a4_verdict = 0`（视同「无更新」）+ 继续主增量 |
| 调用点（流式） | 同函数在流式路径的同构调用（若为同一入口则一处覆盖；实施前再 grep 确认第二处是否存在独立调用） | 同上 |
| 写回点（保持原位） | `daemon.py:1429-1436`（非流式）/ `1678-1685`（流式） | **位置不动**；仅改 `except Exception: pass`（见 P0-2） |

**语义**：A4 是「云端 repair/full 局部重拉」的**增强子段**；其失败不应使主增量失败——这正是设计意图「增量主体成功即推进」。

**判型：纯恢复型**（回到设计原态，不改取数/校验/水位语义）。

### P0-2 写回异常不静默（新增检测型·与 P0-1 分开验收）

| 项 | 实测落点 | 改法 |
|---|---|---|
| 异常吞没 | `daemon.py:1434-1435`（`except Exception:` / `pass  # last_sync 持久化失败不影响采集`） | 改 `logger.warning("[%s] A4 基准写回失败: table=%s err=%s", batch_id, table, type(e).__name__)` |
| 同构 | `daemon.py:1683-1684`（裸 `pass`） | 同上 |

**判型：新增检测型**（开始报告真相；须与 P0-1 **分开验收**，不得混办）。

### P1 计数去重 + 阈值可配（判断类·单列·**不与 P0 混办**）

| 项 | 实测落点 | 改法 |
|---|---|---|
| 去重 | `daemon.py:3059-3062`（`repull_dates = []` / `repull_dates.append(str(u.get("trade_date",""))[:10])`） | 累加后 `repull_dates = sorted(set(repull_dates))`，**按 trade_date 去重后再计数** |
| 阈值可配 | `daemon.py:3031-3032`（`# F-3.3…` / `_A4_MAX_WINDOWS = 20`） | `self._A4_MAX_WINDOWS = int(os.environ.get("QS_A4_MAX_WINDOWS", "20"))`，**默认 20 ⇒ 既有行为逐位不变** |

⚠️ **去重改变熔断触发语义**（例如 987 条记录但仅 12 个交易日 ⇒ 去重后 12 < 20 **不熔断**）⇒ 属**行为变更型**，须显式声明影响面、单列验收（C3）。

### P2 缺位显式化 + 建表收口（纯增益）

| 项 | 实测落点 | 改法 |
|---|---|---|
| 缺位升告警 | `daemon.py:3052`（`logger.info(f"[{batch_id}] A4 跳过检测：{table} 无 last_sync 基准（首次/升级后）")`） | 升 `logger.warning`，文案补「本表 repair 检测未启用（基准缺位）」 |
| 建表收口 | `update_detector.py:65`（`ensure_last_sync_table`，懒执行） | writer init 处**幂等调用一次**；并加「表存在但目标表无行」体检告警 |

**判型：纯增益**（不改既有成功路径行为，除日志级别）。

## 五、回退条件与手段

| 回退触发 | 手段 |
|---|---|
| 出现 `_a4_last_sync` 基准「跑在数据前面」（C1-N1/N2 反向失败） | 回退 P0-1（恢复 A4 子段异常上抛） |
| 日志噪声过大（P2 升 WARNING 后每表每轮一条） | `QS_A4_MISSING_BASE_LOG=0` 降回 INFO |
| 去重导致熔断失效过度（该熔断的未熔断） | `QS_A4_DEDUP=0` 关闭去重（默认按 P1 实施后为 1） |
| 阈值行为漂移 | `QS_A4_MAX_WINDOWS` 显式设回 20 |

**共性回退**：所有新增行为均带 env 开关，且**默认值 = 既有行为**（除 P0-1/P0-2 的语义修正本身）⇒ 回退后**不劣于现状**。
