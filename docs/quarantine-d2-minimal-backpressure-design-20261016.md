## 1 问题定义

现状（quarantine.py:105-124）：pending_repair 计数达 max_rows（默认 500,000；配置 quarantine.max_rows）⇒ 记 logger.error 后 return 0。

缺陷三点：
1. 静默丢弃：return 0 属成功语义（0 行入库）⇒ 调用方无法区分「本批无有效行」与「配额满全丢了」⇒ 任务报成功、数据却缺；
2. 不阻断不重试：上游继续跑（10-13 实证 06:35-15:30 共 9 小时、712 批隔离行被丢弃，时间照付）；
3. 腾退当日无效：_auto_archive_expired（:156-164）按 retention_days=7 归档 ⇒ 当日积压腾不出配额。

与 D1 的耦合（本件时限由来）：D1 把少数坏行转为隔离跳过 + 登记，而登记落点就是隔离区 ⇒ 顶格静默丢弃会吞掉 D1 的登记与跳过结果。

## 2 改动范围（仅两项·不含腾退）

1. 背压：顶格时不再返回 0 假装成功，而向调用方抛出明确背压信号（专用异常类型或显式失败状态），由调用方决定中止本批/停止采集/上报；
2. 告警升级：从单条 logger.error 升级为任务级/管道级可观测（落审计行 + 任务状态/摘要可见）。

明确不做（照裁）：腾退/扩容/按表配额/归档策略调整。

判型：新增检测型 + 行为修正型（顶格时由静默成功改为显式失败/背压）。影响面声明：原顶格后仍报成功的批次将转为失败/中止——系有意（让缺口暴露而非隐藏），呈批时单列。

## 3 影响面

- 顶格时：由返回 0（成功）转为抛出背压信号/显式失败 ⇒ 上游批不再静默完成；
- 未顶格时：零变化（分支不进入）；
- 归档/腾退：零变化；
- 与 D1 关系：D1 登记不再被吞（本件即 D1 的前置保护）。

## 4 验收标准

1. 顶格注入（pending_repair >= max_rows）⇒ 写入尝试不得返回 0 成功，必须产生可捕获背压信号；
2. 告警可观测：运行摘要/审计面可见顶格事件（不仅日志）；
3. 未顶格回归：低于上限时行为逐位不变（既有测试全绿 + 黄金零回退）；
4. D1 联动演练：构造少数坏行 + 隔离区顶格 ⇒ 断言登记不被吞（跳过行数在审计/摘要可见）；
5. 判型声明与实际一致。

## 5 回退条件

按定 scope 四步配方建回退点；回退＝还原硬上限分支为 logger.error + return 0（单点改动）。

## 6 待审项

1. 背压信号形态：专用异常 vs 显式失败状态（建议专用异常，避免被 except Exception 静默吞掉而回归成功语义）；
2. 调用方（daemon ingest 路径）对背压信号的处置：中止本批 vs 停止本轮采集 vs 仅上报（建议中止本批 + 上报，停止采集留运维决策）；
