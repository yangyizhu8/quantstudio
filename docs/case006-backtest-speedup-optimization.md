## 一、处置原则（本案例的第一条经验）

**不采信客户归因，自行溯源取证。** 客户附带的归因方向**大体正确**，但其中**一处关键判断
不准确、一处预期缺证据**（见 §三）——若照单执行，会把"结构性日界冲突"误修成"调时区偏移"，
并对外承诺一个无依据的提速幅度。

## 二、归因结论（分层）

### 2.1 第一处：日线快照预取缓存失效 —— **确凿回归**

| 项 | 事实 |

| 缺陷点 | `quantstudio/backtest/providers/duckdb_data_access.py:499`：`time // 86_400_000 * 86_400_000`（**UTC 日界**，输出 mod 恒为 0） |

## 三、对客户归因的两处精化更正（**本案例核心价值**）

1. **客户说**「该式假设数据是 UTC 零点，正好与北京时间错位」
   **实测更正**：该式输出 **mod 恒为 0**，**与库内 `time` 实际存什么时区无关**——是
   **UTC 日界 vs CST 日界的结构性冲突**。此精化决定了修复必须是「统一日界到唯一真相源」，
   而非「把偏移调对」。
2. **客户预期**「修好后应从 1 小时降到秒级」
   **实测反证**：单次未命中仅 **0.0165 s**，若每日一次，8 年约 33 s，**无法解释 1 小时**。
   ⇒ **不为其背书**，改为「实测口径 + 不换算承诺」。

## 七、通用教训（已入全局记忆 `c6074346`）

① 缺陷严重性 ≠ 收益大小（本案「缓存 100% 失效」与「实测收益 <4%」并存）
② 性能件双证：等价性 + 收益实测，缺一不可
③ 对照有效性前提：证明「走了不同路径」才能说「结果相同」
④ 术语口径一次说清（同一份库被叫影子/备份/副本致沟通错位一轮）
⑤ 小样本不作方向性结论（n=3 全同号单侧 p=1/8）
⑥ 先读被测实现再采信自述（本案发现「签名逐字符不变」申报失实一处）
⑦ 文件级拷贝 ≠ 一致快照（活动 WAL 下不可拷贝；安全快照须 `VACUUM INTO`）

**另两条流程教训**：
⑧ **参考 message 先于 commit 到达审核侧**（本次曾先 commit 后送达，登记为事后追认）
⑨ **推送闸门凭证化（C7 实例 #2）**：本线推送时未拦截本地挂着的他线未确认提交，
随推泄漏；根因是**「已 commit」被误当「已过闸门」** ⇒ 今后推送请求必须随附
`git log origin/main..HEAD` 全清单原文 + 逐条归属与闸门状态
