## Q1 重锚环在增量场景的开销（12h40m 中约 90%）

### 1.1 机制（取证）

| 要素 | 落点/事实 |
|---|---|
| 引导门 | `QFQOrchestratorConfig.require_bootstrap`（默认 `True`，`qfq_orchestrator_types.py:401/466`）；`require_bootstrap=true` 且无匹配版本 completed bootstrap → **本轮 fail-closed（不推进水位）**（`qfq_resident_orchestrator.py` §8 契约） |
| 水位策略 | `watermark_policy`（默认 `hold_until_consistent`，`:420/480`）；**当前仅接受这一个值**（`:508` 校验 `not in ("hold_until_consistent",)` → 其他值非法） |
| 水位提交 | `_commit_or_hold_watermarks(...)`（`:811`）：gate 通过才推进四价格表水位；否则 `status='held'` + `hold_reason` |
| 窗口切分 | `qfq_fresh_capture._split_windows(start, end, cap_days)`（`:116`）——把 [start,end] 切成单窗 ≤ cap_days 的闭区间列表 |
| 价格修正源 | **永远 xtquant**（fresh_capture fail-fast 锁定）→ 每次重锚都要**真拉数据**（非纯计算） |

**推定触发链（待补证）**：增量任务 → 价格表写完后 gate 校验 → 因 `hold_until_consistent` 未一致 → 触发重锚环：
`require_bootstrap` 路径跑**全窗口**（含年内全窗）fresh fetch（xtquant 真拉）+ **逐段校验** → 未一致则继续 hold →
**每个价格表任务后重复** ⇒ 12h40m 里约 90% 落在该环。

### 1.2 改进候选（三案）

| 案 | 内容 | 影响面 | 三型判定 |
|---|---|---|---|
| **A 窗口化**（增量模式仅校验增量窗 + 低频全量校验） | 增量周期内 gate 只校验**本周期增量窗**；全量窗口校验降频（如 T+N 或每日一次/冷启动） | **改变校验覆盖语义**（同一周期内不再全窗校验）→ 可能延后一致性问题发现 | **非纯性能型**：属**行为/覆盖语义变更**，须单独立项 + 用户裁定 |
| **B 配置化**（把重锚环窗口/频次做成显式配置，默认不变） | 新增配置键（如 `reanchor_window` / `full_verify_interval`），**默认仍等于现行为** | 行为默认不变；仅提供运维可调旋钮 | **纯恢复型（默认不变）+ 新增能力**；可作为 A 的载体 |
| **C 冷启动解耦**（首次部署 bootstrap 与日常增量分离） | bootstrap（首次建基线，重）只在冷启动跑；完成后日常增量走轻校验 | 影响 bootstrap 语义边界 | 需先补证 bootstrap 是否**每轮**重跑（若只在冷启动跑，则 12h 主因另有其处） |

> **先取证再定案（禁止未证实归因）**：必须先在**副本/测试环境**量化「一次增量周期内重锚环被触发几次、每次覆盖多少窗口、各类耗时占比」。
> 取证动作：① 读 `_discover`/gate 调用链确认触发条件；② 在测试 profile 上跑一次 `once` 增量，采集
> `qfq_trigger_queue` / `qfq_watermark_intent` / fresh_capture 调用日志的**次数与窗口跨度**；③ 与客户 12h40m 拆解对齐。

### 1.2b 我线自审：笔3「收尾检查点」在增量场景的**新增成本**（必须计入 12h 拆解）

**事实**：本线笔3（`aef6b9d`，随 `000b5bb` 批推送）在 `ResidentCollector.close()` 末尾加了安全检查点
（`daemon.py:222-226` → `db_checkpoint.checkpoint_database(main_db)`），而 **`close()` 每轮采集后都会被调用**：

| 成本项 | 量级 | 说明 |
|---|---|---|
| `join` 上限 | **每轮最多 +120 s**（`DEFAULT_CHECKPOINT_TIMEOUT_S`） | WAL 大/库被占用时，`close()` 在该轮**阻塞至多 120 s** 才返回 |
| 检查点本体 | 实测 **7.3 s / 2.33 GB** | 无 WAL 时为空操作（≈0）→ 常态便宜 |
| 多轮累计 | **120 s × 轮数**（最坏） | 若该轮 12h 内轮次多，可显著放大 |

⇒ **结论**：该项是**我线引入的可测量新增成本**，必须纳入 Q1 的 12h 拆解；
**若客户版本含笔3**，则 12h 中应能观察到 `[db_checkpoint]` 日志行（据此可直接量化）。
**优化候选（与本线台账联动）**：① 把收尾检查点从「每轮同步 join」改为**空闲期巡检触发**（与 `wal_health_check` 同宿主，避免每轮付 join 成本）；
② 或把 `timeout_s` 降到与常态 WAL 匹配的小值（如 15 s），超时即让巡检接手——**属纯恢复型（默认行为不变）+ 配置化**，需走六步轻量方案。

### 1.3 六步轻量方案骨架（待案例 A/B 定性后细化为呈审件）

1. **方案**：以 B（配置化，默认不变）为**载体**，A（窗口化）作为**推荐配置值**单独立项，附影响面声明；
2. **审计**：独立审核（含「覆盖语义变更」风险与回退开关）；
3. **实施**：最小改动（配置键 + gate 分支），默认值 = 现行为（保证零影响）；
4. **验收**：① 默认配置下**黄金结果逐项一致**（纯恢复型判据）；② 开启窗口化后一致性收敛时间/耗时对比（附差异归因）；③ 回归全绿；
5. **用户确认**：A 的启用属行为变更 → **须用户裁定**；
6. **双推**。

## Q2 `get_artifact` 载荷级 error 未识别 → 误判协议错误 → 周期 hold

### 2.1 定性（取证，链路完整）

| 步 | 事实（代码） |
|---|---|
| ① 工具级错误通道已存在 | `client.py:359-370`：`result.isError` → `MCPToolError`；`result["error"]`（dict）→ `MCPToolError` |
| ② 但客户的错误**在载荷内** | 客户日志：`get_artifact 缺少 Parquet base64 字段: keys=['error','artifact_id']` ⇒ 工具**成功返回**了一个结构化载荷，其内含 `error` 键（服务端把错误塞进 artifact 内容），**未走**上述两通道 |
| ③ 客户端随后按「协议错误」上抛 | `client.py:806-810`：四个 base64 字段全空 → `raise MCPProtocolError(...)` |
| ④ 后果 | `MCPProtocolError` 被上层视为**不可重试**（区别于 `MCPToolError`/预算类重试路径）→ export 路径失败 → **gate hold**，且该错误**无重试、无降级、无显式留痕字段** ⇒ 水位可**永久卡死** |

**结论：框架缺陷成立**（服务端返回 error 载荷属协议内可预期形态，客户端必须显式分类处理，而不是当作协议违例上抛）。

### 2.2 修复方案（最小、纯增量）

| # | 改动 | 说明 |
|---|---|---|
| ① | `get_artifact` 开头**显式识别载荷级 error**：`if d.get("error"): …` | 提取 message（截断）+ `artifact_id`/`job_id` → 抛**专用异常**（建议复用 `MCPToolError` 语义或新增 `MCPArtifactError(retryable=…)`） |
| ② | **可重试分类 + 重试**：瞬时类（超时/未就绪/服务 busy）→ 走既有重试预算（`_call_with_retry` 语义，重试计入审计行）；**不重试类**（artifact 过期/不存在/参数错）→ 明确失败 | 复用既有重试预算与审计通道，不新增机制 |
| ③ | **降级与留痕（关键）**：不重试类失败时**不得静默**——结构化留痕（artifact_id/job_id/shard/error 原文），并让上层能**降级**（重取该批 / 标记该 shard 失败 / 计入死信），**不使水位永久 hold** | 与既有 `dead_letter_max` 死信机制对齐（`qfq_resident_orchestrator:759`） |
| ④ | 错误文案**保留 keys 提示**（现状有价值）但补充 error 原文 | 便于下一次同类问题一眼归因 |

**三型判定**：**纯恢复型 + 新增检测型**——
- 正常路径（有 base64）行为**完全不变**（纯恢复型判据：diff 纯新增、无行为漂移）；
- 对「error 载荷」这一**原先未处理**的形态，属**新增能力**：它会把原本「误判协议错误→hold」改判为「可重试/可降级 + 留痕」→ 属**新增检测/健壮性**形态，须在方案阶段单列（不按纯恢复型混办）。

**验收**：① 载荷级 error（构造 `{"error": {...}, "artifact_id": ...}`）→ 断言走专用异常 + 留痕字段齐全；② 瞬时类 error → 断言重试计数与审计行；③ 不重试类 → 断言上层可降级且**水位不永久 hold**（重跑后自然推进）；④ 正常路径 golden 逐项一致；⑤ 回归全绿。
