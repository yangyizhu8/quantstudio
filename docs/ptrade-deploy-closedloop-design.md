# PD-0011 方案：qs-deploy 全流程闭环管线（测试 → 反哺 → 修复 → 验证 → 沉淀 → 再验证）

> 立项依据：2026-10-28 用户裁定「先完成回测转 PTrade 模拟盘/实盘的**全流程测试、反哺、修复、验证、知识沉淀**
> 闭环管线，再进行该转换框架层缺陷的修复」；本件为①方案，**未实施、未提交**。
> 关联：`docs/ptrade-deploy-pipeline-design.md` §8（回哺机制）、`docs/ptrade-deploy-convergence-ledger.md`
> （§4.1–4.8 轮次与收敛判据）、`knowledge/ptrade-deploy/`（PD 族 10 条）、铁律 22（知识反哺 R1/R4）、
> 铁律「新功能模块闭环收敛」。
> 编号说明：原拟 PD-0011=is_trade 契约修复、PD-0012=契约表补 `get_order`；本件占用 **PD-0011 = 闭环管线**，
> 两个框架缺陷案顺延为 **PD-0012（is_trade 契约）/ PD-0013（契约表补 get_order）**，待本件闭环建成后立项。

## 1. 问题定义（实证）

**现状判定：管线是「回哺自动 + 沉淀/修复人工」的半闭环。**

| 环节 | 自动化程度 | 实测证据（2026-10-28） |
|---|---|---|
| P0 回哺读库 | ✅ 自动 | 转换日志 `[note] P0 vault 回哺来源：trading-knowledge`；`read_vault` 读 10 条 |
| 失败 → 沉淀条目 | ❌ 无 | `quantstudio/ptrade_deploy/*.py` 对 `kb_draft`/`kb_hook` **零调用**（grep 仅命中文档注释） |
| 修复推进 | ❌ 人工 | 六步全靠人驱动 |
| 收敛 N_i/R_i 计数 | ❌ 人工 | 台账 §4.1–4.8 手工登记，无机检 |
| R1 开工留痕 / R4 验收沉淀 | ⚠ 靠自觉 | 无脚本校验「本轮是否留痕」 |

**后果（本次实证）**：`全球资产轮动` 转换 P5 FAIL（`set_limit_mode` 嵌套未门控 + `get_order` 契约表外），
系统**正确检出**，但失败停在「人工分析」——R1 检索面无对应条目（PD 族无 `is_trade` 条目）、
未生成任何沉淀草稿、无脚本能回答「此刻闭环是否健康」。这正是闭环后半段缺失的直接表现。

## 2. 目标与非目标

**目标**：把六环节固化为**可重复执行、可机检、可审计**的 PD 域闭环管线，使「跑一次转换 → 失败 → 沉淀 →
回哺 → 再验证」有固定动作、固定判据、固定产物、固定退出码。

**非目标（明确排除，按裁定时序）**：
- 框架缺陷本体修复：`is_trade()` 语义契约冲突（顺延 PD-0012）、契约表缺 `get_order`（顺延 PD-0013）——
  **本件建成闭环后才启动**；
- 不改 `quantstudio/ptrade_deploy/` 任何代码（本件纯增量：脚本 + 测试 + 文档）。

## 3. 设计

### 3.1 六环节定义（每环节：动作 / 产物 / 判据）

| # | 环节 | 动作 | 产物 | 判据 |
|---|---|---|---|---|
| ① | 测试 | 跑样本集 `run_deploy`（6 策略产物 + 含 `if not False:` 的 3 个产物 + 全球资产轮动） | 逐阶段 verdict 汇总 | 与既有基线一致（已知 FAIL 归因明确） |
| ② | 反哺 | P0 读库 + 本轮 R1 留痕 | P0 `vault_source`/`vault_entries` 读数 + 留痕行 | 读数非 degraded；留痕行 grep-able 命中 |
| ③ | 修复 | 六步流水线（方案→②审→实施→验收→⑤确认→⑥推送） | 设计件 + 证据件 + 台账轮次 | 六步不缺环 |
| ④ | 验证 | deploy 套件 + P4 equiv + 契约矩阵 + （涉及产物时）6 策略重转 | 证据件 | 全绿；任何回归即回退 |
| ⑤ | 沉淀 | `kb_draft --kb knowledge/ptrade-deploy` → `kb_hook --strict` → 台账 N/R | PD 条目 + 台账轮次 | 族机检 0 不合规 |
| ⑥ | 再验证 | 回哺有效性两级判定（见 §3.3） | 台账 `R_hit` 列 + 巡检读数 | L1 必过；L2 人工确认留痕 |

### 3.2 五项缺口与解法（本件实施面）

| 缺口 | 解法 | 落点 |
|---|---|---|
| **G1** 失败不自动起草条目 | 新增 `scripts/kb_draft_from_deploy.py`：吃 `run_deploy` 报告（json/退出码）→ 生成**可直接执行的 kb_draft 命令**与待填字段清单（root_cause/trigger/fixture 占位） | 新脚本；**不自动落盘**（保持人工确认，避免脏条目污染族库） |
| **G2** 「回哺生效」无判据 | 定义两级：**L1 句柄级**＝条目被读到（`entries>0` 且 `source` 非空且未 degraded）——机检必过；**L2 语义级**＝本次失败的 `trigger` 与已有条目命中——人工确认后于条目 `feedback.gate_rule` 记「命中轮次」，台账记 `R_hit` | 判据定义 + 台账列 |
| **G3** N/R 手工计数 | 新增 `scripts/check_pd_convergence.py`：解析台账 §4.x 的 `N_i`/`R_i` → 校验「连续 3 轮 R=0 且 N 单调不增且末轮=0」→ 输出 PASS/FAIL + 序列 | 新脚本 |
| **G4** 无闭环巡检 | 新增 `scripts/check_deploy_closedloop.py`：一键跑 ①测试摘要 ②读库读数 ③族机检 ④收敛校验 ⑤R1/R4 留痕检查 → 汇总 + **退出码**（0 健康 / 1 硬缺口 / 2 仅 WARN） | 新脚本 |
| **G5** R1/R4 无校验 | 并入 G4：本轮台账段落须含「知识反哺：」与「本轮沉淀：」行，缺失 → WARN（连续 3 轮缺失升 FAIL） | G4 内实现 |

### 3.3 「回哺有效性」判据（G2 细化，本件核心增量）

- **L1（机检，必过）**：`read_vault()` 返回 `entries ≥ 1`、`source ∈ {trading-knowledge, main-knowledge}`、
  `degraded=False`。**含义**：回哺链在本次运行确实读到库——这是现状已能测的。
- **L2（人工确认 + 留痕）**：失败现象的 `trigger` 与某条目 `trigger` 命中时，须在该条目
  `feedback.gate_rule` 追加「命中 轮N/日期」，并在台账该轮记 `R_hit=PD-YYYY-NNNN`。
  **含义**：区分「读了库」与「库真的救了这次」——后者才是闭环的目的。
- **不做**：不引入自动语义匹配（易误判）；L2 保持人工判断 + 强制留痕。

### 3.4 退出码与挂载点

| 退出码 | 含义 | 处置 |
|---|---|---|
| 0 | 闭环健康 | 可推送 |
| 1 | 硬缺口（收敛不满足 / 族机检不合规 / 回哺 degraded） | 阻断本域推送 |
| 2 | 仅 WARN（R1/R4 缺失、样本缺项） | 允许推送但须在回执申报 |

**挂载点**：本轮**仅手动执行**（`py -3.11 scripts/check_deploy_closedloop.py`），**不挂 `.githooks/pre-push`**
——理由：pre-push 已挂 C7 闸 + 铁律预算门，再叠加会让他线推送被本域巡检阻塞（跨线耦合风险）。
待本件运行 ≥3 轮稳定后，再单独提案是否挂载。

## 5. 验收标准（七项，逐项可机检）

1. `check_deploy_closedloop.py` 在真实仓运行 → 输出五项读数且退出码 0；
2. `check_pd_convergence.py` 对 §4.1–4.8 判 **PASS**（N 序列 4→2→1→0→1→1→1→0，R 连续 8 轮=0）；
3. **负向对照**：合成台账（R>0 / N 非单调）→ 脚本 FAIL（退出码 1）；
4. `kb_draft_from_deploy.py` 对「全球资产轮动 P5 FAIL」**真实报告**生成可执行起草命令（含待填字段）；
5. **零行为变更**：deploy 套件仍 **84/84**、契约矩阵哈希一致、`quantstudio/ptrade_deploy/` **零 diff**；
6. R1/R4 缺失检测：临时删台账「本轮沉淀」行 → 巡检输出 WARN（退出码 2），恢复后回 0；
7. 族机检 `kb_hook --strict` 仍 **10/10**（新增脚本不得影响族库口径）。

## 6. 影响面 / 风险 / 回退

| 项 | 评估 |
|---|---|
| 转换行为 | **零变更**（不改 `ptrade_deploy` 任何代码；新增脚本不参与转换路径） |

## 7. 三型判定

**新增能力型**——新增巡检/起草/校验能力，**不改变**任何既有 verdict 与转换产物；按铁律「新功能模块添加：
纯增益 + 双端对等」，本件**不提供 CLI/UI 双端功能入口**（属内部运维脚本，非用户功能），故双端对等条款不适用
（若②审认为需纳入 `qs-compile` 子命令，则在③实施时补 CLI 入口并保持单一内核）。
