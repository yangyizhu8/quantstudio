## 2 机制定谳：F1 vs F2（②审要求的判别核心）

### 2.1 ②审提出的账目矛盾

> 11-06 轮应写 ≈ 11-05 残余 121 万 + 11-06 全天 126 万 ≈ **247 万行**，但 changed 仅 **87.7 万**。
> 约 **160 万行「库里没有、理应 changed」**被归入 unchanged（或根本不在拉取里）。

### 2.2 判别问题：`unchanged` 到底与谁比对？

**代码直读（`daemon.py:3424-3477` `_filter_unchanged_rows_scoped`）**：

```python
tmin, tmax = int(t_ser.min()), int(t_ser.max())
existing = self.writer.read_df(
    f'SELECT {quoted} FROM "{table}" WHERE time >= {tmin} AND time <= {tmax}')
```

**⇒ `existing` 来自 `FROM "stock_minutes"` = 主库当前表内容（writer 连接）。**

**⇒ F1（比对源污染：与 stale manifest/staged 比）在代码层【不成立】。**
比对锚定主库，不存在"库里没有却因 manifest 见过而跳"的路径。
（唯一例外：`except` 兜底 `return df` 是全量写，只会多写不会少写；`existing.empty` 也是全量写。）

### 2.3 那 160 万行去哪了？→ **F2 成立，且形式是「A4 重拉取代主增量」**

**11-05 轮实测（`daemon.log.2026-11-05`）**：

```
轮次开始 @ 07:27:21
** INCREMENTAL: 2026-10-17 → 2026-11-05 **          ← 上界含当天 ✅
A4 检测到 stock_minutes 有 3 个 repair/full 更新窗口，开始局部重拉:
   ['2026-11-04', '2026-10-26', '2026-10-23']        ← 只重拉这 3 天

export 分片按日统计 ==> {'2026-10-23': 26, '2026-10-26': 26, '2026-11-04': 8}
```

**⇒ 决定性事实：**
| 项 | 值 |
|---|---|
| 增量声明上界 | **11-05（含当天）** |
| **实际 export 覆盖** | **只有 10-23 / 10-26 / 11-04** |
| **11-05 当天分片** | **0 片** |

**⇒ 11-05 当天根本没被拉取。** 160 万行不是"被判 unchanged"，而是**从头就没进入拉取集**。

**⇒ F2 成立，且具体形式比"上界滞后"更精确**：
> **A4 的 repair 窗口重拉【完全取代】了主增量的拉取，不是【补充】。**
> 声明写着 `10-17 → 11-05`，实际只执行了 A4 的 3 个窗口，**当日被系统性跳过**。

**⇒ 这同时解释了 `etf_minutes` 更早断（11-02）**：它每轮的 A4 窗口集合不同，连续多轮都没覆盖到新日期。

### 2.4 结论（F1/F2 判定）

| 假说 | 判定 | 依据 |
|---|---|---|
| **F1 比对源污染** | ❌ **代码层不成立** | `_filter_unchanged_rows_scoped` 直查主库表，不读 manifest |
| **F2 拉取边界/取代** | ✅ **成立（主因）** | 声明含 11-05，实拉仅 3 个 repair 窗口，当日 0 分片 |

**但按②审要求「不许收敛」**：F1 虽代码层排除，**仍保留其守卫腿**（成本低、防未来回归），修复三腿全上。

## 3 修复设计（三重腿全上，②审硬性要求）

### 腿 1（F2 主修）：增量边界硬保证 + A4 不得取代主增量

| # | 改动 | 说明 |
|---|---|---|
| 1.1 | **增量上界硬保证**：`end` 必须 ≥ 最近交易日（取 `trade_calendar` 最新 `cal_date` 或"今天"） | 现状已含当天（声明正确），**但需断言**：若 `end < 最新交易日` ⇒ 拒绝执行 + ERROR |
| 1.2 | **A4 重拉与主增量解耦**：A4 窗口集合**必须并入**主增量拉取集，而非替换 | 现状是"检测到 repair 窗口就开始局部重拉"覆盖了主流程 ⇒ 改为「主增量 ∪ repair 窗口」并集 |
| 1.3 | **当日窗口零分片守卫**：每个交易日在 export 后校验「分片数 > 0」，为 0 ⇒ WARNING + 记入缺口账本 | 11-05 当天 0 分片却无任何告警，这是监控缺失 |

### 腿 2（F1 守卫 + 缓存完整性）：缓存命中必须校验，不信托 manifest

| # | 改动 | 说明 |
|---|---|---|
| 2.1 | **比对源断言**：`_filter_unchanged_rows_scoped` 入口断言 `existing` 来自目标表（防未来改成读 manifest） | 现状正确，加断言防回归 |
| 2.2 | **`export_cache` 命中强校验**：命中时校验分片文件存在 + 行数 > 0 + 与 manifest 记录一致；不符 ⇒ 视为 miss，回退直连 | D4 归因件有 1,254 条 `重取无 shard` 前科；11-07 也有 `校验失败回退直连` |
| 2.3 | **当日数据不参与 RS 过滤（第三重保险）**：`time` 落在最新交易日内的行，`changed` 恒为 True | 成本极低，两者通吃 |

### 腿 3（监控）：按日 × 证券数剖面告警

| # | 改动 | 说明 |
|---|---|---|
| 3.1 | 新增每日不变式检查：`(行数, 证券数)` 对比最近 N 日中位数，低于阈值（如 95%）⇒ **WARNING/ERROR 告警** | 移植云对拍系统「码×日 bar 计数达标」思想（`trading-battle-back` 的 S3 自愈器，脚本在先生工作区，**库不相通不可直接用，仅借鉴方法**） |
| 3.2 | 告警写入 `batch_audit` 或新增 `minutes_daily_invariant` 表，供 GUI/QA 读取 | — |
