# R1 补遗 · 两处实测定谳

## 一、get_stock_exrights 调用成本基准（决定"纯策略层计算股息率"是否可行）

证据脚本：`r1_addendum_exrights_bench.py`（运行时真实调用，非估算）

| 场景 | 调用数 | 耗时 | 单次 |
|---|---|---|---|
| 1 只 x 245 个交易日（12 个月窗口，miss 为主） | 245 | 0.38 s | **1.554 ms** |
| 5 只 x 50 个交易日 | 250 | 0.35 s | 1.398 ms |

单次成本拆解（DuckDB 直测）：`DESCRIBE stock_dividend` 0.407 ms + 索引 SELECT 0.899 ms = 1.31 ms，与实测吻合。
即 `query_stock_exrights` **每次调用都重跑一次 DESCRIBE**（duckdb_data_access.py:1259），属调用开销主导。

### 关键结论：`get_stock_exrights` 是"单除权日精确匹配"API，不是区间查询
```
底层 SQL: SELECT ex_date, cash_div_before_tax AS bonus_raw, stk_div
          FROM stock_dividend WHERE code = ? AND ex_date = ?
```
因此"Σ bonus_ps（ex_date ∈ 近 12 个月）"**不能一次调用取得**，必须对每只标的扫描窗口内全部交易日
（约 244 个交易日 / 次）。

### 方案可行性（含强制缓存约束）
- **必须**在策略层维护"每只标的的已扫描游标 + 除权事件列表"的会话内缓存；否则成本为
  `调仓次数 x 池大小 x 244`。
- 采用增量游标（首次入池回填 244 日，此后每次调仓只补新增交易日）时，全回测估算：
  300 只池 x 244（首次回填）+ 约 390 次调仓 x 300 只 x 5 日 ≈ **66 万次调用 ≈ 16 分钟**。
- 不做缓存：60 次防守月调仓 x 300 只 x 244 日 ≈ 439 万次 ≈ **114 分钟**（不可接受）。
- **性能契约须写入 R2 设计**：单次探测 1.4-1.55 ms；游标增量 + 事件列表缓存为强制项；
  缓存失效条件（新标的入池、窗口滑动）显式声明。

## 二、估值快照真实锚点实测定谳（客户要求"实施前实测定谳并写进契约"）

attach 上下文：`_api.attach(engine, None, None, date='2026-07-30', prev_date='2026-07-29')`

| 标的 | 快照返回 turnover_ratio | 07-29 真值 | 07-30 真值 | 归属 |
|---|---|---|---|---|
| 600519.SS | 0.4986 | **0.4986** | 0.5749 | prev_date |
| 000060.SZ | 2.2147 | **2.2147** | 2.0728 | prev_date |

流通市值同源验证：快照 float_value = 1.651358e8 万元 = 165,135,779.36 万元 = **2026-07-29** 的 `stock_daily_valuation.circ_mv`（07-30 为 170,231,111.96）。

### 定谳
**预加载快照的锚点是 prev_date（T-1），不是决策日 T。**
R1 报告第 3 节 B2 中"命中预加载快照即直接返回决策日估值"的措辞**不准确，特此更正**为
"返回 **T-1（prev_date）** 的估值快照"。该事实须写入 B2 修复方案的契约章节。
