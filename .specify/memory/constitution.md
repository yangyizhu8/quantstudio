# QuantStudio Constitution

> 本准则为 SDD 各阶段（specify / plan / tasks / implement / converge）的最高治理基准。
> 违反任一条 MUST 原则 = 最高严重度（CRITICAL）问题，不得以「差异很小」「结果更合理」放行。

## Core Principles

### 一、代码质量：最小可逆改动，落点必须是所有者
- MUST 把修复/改动落在问题的所有者层（框架内核、契约表、校验器、模板），禁止在产物或调用点打补丁掩盖根因。
- MUST 保持改动最小且可逆；每笔改动必须能单独回滚，回滚后系统回到改动前可观察状态。
- MUST NOT 引入与本次任务无关的重构、格式化或依赖升级（禁止捆绑）。
- SHOULD 新增能力优先复用系统已有的、语义匹配的原语，而不是另造一套并行机制。

### 二、测试先行：先能复现，再谈修复
- MUST 在改动代码前先有可失败的验证手段（复现脚本、契约测试、黄金对比基线之一）。
- MUST 每项验收标准都可机检；无法机检的标准必须显式标注为人工评审项并说明判据。
- MUST 区分「新增能力型」与「行为漂移」：新增能力开始报告真相可以改变 verdict，但既有功能不得回退。
- MUST 测试证据落盘（`docs/evidence/` 或 spec 目录下的验收记录），申报时附实测读数，禁止以「已完成」替代证据。

### 三、可维护性：单一内核 + 双薄壳，双端对等
- MUST 同一能力只实现一份内核逻辑；CLI 壳与 GUI 壳调用同一内核函数，禁止两套独立实现。
- MUST 凡提供终端入口的新能力，同时在 GUI 提供功能对等入口（反之亦然），且对等性可机检。
- MUST 状态机、生命周期钩子等跨模块协作点有单一权威定义处，不允许多处各自维护同一份状态。
- SHOULD 新概念引入前先检查系统内是否已有同义概念，避免语义分叉。

### 四、纯增益：可观察行为不得漂移
- MUST 任何改动前完成三审计：是否影响项目其他功能 / 是否影响回测性能 / 是否影响回测精度；任一项为「影响」即不得按纯增益处理，须单独立项。
- MUST 显式声明改动类型（纯性能型 / 纯恢复型 / 数据修正型 / 新增能力型），并按其判据验收。
- MUST NOT 改变回测引擎的可观察结果（信号、订单、净值、费用、撮合、PIT、复权口径、生命周期调用时机），除非该改动本身被声明为数据修正型且已获批准。

### 五、逐位一致与可回滚
- MUST 涉及结果正确性的验收以逐位一致（哈希/全精度字符串镜像）为准，只允许既有测试契约明确写出的浮点容差。
- MUST 出现任何非预期差异即判验收失败并立即回退，不得带病入库。
- MUST 危险操作（批量 git 操作、停启 daemon、DDL、强杀进程）前建立回退点并声明占用窗口。

## 附加约束

- **运行环境**：Python 项目，本地零依赖策略；数据主库为 DuckDB。duckdb 版本治理按**放行集合**执行（当前集合：`{1.4.5 ≤ x < 1.5} ∪ {x == 1.5.6}`；唯一判定源 `quantstudio/pipeline/duckdb_version_policy.py`，门禁/双脚本/契约三个判定面共用同一实现，不得各自维护规则）。集合外版本一律由启动门禁拒启（固定退出码 3）；紧急放行只经 `QS_DUCKDB_VERSION_GATE=0`，且必须留醒目告警。升级决策须满足 **90/60/30 升级判据**（见下）。
- **到期复核装置**：放行集合的每条版本线登记 EOL 日期；按 **90/60/30 升级判据**推进——**距 EOL 90 天出方案**、**60 天进实施**、**30 天完成或书面接受风险**（**判据以 spec FR-010 为唯一口径**）。到期、以及缺陷单关闭或新补丁发布时，由承载方（**总调度 EOL 日历守护** + 仓库内守护条目；落地实现见 `specs/002-duckdb-1.5-upgrade/tasks.md` T056）自动落一条复核提醒；未完成复核的版本线不得继续放行。
- **数据一致性**：被指纹校验的表（`source_watermark` / `trade_calendar` / QFQ 契约表等）任何 DDL 视为契约变更，须按契约变更六件套同 commit 交付。
- **并发边界**：存储层不做真并发/副本快照读/单写者服务化等结构性改造，除非单独立项并经用户批准。
- **文档同步**：代码改动必须同步更新受影响的 README / docs 引用；禁止只改代码漏文档。

## 开发流程

- 框架层改动走六步：书面方案（含影响面、验收标准、回退条件）→ 独立审核 → 实施（不擅自提交/推送）→ 验收（测试全绿 + 回归/黄金对比，证据落盘）→ 用户明确确认 → 双仓推送并核对两远程一致。
- SDD 链内以 `tasks.md` 为执行清单，完成即勾选；`analyze` 阶段只读，`converge` 阶段只允许向 `tasks.md` 追加任务。
- 首次改动源码前必须通过检查点 A（呈报 spec/plan/tasks 三件套摘要与 analyze 结论，停等用户批准）。

## Governance

- 本准则高于其他实践约定；与项目 `AGENTS.md` 铁律冲突时，以更具体者为准，并在变更记录中说明取舍。
- 修订须记录版本号、修订日期、修订理由与迁移说明；破坏性修订须逐条列出受影响的既有约定。
- 下游各阶段（specify / plan / tasks / analyze / converge）以本文件为核对基准；analyze 发现违反 MUST 原则即判 CRITICAL。
