## 【铁律】框架层改动六步流水线：方案 → 审计 → 实施 → 验收 → 用户确认 → 双仓库推送

### 适用范围
凡涉及以下**本地回测框架层面**的修复/改动，一律适用本规则：

- 框架 API 函数（如取数 API、策略工具箱注入 API 等）
- 数据适配层（数据读取、复权处理、字段映射等）
- 框架生命周期函数（initialize / before_trading / handle_data / after_trading 等）
- 其他属于回测框架内核层面的修复（编译器契约、校验器、QFQ/复权管线、数据巡检等框架组件同理）

### 必须执行的流程（六步流水线，任何一步缺失即违规）

1. **先给方案**：任何框架层改动，必须先产出书面方案（设计文档，如 `docs/*-design.md`），
   至少包含：问题定义、改动范围、影响面、验收标准、回退条件。**禁止未给方案直接改代码**。
2. **审计方案**：方案提交独立审核（ZCode 等审核方）审计通过后，才能进入实施。
   审计未通过 → 修订方案重新审计，**禁止带病实施**。
3. **实施**：按审计通过的方案实施改动，**绝不擅自**提交或推送到 GitHub。
4. **验收**：实施完成后必须验收（单元测试全绿 + 回归/黄金结果对比 + 差异逐项归因等，
   按方案验收标准执行），验收结论写入证据文档（如 `docs/evidence/*.md`）。
5. **用户确认**：向用户完整汇报（改动内容 + 验收证据），**经过用户明确同意确认之后**，
   才能执行同步提交。
6. **双仓库推送**：确认后 `git push origin`（多 push URL 双仓库同步，2026-08-12 起），
   推送后核对两个远程仓库均一致：
   - https://github.com/yangyizhu8/quantstudio-plus
   - https://github.com/yangyizhu8/quantstudio

### 同步内容必须完整

- 相关框架代码文件的更新；
- `README.md` 中涉及这些修复的相关内容（策略工具箱、提示词工程等章节）；
- 引用文档中涉及的相关内容，至少包括：
  - `docs/strategy_toolbox.md`（策略工具箱）
  - `docs/prompt_engineering.md`（提示词工程）
- 即：README 正文 + 上述引用文档中所有涉及该修复的表述，都要同步更新，确保 GitHub 项目与本地实时一致。

### 禁止事项

- 禁止未给方案、或方案未审计通过即开始实施。
- 禁止在未获用户确认前，将框架层修复推送/提交到 GitHub（含任何代理顺带提交）。
- 禁止跳过六步流水线中的任何一步（方案/审计/实施/验收/确认/推送）。
- 禁止只更新代码而遗漏 README 及 docs 引用文档的同步更新。

> 用户原话要求：任何涉及框架层的改动，都需要先给方案，再审计方案，最后实施，实施后验收完成，用户确认后再走双仓库推送。养成习惯，写死到记忆中，确保以后不会忘记执行，从而确保 GitHub 上的项目保持实时同步。
