## 修复设计

**落点**：框架层 `_QS_QMT_MODULE_HEADER`（wrapper 加载期），策略源码零改动。

**分级**：
- **P0 探测**：`pd.Timestamp('2000-01-01', tz='Asia/Shanghai')` 是否可解析 → 可解析则**直接返回**（零副作用）
- **P1**：`pytz._tzinfo_cache[别名] = pytz.FixedOffset(480)`（pytz 存在但缺命名数据时生效）
- **P2**：patch `pandas._libs.tslibs.timezones.maybe_get_tz`（原函数存**模块属性**，避免局部别名调用被 portability 校验判「未知 API」）
- **P3**：patch `zoneinfo.ZoneInfo`（同上）

**等价性**：中国自 1991 年起无夏令时 ⇒ 固定 `UTC+8` 与 `Asia/Shanghai` 在回测窗口**逐位等价**（T4 抽样验证）。

**反向设计（fail-loud）**：三层全失败必须打印 `QS_QMT_TZ_SHIM failed`，**不得**静默降级或返回原对象——否则重演「零告警静默失效」（与本族 QD-2026-0021 同型病）。


### ✅ 真机验证（2026-11-06 10:41，交付定谳）

**探测行实测原文**：
```text
QS_QMT_TZ_PROBE pytz=Y zoneinfo=N resolve=P1-Y tzcache=5 level=P1
```

**读法（每一字段都是证据）**：

| 字段 | 实测值 | 含义 |
|---|---|---|
| `pytz` | **Y** | QMT 内置 Python **有 pytz**（排除"pytz 完全缺失"假设） |
| `zoneinfo` | **N** | QMT **无 `zoneinfo` 模块**（Python 版本较早或精简）⇒ **原方案 P3 级垫片在该环境天然不可用** |
| `resolve` | **P1-Y** | 初判（`pd.Timestamp(tz='Asia/Shanghai')`）**失败** ⇒ 走 P1 注册（5 别名）后**成功** |
| `tzcache` | **5** | 5 个别名全部注册成功 |
| `level` | **P1** | **仅 P1 即足够，P2/P3 未触发** |

**结论**：真机缺的是「pytz 的 Asia/Shanghai 命名数据」而非 pytz 本体；P1（`pytz._tzinfo_cache[名] = FixedOffset(480)`）是**恰好的那一级**。分级设计在此环境省掉了 P2 的 pandas 内部 patch 与 P3 的 zoneinfo patch——**若当初直接上 P2/P3，会因 zoneinfo 不存在而失败，反而绕远**。

**修复效果**：真机全文 `get_fundamentals failed: 'Asia/Shanghai'` **零出现**（修复前每个调仓日必现）；选股口径随之改变（新增 `002577`、`300321` 消失）——即 EPS 的 C/A 因子重新参与综合评分。

**方法论留痕**：`zoneinfo=N` 这一条**只能靠真机探测得到**，本地（有 zoneinfo）永远测不出。这再次印证「P0 探测先行、不盲选垫片层」的设计价值。

## 讨论

- **实施中发现的两处修正（R318 自测拦下）**：
  1. **零输出契约冲突**：原方案「恒打印探测行」会破坏 wrapper 既有「absent 态零输出」契约（5 个既有测试当场变红）⇒ 改为**仅当需要垫片时输出**：正常环境静默、缺时区环境必打印（真机诊断信息不丢，契约不破）。
  2. **portability BLOCK**：初版用 `from datetime import timezone as _dttz` + `_dttz(...)`、`_orig_get(...)` 局部别名调用，被 `validate_qmt_portability` 判 6 条 `QMT-API-WHITELIST` BLOCK ⇒ 改为 `import datetime as _qs_qtdt` + `_qs_qtdt.timezone(...)`（模块方法调用）＋原函数存模块属性（`_pdtz._qs_orig_get_tz`）。
- **同族教训（值得上提为普适判据）**：
  - **「取不到就用默认值」在替使用者做安全判定**：QD-2026-0021 的 `or 0` 与本条的 `except` 兜底空表，都是「失败被压成看似正常的值」；
  - **宽 try 块的「成功路径上的失败」最难察觉**：A 成功、B 失败时，日志把 B 记成 A，且业务表现为「少了几个因子」而非报错；
  - **改动的输出行要与既有输出契约对齐**：新增任何 print 前先查该模块「零输出」是否被测试断言（本案 5 例红）。
