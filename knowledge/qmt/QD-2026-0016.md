## 复现步骤

1. **未入库内核**：M5.2 件4 的 `quantstudio/strategy_compiler/qmt_deploy.py`（7,145 B）、`tests/test_qmt_deploy.py`（4,772 B）、`config/qmt_deploy.json`（255 B）自 2026-10-12 立项起**从未进入 git 历史**；`orchestrator.py`（＋`deploy_qmt: bool = False` 形参）与 `cli.py`（＋`--deploy-qmt` 透传）长期停留在工作区 M 态。
2. **已提交侧断裂**：origin/main 树内 `tests/test_delivery_*.py` 共 18 个，其中 **14 个** `import tests.fixtures.delivery`；而 `tests/fixtures/delivery/`（`__init__.py` 795 B／`env.py` 10,844 B／`main_db.py` 5,925 B／`crash_runner.py` 1,619 B）在 origin/main 树内**不存在** ⇒ 远端跑 delivery 族必 ImportError。
3. **机制缺口**：`.githooks/pre-push` 原仅两闸（铁律预算门 ＋ C7 声明闸），**不校验**待推文件集在 HEAD 树中的 import 闭包 ⇒「提交了导入者、没提交被引用模块」可无声过闸。
4. **复现判据**：跑 `python scripts/scan_untracked_dependency_gaps.py`（修前基线：引用缺口 15 处／2 簇）与 `python scripts/check_dependency_closure.py --base <base> --head <tip>`（修前对缺口窗口返回退出码 2）。

## 影响面

- **远端**：origin/main 上 14 个 delivery 测试必红；M5.2 件4 的 QMT 部署内核在远端完全不可用。
- **本地**：五件在工作区可用但未入库，任何「只提交导入者」的操作都会制造新的远端断裂（簇 A 属此类**潜在**断链；实测 `ddb1087~1` 的 orchestrator.py 树内容对 `qmt_deploy`／`deploy_qmt` 引用行数为 0，故此前未成为既成断裂）。
- **流程面**：暴露三处缺口 —— G1 入库单元按「件」而非「依赖闭包」切分；G2 push 门禁不校验 import 闭包；G3 未跟踪 .py 无盘点闸。

## 讨论

- **修复落点分层**：纯恢复型补提交两笔（`ddb1087` 五件套／`dbaaccf` fixtures 四件，.pyc 不入库）＋ 两个新增门禁工具（`scripts/check_dependency_closure.py` fail-closed 待推集闭包门 ＋ `.githooks/pre-push` 挂载；`scripts/scan_untracked_dependency_gaps.py` CI/周期扫描位，按用户裁定**不挂 pre-push** 以保持推路径快）。
- **白名单通道**：`scripts/dependency_closure_allowlist.json`（精确/通配/目录前缀）＋ 环境变量 `QS_DEP_CLOSURE_ALLOW`；缺脚本 ⇒ exit 9（门禁不可用即拒推，与铁律预算门同纪律）；已知可绕过面 `git push --no-verify`（须在回报中声明）。
- **BOM 坑（可复用）**：Python `path.read_text(encoding="utf-8")` 会保留文件首部 U+FEFF ⇒ `ast.parse` 抛 `SyntaxError`；闭包门/扫描器读源须用 `utf-8-sig` 或显式剥离 BOM，否则整轮扫描被单文件中止（本次已两处修补）。
- **验收口径**：脚本 `--self-test` 4/4 ＋ 3/3；**独立 oracle（自建合成 git 仓）11/11**；hook 挂载块隔离实测 `sh -n` rc=0、正例 rc=0、合成负例 rc=9（打印缺口明细）、合成正例 rc=0。
- **编排披露**：(b)(d) 两脚本由 ZCode-GLM 委派生成，goal 超时（>1800s）后**已回退 DSH 模型执行**（产物已落盘，未重跑委派，改以独立 oracle 复核）；产物含外部生成代码，业务逻辑与边界分支仍需人工复核。
- **后续项**：Tab 懒加载降级按用户裁定**本轮不实施**（内核落地即修复，懒加载属降级打磨）；G1「按依赖闭包切分入库单元」的制度化待用户裁定。
- **跨平台大小写语义坑（可复用）**：Windows 工作区大小写不敏感，`Path.is_file()` 会把 `Env.py` 误判为 `env.py` 存在 ⇒ 闭包门产出 **13 条假缺口**（误阻断合法推送）；而 Linux CI 大小写敏感 ⇒ 真断链反被掩盖。修复＝逐段以 `os.scandir` 取**磁盘真实条目名**比对（`Path.name` 是词法串，不反映磁盘真实大小写，故不可用）。门禁类工具凡判「文件是否存在」者均须跨平台对齐。
- **白名单落盘与匹配面**：`scripts/dependency_closure_allowlist.json` 落 3 条**模块名全串**精确匹配（`...workers`／`...skin`／`..daemon_process` 三个归档备份副本的越界相对导入），附 `_readme`／`_matching`／`_basis`；**不放行任何通配**。匹配面＝「目标路径 ∪ 模块名」——逃逸相对导入的 target 为 None，故只能用模块名全串表达；若要按导入方文件族豁免，须扩展匹配面（门语义变更，另行裁定）。
- **全树核口径**：空树基线不能用 `git rev-parse --verify <empty-tree>^{commit}`（会报 `expected commit type, but the object dereferences to tree type`），须用 `git commit-tree <empty-tree> -m ...` 造**悬空**提交（不动任何 ref）；本机全树 2611 文件耗时约 50 s。
- **CI 接线**：`.github/workflows/dependency-closure-scan.yml`（PR(main)／push(main)／每周一 cron／手动）＝变更集闭包核 ＋ 全树闭包核 ＋ 未跟踪扫描，与本地 `.githooks/pre-push` 闭包门同源同判据；CI 检出树内无未跟踪文件 ⇒ 未跟踪扫描在 CI 内为**脚本冒烟**，其实质告警在本地/周期位。
- **验收口径增补**：独立 oracle 增列大小写语义 4 用例——O12（属性导入大写，不报缺口）、O14（真断链，exit 2 且 target 精确）、O15（扫描器大小写不判缺口）均 PASS；O13（`from pkg import Missing` 期望报缺口）判定为**我方 oracle 期望口径错误**——本门范围是模块级闭包，属性级存在性不在范围内，已据此更正期望，非脚本缺陷。
