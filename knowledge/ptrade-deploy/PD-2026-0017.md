## 讨论

- **A 的关键设计**：代理取价必须与 `order_target_value` 的股数换算价**同源**（`_qs_px_exec`，`source_import.py:989`），否则「目标数量」与「下单金额」自相矛盾；代理**必须无状态**（默认参数在 def 时求值一次并共享 ⇒ 禁缓存价格）。
- **P4 等价性零影响的结构性论证**：`equiv.py:120-122` 形态一把包装签名**重写**为 `(context, data)` 且 `defaults=[]` ⇒ 产物侧默认值改写被归一化抹除；`run_daily` 注册语句（MOUNT 标记）在 P4 **整条剔除**（形态二 `_droppable`）⇒ 注册目标改名无影响；新增 `DATA_PROXY`/`DAILY_HOOK` 块**整体剔除**（与 `GUARD`/`PERSIST` 同级）。
- **C 的零漂移保证**：只加登记，**不改订单序列**（`_qs_split_order` 未动）、**不改返回值**（仍 `_ids[-1]`）⇒ 双端订单序列逐笔一致的同构约束不被破坏；策略审计函数对委托字段访问全部 `.get()`，框架代填最小 dict 安全。
- **D 的不可逆闸门**：撤单为外部不可逆动作 ⇒ 默认 `false`，显式开启须用户单独确认；日戳不可得时**跳过判定**（宁可不告警，绝不误撤）。
- **判型**：A 新增能力型 / B 纯恢复型 / C 纯恢复型 / D 新增能力型（撤单默认关闭 ⇒ 零行为漂移）。
- **反哺可机读**：模板改动 + `gates.py` 产物断言 + `check_deploy_closedloop.py` 产物级巡检 ⇒ 下次转换若缺代理即被 P5 拦下（知识库真实触发）。
- **共享核心文件**：`source_import.py` 属铁律 10 ⇒ 写前快照 + 精确 add + wrapper_hash 变更须同 commit 追认 `check_fund_matrix.py --check --reverify` 矩阵哈希。
- **E′（③实施期新增发现，本族首现）**：幂等台账 `orders_done` 存于 `g.state` 并随 pickle 跨日持久化，而护栏全文**只 append 不清空** ⇒ 部署次日首个 `[security, side]` 命中即被误判「当日重复下单」**拦死全量下单**，且比 A 更隐蔽（A 只打一类策略，E′ 打所有启用幂等护栏的产物）。修法取「恢复后清空」而非「落盘清空」——同时覆盖重启场景（重启后无法判定当日是否已下过，保守清空优于锁死）；代价是重启后同一 (标的, 方向) 可再下一次，属可接受的弱化（幂等本为防 6 秒同步窗口内的重复提交）。
- **E（时点自检，未进批）**：策略自检常量（15:00）与挂载时点（14:50）的表述差异，不影响下单执行；框架无可靠手段识别「哪个字面量是调度自检时点」⇒ 零越权登记，待专门轮次以「档位时点暴露为模块级常量」消歧。
- **可复用教训·假信号留痕（2026-11-02 实证，随 R4 沉淀）**：验收复验时从产物源码抽取策略取价函数做实测，`safe_float(1.777)` 恒返 `0.0`，一度误判 A「未修好」。真因是**抽取沙箱缺依赖**——`safe_float` 内 `np.isnan` 抛 NameError 后被 `except → default_value` 静默吞掉，产出 0.0 假结论。**判据**：①凡「桩/沙箱内跑原件」的验证，必须同时打印被测函数**依赖的直接读数**（如 `safe_float(1.777)`）作为沙箱自检，否则「静默 0.0/None」会被误读为被测缺陷；②`except Exception: return default` 这类兜底会把「环境缺失」与「业务失败」压成同一观测值，故此类函数的测试必须能区分二者（本例以依赖直读区分）；③假信号一旦识别，须与真缺陷一样留痕，避免下轮重踩同坑。
- **★ 验证点设计判据·「次日首单」类断言必须先验「该日是否存在下单尝试」（2026-11-06 实证订正，随 R4 沉淀）**：E′ 类缺陷的验收点常被写成「部署次日首单不被拦」，但**该断言是否成立取决于策略的实际调度面**——若次日不在任何下单路径上，断言会**空真**（无下单 ⇒ 无拦截 ⇒ 判 PASS），构成假通过。本批订正过程：E′ 拦截只在「当天存在下单尝试」时才可能触达，故须先逐策略核下单面（四象限＝月度首日＋**每日**止损/风控；F-Score＝**仅**月度首日；全球资产轮动＝**仅**首次建仓＋**126 策略日**动态调仓）⇒「次日」若无下单尝试即不可达；再叠加**判别力**要求：幂等台账键为 `(security, side)`，跨日**同标的同方向**才碰撞（买入次日止损卖出方向相反 ⇒ 天然不碰撞 ⇒ 即便修复失效也不被拦 ⇒ 假通过）。**硬动作**：①验收点写「某日某断言」前，先从产物代码核该日**是否在调度面内**；②断言须具**判别力**（存在「修复失效即必失败」的对照样本），否则明示「本次不具判别力」而非判 PASS；③空真断言（无事件即通过）一律不得作为验收证据。本批据此把平台侧验证点由「11-04」订正为 **2026-12-01**（下一个必然下单日），并要求同时确认「同标的同方向」碰撞是否存在。
- **★ 平台侧运行痕迹的取证边界（2026-11-06 实证）**：PTrade 策略运行于**券商服务器侧**（初始化日志含「当前服务器配置为…交易时间段服务器重启后，执行拉起本交易操作」），本机 PTrade 客户端（`D:\Ptrade\ptrade_UAT`）**开合不影响 14:50 触发**；本机客户端日志止于 09:49:53（`OnClosed 客户端程序退出`）、`Users/` 下无 `*_state.pkl`（无 `after_trading_end` 落盘）⇒ **本机无痕迹 ≠ 当日未跑**。硬动作：①判「某日是否真跑过」不得以本机痕迹缺失为据（反向亦然）；②若策略在券商侧运行，验收取证源固定为平台侧【日志】＋【委托】＋【普通持仓】三表，须由用户回传；③本地等价路径（`python -m quantstudio.backtest.run_ptrade_strategy <产物> <起> <止> --profile minute-bar-v1`）可作**机理补强**，但**不得替代平台侧验收**（撮合/账户/托管环境不可本地等价）。
