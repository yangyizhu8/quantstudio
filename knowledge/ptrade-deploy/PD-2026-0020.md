### D1（2026-11-10 · 判据）按代码推断行为，**必须读到关键分支出处**，不能只看调用点

**事由（我方两次误判，均在同一轮内被自己推翻）**：

| 序 | 我方判定 | 推翻方式 | 真实原因 |
|---|---|---|---|
| 1 | 「`portfolio.cash` 是总现金，不是可用资金」 | ②审 zcode 指出 + 我方查 Context7 逐字：「Current available funds」 | 未先查平台文档语义就按实跑读数反推 |
| 2 | 「**G1（P0）**：`order_value` 卖出会经 `_qs_cash_budget` ⇒ fail-closed 返 0 ⇒ **阻断卖出**」 | 我方预研读 `_qs_split_order` **首行**：`if … or value <= 0: return [], 0` ⇒ 卖出压根不进拆单/预算链路 | 只看了 `order_value` 的**调用点**（L1485）与 `if not orders:` 分支，**没读被调函数的首个 return 条件** |

**判据（可复用）**：

1. 凡断言「A 会因 B 而被阻断/钳制/跳过」时，**必须沿调用链读到被调函数的第一个决定分支**（首行 return / 首个 if），而不是停在调用点；
2. 特别地，**早退（early-return）与哨兵值（`<=0`、`None`、`[]`）是第一优先级审查对象**——它们往往使后续全部逻辑对其输入类别不生效；
3. 断言「会阻断」之前，先写出**该输入类别在链路首个分支出处的结果**（本例：`value=-3200 → _qs_split_order 返回 [] → 走 value_orig → 卖出正常`）；
4. 定性分级（P0/P1/P2）**须在 1–3 完成之后**再给——本次先给了 P0「安全底线」，读码后降为 P2「告警噪声」，属**定级早于取证**；
5. 反向教训：zcode 给的原则（「零预算只阻断买入、不阻断卖出」）**本身正确**，我方将其**过度解读为「必须改码」**——原则→实现的映射仍需读码落实。

**落点**：本条同时适用于 PD 族其他条目的事故归因；与「桩/沙箱验证必须带依赖直读自检」同族（都是「**观测点选错导致假结论**」）。
