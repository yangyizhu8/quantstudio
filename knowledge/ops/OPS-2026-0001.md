## 复现步骤

1. 用真实 BacktestWorker（非直调 run_backtest）跑首板1进2 的 5 日窗 2026-03-02~2026-03-06。
2. 该链路实测 wall 约 300.4s（直调）/ 6 分钟以上（经 Worker），超过单次工具调用 600s 上限。
3. 工具返回超时；我按「超时=卡死」处理并 kill，进程被杀（第一次错误：只看时长）。
4. 反证：被 kill 前日志仍在推进——
   - 03:32:30 QS_BARS_CACHE_PROGRESS table=stock_daily loaded=2/2 elapsed=2.2s
   - 03:33:26 买入 600635.SS
   - 03:33:28 QS_REBALANCE_AUDIT date=2026-03-04 selected=1 tradable=1 sell_submitted=0 buy_submitted=1
5. 我据此把判据改成「看有没有新日志」——这是第二次错误：仍是单项一票（见下节双向造假）。

## 影响面

| 维度 | 影响 |
|---|---|
| 直接 | 误杀健康进程，浪费 6 分钟以上计算 |
| 证据 | 被杀进程产物不完整，该窗口读数整段作废 |
| 后续 | 若据此判「该链路有问题」会引入错误的框架债方向（铁律 08 禁止按猜测方向改码） |
| 判据本身 | 单项一票的判据会被下一次同类事件推翻，无法沉淀成稳定规则 |

## 讨论：为什么「只看日志」仍是单项一票

### 双向都可造假

| 观测 | 假信号 | 机理 |
|---|---|---|
| **有新日志** | **假活** | 循环/心跳/重试日志持续刷行，但业务未推进（如反复报同一条 QS_DIAG、周期性 progress 行） |
| **无新日志** | **假死** | 纯计算阶段（大循环、内存聚合、导出）本就不写日志；批处理也可能缓冲未 flush |
| 产物目录有文件 | **假活** | 旧文件或上一轮残留；须看**是否增长/新增**，不是「有没有」 |
| CPU 不涨 | **假死误判** | 阻塞在数据库锁/IO 等待时 CPU 不涨，但进程未死 |
| CPU 在涨 | **假活** | 空转重试、死循环同样吃 CPU |

### 多证据诊断表（替代单项一票）

| 证据项 | 判「在推进」的信号 | 判「疑似卡住」的信号 |
|---|---|---|
| 日志**语义** | 出现**新标的/新日期/新阶段**（非重复行） | 只有重复的循环行，无新实体 |
| 日志**行数与心率** | 稳定持续的实质行 | 突然停止且无收尾行 |
| 产物目录**增长** | 文件新增或大小递增 | 长时间零变化 |
| 进程 **CPU 时间**（累计值，非百分比） | 累计 CPU 秒数增长 | 累计值长时间不变 |
| 数据库活动 | 连接存活、有查询/写入在进行 | 连接挂起无查询 |
| Worker 进度回调 | progress 内容有实质变化 | 回调停在同一百分比 |

### 判定规则（不用单项一票）

1. **任一项出现「实质推进」⇒ 证伪卡住**（不 kill）。
2. **多项同时无实质活动 ⇒ 判「疑似卡住」**，但**仍不直接 kill**：先做一次**低风险探针**（如读进程 CPU 累计值、查 DB 连接），仍无活动再处置。
3. **与已知正常基线对照**比绝对阈值可靠：同链路同窗口此前跑多久、日志长什么样，基线内不判卡。
4. **禁止以「超时」本身作为卡住证据**（超时只是我的观测边界，见 OPS-2026-0001 起源事件）。

### 同族归并

本条与以下同属「把观测装置的边界误读为被测对象的缺陷」：
- Select-Object -First N 提前关管道，导致假失败（已入全局铁律）
- grep 0 命中，误判「对象不存在」（已在记忆）

可执行判据：判「卡住」用**多证据交叉**，不是换一个单项指标再断言一遍。
