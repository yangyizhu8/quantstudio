1. 副本库（`D:\qs_g6_replica_20261110`，45,122,324 行观测）
2. `QSS_QFQ_OBS_INCREMENTAL=0` 跑 120 条观测 → wall ≈ 0.066s
3. 恢复 aux 至同起点（恢复法）
4. `QS_QFQ_OBS_INCREMENTAL=1` 跑同 120 条 → wall ≈ 74.947s
5. `EXPLAIN QUERY PLAN` 可见 `_inc_fetch_last` 外层为 `SCAN qfq_factor_observation`（全表），非 `SEARCH ... USING PRIMARY KEY`

## 讨论

- **测量的两种污染**：①计时窗口包含了测量辅助代码（本次 `_dump_last`）；②一次 SQL 的 EXPLAIN 计划未验证就假定「WHERE asset_type=? 已走 PK 前缀」——PK 前缀只在**无 JOIN 干扰**时有效，JOIN 外层必须与子查询同界。
- **等价性与性能可分离**：本次差分布 115,070 键全 0 ⇒ 语义正确；慢是纯性能问题，可单独修。

### L3 的可复用判据（新增，最重要）

**凡「两段对比」型性能测量（A 段跑完 → 恢复/拷贝 → B 段跑），若中途涉及大文件拷贝（GB 级），
A 与 B 的 OS 页缓存状态必然不同 ⇒ B 段的 wall 含冷缓存代价，与 A 段不可直接比。**

硬动作：
1. 对比型测量**必须**在同一缓存状态下跑两段，或**两段都先做一次预热跑**（丢弃其读数）；
2. 报告 wall 时必须注明「该段跑之前是否发生过 ≥1 GB 的文件拷贝/恢复」；
3. 出现「同操作跨次差 10× 以上」时，**先怀疑缓存/IO 状态，再怀疑代码**（与 L1 同类，但 L1 是测量代码、L3 是测量环境）。

### 结论（收口）

- **F1 是独立成立的缺陷修复**（L2 已修，183× 提升，纯等价四判据绿）⇒ 保留，`QS_QFQ_OBS_INCREMENTAL` **继续默认关**；
- **A4「≤0.5 s」不可达不是因为代码慢，而是原测法把冷缓存代价算进了 new 段** ⇒ A4 阈值应在新测法（同缓存态 / 双段预热）下重测，**本轮按裁定「结构性 ⇒ 收口」，不追**；
- 若将来要重开：先做「同缓存态对照」（两次都预热）再谈阈值。
