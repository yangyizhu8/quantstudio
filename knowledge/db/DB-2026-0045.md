## 复现步骤

1. 取一含「当前值 + 历史回执」的文档（如证据件：正文引当前 hash，附录记历次运行的 verdict 回执）。
2. 对该文档做全局 `s.replace(OLD, NEW)`，OLD=被替换的旧值、NEW=新值。
3. 观察：正文的当前值被正确更新；**历史回执块里的同一字符串也被一并改成了 NEW**。
4. 断言「旧运行当时读的是 NEW」——该断言**不成立**，因旧回执写入时 NEW 尚不存在。

判定：若历史回执块的 hash 与产生它的那次运行的 `verdict.txt` 实测值不一致 ⇒ 命中。

## 影响面

- **性质**：不是「显示错误」，而是**伪造历史**——把从未发生的运行结果写成已发生。
- **受害面**：审计链条（谁在何时读了哪一版）。一旦历史回执被改，复算基线即失效，且失效是**静默的**（文件看起来完整、hash 也自洽）。
- **典型触发场景**：多处 hash 批量同步（本轮实测：同步四处 hash 时一次性改掉了写在呈审件 §4.3 里的 11-17 旧回执）。
- **不触发但更危险**：若历史回执与当前值本就不同（如已用不同模板），替换不会命中——「没出错」的表象让人以为方法安全。

## 讨论

**为什么容易被当成正确做法**：批量同步 hash 的动机是「保持一致」，而历史回执里的旧 hash 与正文当前 hash **字面同源**，看起来就是「没同步干净」，于是被顺手改掉——动机完全正当，后果却是伪造。

**与同族判据的关系**：
- 与 `af4666d0`（判据件须自证）同族：**替换动作本身也要自证**——替换后须能说出「我改了几处、每处属于哪个语义分区」。
- 与 `8d4636f0`（存在性×同一性双证）同族：历史值的同一性以**产生它的那次运行的回执**为准，不以当前文档里的字符串为准。

**正确做法**：
1. 批量替换前先枚举所有命中位置，逐条判定它属于「当前值区」还是「历史记录区」；
2. 历史记录区**只增不改**：补新行，不覆盖旧行；
3. 若确需修正历史记录，须另开一次显式操作并说明依据（如原记录本身有误），不得借「同步 hash」之名顺手改。

**本轮实证**：`docs/evidence/duckdb-1.5-upgrade-window-evidence.md` §7.65.6 第 3 项；发现方式是交叉核对时察觉呈审件 §4.3 回执与 §4.4 所记 run root 自相矛盾，**不是靠单看某一行发现的**。
