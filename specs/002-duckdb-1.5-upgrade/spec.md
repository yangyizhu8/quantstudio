# Feature Specification: duckdb 首跳升级（1.4.5 → 1.5.6）＋ PT-01 覆盖链 PK 保护并行轨

**Created**: 2026-10-29 | **Status**: In Progress（检查点 A 已由总调度批准；实施进行中）| **Input**: 会话节点⑲ 开工提示词（duckdb 数据库升级执行会话）+ decision v9.1（go，范围限首跳 1.5.6）+ 总调度六裁落地（2026-10-29）

## 背景与目标（Why）

数据主库所在引擎版本被**声明面 3 处 + 门禁面 3 处 + 运行环境**三重锁定在 1.4.5；1.4 线于 **2026-11-17 EOL**，1.5 支持至 2027-03。首跳升级的唯一目的是**维持受支持状态**，不是修复缺陷：

- 已知缺陷（非唯一 ART 索引删除失败）在 1.5.x **全线仍在**（含目标版本 1.5.6），仅由「静默丢索引」变为「显式 FATAL」；本项目对该缺陷的暴露面为 0（非唯一 ART = 0；41 个主键经三臂验证不丢）。
- 版本间**无存储格式门**（写旧库仍为旧格式、新建库同格式、旧版可读），故首跳**不重建库、不转格式**。
- 09 月的历史 FATAL 属**另一机制**（passthrough 覆盖链 `DROP+RENAME`），不能由本次「零暴露」结案：该链在三个版本上均**静默清空目标表主键**（观测值 1→0），构成独立的数据完整性缺陷，与升级同批规划、独立修复。

## User Scenarios & Testing

### User Story 1 - 升级后进程能正常启动并读写（Priority: P1）

运维按批次把依赖版本与代码一起更新后，GUI 与常驻采集进程（含由系统计划任务拉起的形态）都能通过版本门启动，正常读写真库。

**Why this priority**: 门槛放错会直接导致全量进程拒启（历史已发生「声明与运行环境脱钩」事故），这是升级是否可用的第一判据。

**Independent Test**: 在同一台机上以旧/新两种版本各启动一次三入口（含计划任务拉起形态），观察「启动成功 / 拒启」与退出码，即可独立验证本条。

**Acceptance Scenarios**:

1. **Given** 运行环境为放行集合内的版本 **When** 启动 GUI 或常驻采集进程 **Then** 进程正常启动，无拒启提示
2. **Given** 运行环境为放行集合外的版本 **When** 启动任一入口 **Then** 进程以固定退出码拒启并给出可执行的修复指引
3. **Given** 版本号无法解析或依赖缺失 **When** 启动入口 **Then** 判为不合规并拒启（fail-closed，不静默放行）
4. **Given** 显式放行开关被置位 **When** 启动入口 **Then** 放行且留醒目告警（语义与升级前一致）

### User Story 2 - 声明、门禁、测试对同一版本集判定一致（Priority: P1）

同一版本字符串在依赖声明、启动门禁、双平台运维止损脚本、测试契约中得到**同一个判定结果**，不存在「某处放行、另一处拒绝」。

**Why this priority**: 六处口径不一致正是历史事故的成因；一致性是升级能否被信任的结构前提。

**Independent Test**: 用一组版本字符串（含边界）分别喂给**三个判定面**（启动门禁 / 双平台运维止损脚本 / 测试契约），比较结果矩阵是否逐项一致；声明面是**单版本 pin 固定**，只核对「是否落于集合内」。

**Acceptance Scenarios**:

1. **Given** 放行集合 = `{1.4.5 ≤ x < 1.5} ∪ {x == 1.5.6}` **When** 以 1.4.5 / 1.4.9 / 1.5.6 测试 **Then** 三个判定面均为放行，且声明面版本锁定落于集合内
2. **Given** 同一集合 **When** 以 1.4.4 / 1.5.0 / 1.5.5 / 1.6.0 / 2.0.1 / 2.1 / 无法解析 测试 **Then** 三个判定面均为拒绝
3. **Given** 运维止损脚本在无项目内包的极简路径下运行 **When** 执行版本判定 **Then** 判定结果与门禁一致且退出码可被脚本消费

### User Story 3 - 出问题能在窗口内回退（Priority: P2）

升级后发现异常时，能在同一维护窗口内把运行环境降回 1.4.5，旧版本能打开现库并正常读取，门禁同步回到可放行 1.4.5 的状态。

**Why this priority**: 升级是低风险但非零风险动作；无回退的升级不可执行。

**Independent Test**: 在演练环境执行一次降版 + 旧版打开现库 + 读取抽样表，记录读数。

**Acceptance Scenarios**:

1. **Given** 已升级且判定需回退 **When** 执行降版并按记录步骤打开现库 **Then** 旧版本可读、抽样查询返回结果、无格式不兼容报错
2. **Given** 回退完成 **When** 重新启动三入口 **Then** 1.4.5 被放行、1.5.6 被放行（集合不变），无拒启
3. **Given** 回退过程中库状态异常（WAL 残留/无法收敛） **When** 走既有 WAL 收敛入口处置 **Then** 处置后库可正常打开

### User Story 4 - 覆盖链不再静默销毁主键（Priority: P2）

passthrough 全量覆盖执行后，目标表的主键**仍然存在**；若配置让覆盖链指向带主键的表，静态检查在运行前就拦下。

**Why this priority**: 每轮覆盖静默清空主键且不告警，会连带使冲突探测失效、后续写可能产生重复行——比 FATAL 更隐蔽。

**Independent Test**: 在合成库对「带主键表」执行一次覆盖链，比对覆盖前后的主键存在性；再用一份故意指向带主键表的配置跑静态检查。

**Acceptance Scenarios**:

1. **Given** 目标表带主键 **When** 执行全量覆盖 **Then** 覆盖后主键仍存在（1→1），行数与内容符合预期
2. **Given** 覆盖链改道（保留表对象方式 或 重建同构约束方式） **When** 同一数据集分别经旧/新路径写入 **Then** 列集、行数、内容哈希逐位一致
3. **Given** 配置把 passthrough 任务指向带主键的表 **When** 运行静态检查 **Then** 检查报错并指出该任务（负向用例必拦）
4. **Given** 现有全部 passthrough 任务（与带主键表交集为空） **When** 运行静态检查 **Then** 零告警（前瞻守卫不误伤）

### User Story 5 - 治理条文与知识库不再自相矛盾（Priority: P3）

项目治理条文从「不经手升级数据库版本」改为「放行集合 + 升级判据 + 到期复核装置」，知识库与工作纪律中过时的钉版表述同步更正。

**Why this priority**: 条文不改，本次升级即处于违规状态；复核装置不改，下一次 EOL 仍会重演「到期才发现」。

**Independent Test**: 检查治理条文三要素齐备、全仓不再残留旧钉版表述、复核装置可被触发一次。

**Acceptance Scenarios**:

1. **Given** 条文已更新 **When** 检索放行集合、升级判据（90/60/30 三段式）、到期复核装置 **Then** 三要素均可定位
2. **Given** 已升级 **When** 全仓检索「版本门必须 1.4.x」类旧表述 **Then** 零命中
3. **Given** 上游发布新补丁或缺陷单关闭 **When** 复核装置被触发 **Then** 产生一条待办复核提醒（可被审计）

### User Story 6 - 客户能一次自检（Priority: P3）

客户在同一批次更新代码与依赖后，运行一条自检命令即可看到「版本号 + 门禁 PASS/FAIL」，不需要运维介入解读。

**Why this priority**: 代码与依赖不同批更新会导致拒启；自检把该风险前置到客户侧一次点击。

**Independent Test**: 在干净环境执行自检命令，观察输出与退出码。

**Acceptance Scenarios**:

1. **Given** 版本在放行集合内 **When** 运行自检命令 **Then** 打印版本号与 PASS，退出码为成功
2. **Given** 版本不在集合内 **When** 运行自检命令 **Then** 打印版本号与 FAIL 及一句修复指引，退出码为失败
3. **Given** 收到通知的客户 **When** 按通知步骤操作 **Then** 无需任何额外参数即可完成自检

### Edge Cases

- **版本字符串畸形（严格三段口径 · 2026-10-29 H1 裁定）**：只有**恰三段整数**才是可参与集合判定的形态。带预发布/构建后缀（`1.5.6.dev0`、`1.5.6.post1`）与两段式（`1.5`、`2.1`）**可识别但不合规** ⇒ 判 `FAIL`（退出码 1）；完全无法解析（`unknown`、`1.5.6rc1`、空串）⇒ 判 `ERROR`（退出码 2）。二者一律 fail-closed 拒绝，不按前缀猜测。
- **集合下界外**：`1.4.4` 必须拒（下界为 1.4.5 含端点），契约专门覆盖。
- **事故版本**：`1.5.5` 必须拒（该版本为 09 月事故的实证版本），契约专门覆盖。
- **同机混版并存**：机上仍存在一个不合规的 1.5.3 环境且被别的子系统以只读方式使用 → 本期不升级它、登记为只读消费者；一旦它尝试写库，启动门禁必须拒绝。
- **计划任务形态拉起**：窗口末以计划任务方式启动常驻进程；若任务定义里携带了显式放行开关，须在窗口前核查并纠正（否则等于绕过门禁）。
- **窗口内并发写者**：窗口期间任何会初始化写者/建表的入口（GUI 任务、单次采集、离线工具）必须被禁止；发现他线进程占用则窗口顺延并登记占用声明。
- **库被占用 / WAL 残留**：按既有收敛入口处置，禁止手工删除 WAL 文件；早退不等于已收敛。
- **意外格式升级**：若升级后旧版本无法打开现库（与预期相反），立即触发回退流程并登记为异常读数。
- **客户侧只更新代码未更新依赖**：表现为拒启；通知内的自检命令须能一眼区分「版本不对」与「门禁未过」。

## Requirements

### Functional Requirements

**放行口径与判定**

- **FR-001**: 系统 MUST 以单一放行集合为准：`1.4.5 ≤ x < 1.5` **或** `x == 1.5.6`；集合外版本一律拒绝。
- **FR-002**: 判定 MUST 为 fail-closed——依赖不可导入、版本串不可解析、非严格三段形态（段数不足或带预发布/构建后缀）一律判不合规；**分层 MUST 可区分**：非严格形态判 `FAIL`（退出码 1），不可解析判 `ERROR`（退出码 2）。
- **FR-003**: 系统 MUST 提供**唯一判定源**（单一策略模块 + 一个机器可读的判定结果/退出码），供启动门禁、双平台运维止损脚本、测试契约共同引用；各消费面**不得各自维护第二份规则**；判定源 MUST 可被双平台脚本**单文件直调**（不依赖可导入的项目包）。
- **FR-004**: 依赖声明面 MUST 与判定源同批更新并保持同义，不得出现「声明已放宽、门禁未放宽」或反向；因依赖清单的版本约束语法**无法表达「区间 ∪ 精确点」并集**（单行只能表达单区间或单版本），声明面 MUST 采用**单版本精确锁定（目标版本）＋ 注释承载放行集合**的形式承载放行语义。
- **FR-005**: 显式放行开关 MUST 保留原有语义（仅显式置值时放行、且留醒目告警），其存在不得弱化为默认路径。

**门禁覆盖面**

- **FR-006**: 启动门禁 MUST 覆盖**三入口**：桌面 GUI、常驻采集进程、GUI 拉起的子进程；其中常驻采集进程 MUST 同时覆盖**模块形态与直启形态**。各入口的正向（放行）与反向（拒启）行为一致；**替身触发证据与真实进程触发证据分别记读数**（真实进程读数在停服窗内取得）。
- **FR-007**: 拒启 MUST 使用固定退出码并输出可执行修复指引（含「改用合规解释器」「降版」「显式放行」三类出路）。
- **FR-008**: 双平台运维止损脚本 MUST 与判定源同源；其回归脚本 MUST 全绿（改脚本不带出回归）。
- **FR-009**: 测试契约 MUST 覆盖放行点 1.4.5 / 1.5.6 与拒绝点 2.0.1 / 2.1，**并覆盖边界** 1.4.4（集合下界外）与 1.5.5（事故版本）；契约 MUST 引用判定源而非复制规则表。

**治理与说明**

- **FR-010**: 治理条文 MUST 含三要素：①放行集合 ②升级判据（距 EOL 90 天出方案 / 60 天进实施 / 30 天完成或书面接受风险）③到期复核装置（EOL 日历守护 + 缺陷单关闭或新补丁发布后自动落复核提醒）。
- **FR-011**: 治理条文中与本次授权直接冲突的表述 MUST 被**替换**（不是追加例外条款）。
- **FR-012**: 依赖缺陷说明 MUST 更正为：1.5.x 全线（含 1.5.6）该缺陷仍在，仅由静默变为 FATAL，1.5.6 未修复。
- **FR-013**: 工作纪律/知识库中「版本门必须 1.4.x」类旧表述 MUST 同步更正；相关改动只提供 diff 与提交信息草稿，经独立审核与批准后落码。

**升级执行与验证**

- **FR-014**: 升级 MUST 在单次维护窗口内完成，**不重建库、不转格式、不落新存储版本**；窗口内禁止任何会初始化写者/建表的入口（`create_writer` / `init_schema` 等）；窗口内的**验证性写入 MUST 落独立临时库或独立文件**，不得写主库既有表、不得改主库 schema。
- **FR-015**: 升级后 MUST 完成六项冒烟：①读写 ②时区（Asia/Shanghai）时间戳往返 ③重叠批次 upsert（冲突探测生效） ④分片与主键点查 ⑤存储版本回显符合上限约束（**≤68**，由文件头只读读数取得：`storage_version = uint32 LE @12`，magic `DUCK`@8，创建版本串 @52）⑥门禁三入口正反向；其中 ①②③ 的写入落独立临时库/独立文件，④ 对主库只读点查。
- **FR-016**: 回退 MUST 可执行并留读数：降版命令、旧版打开现库、抽样读取、门禁状态复核。
- **FR-017**: 客户通知 MUST 包含「代码与依赖同批升级」的明确要求（否则拒启）与一条自检命令；措辞与下发时点经审批，下发不晚于 11-17。
- **FR-018**: 观测面 MUST 采集：窗口实测分钟、冒烟通过数、缺陷关键词计数、WAL 体积、采集进程首轮耗时、升级前后各一次基线；**升级后首周**缺陷关键词 MUST 纳入每日哨兵。
- **FR-019**: 执行前置判断 MUST 按**届时实态**（进程是否存在、计划任务形态、库尺寸、WAL 状态）取值，不得以历史快照代替。
- **FR-020**: 里程碑 MUST 按日历推进：方案成文 11-02（不可压缩）→ 独立审核 11-02～11-03 → 实施 ≤11-08 → 验收 ≤11-15 → 通知 ≤11-17。

**PT-01 并行轨（覆盖链）**

- **FR-021**: 覆盖链 MUST 保证覆盖后目标表主键存在性不变（1→1）；可采「保留表对象（截断/删行后插入）」或「重建同构约束」任一方向，改道方式由 plan 定。
- **FR-022**: 覆盖链改动 MUST 通过三项验收：全量回归零新增失败、同一数据集改道前后双写逐位一致（列集/行数/内容哈希）、既有 passthrough 语义不变。
- **FR-023**: 覆盖链相关改动 MUST 可在单文件内回退；主键巡检守卫 MUST 已就绪并接入每日哨兵（先行能力，不属本期新增缺陷面）。
- **FR-024**: runbook MUST 采认「备而不用」：文本保留、不要求演练；段 A 条件补齐的未定谳项（解释 C 保留）MUST 写入 runbook 章节。
- **FR-025**: 静态守卫 MUST 加入「passthrough 任务不得指向带主键的表」，且负向用例必拦、现状任务集零告警。

**升级风险计量**

- **FR-026**: 唯一落在本库引擎上的批量写入路径 MUST 在**真实批次规模**下量化一次耗时，判据为「新版本 ≤ 2 倍旧版本且绝对值 ≤ 5 秒」；超阈 MUST 在实施窗内列入风险项并在通知中提示；该项 MUST 在窗口外完成（≤11-04）。

## Success Criteria

- **SC-001**: **三个判定面**（启动门禁 / 双平台运维脚本 / 测试契约）对同一组版本字符串的判定结果**逐项一致率 100%**；且依赖声明面的版本锁定**落于放行集合内**。
- **SC-002**: 六项冒烟一次执行全通过（6/6），且每项有读数可查。

## Assumptions

- 版本号按「**恰三段整数**」解析（严格口径）；带预发布/构建后缀者**不作名义三段折叠**（`1.5.6.dev0` ≠ 1.5.6，判不合规）；无法解析即拒（fail-closed）。
- 现存 1.4.5 解释器保留在位，作为回退位，不在本期内退役。
- 主库不改结构、不转格式；首跳后新库仍为旧存储版本（≤ 上限）。
