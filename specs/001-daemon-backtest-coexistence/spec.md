# Feature Specification: 常驻采集与回测共存（回测前停采集 · 停止后由用户决定恢复）

**Created**: 2026-10-27 | **Status**: Draft（2026-10-27 口径变更：自动恢复 → 手动重启）

**Input**: 用户原文——「常驻采集开启时用户应能直接发起回测，无需手动停采集。回测期间采集让路（不发起新采集轮），撞上正在运行的采集轮则在任务边界等待并显示真实等待读数、可取消；回测成功/失败/取消后采集必须自动恢复（fail-safe：宁可恢复采集）。任何拿不到库访问的情形必须显式拒绝或继续等待，禁止空数据静默跑完。不做真并发、不读副本、不改 duckdb 版本；回测数据允许缺当日最新。验收：免手动停采集成功率、自动恢复率、空数据回测为 0、与"手动停采集后同参回测"结果逐位一致。」

**口径变更（2026-10-27 用户裁定，优先级高于上文"自动恢复"表述）**：

> 回测停止采集后，**采集保持停止**；PyQt 按钮切到「未开启」，由用户手动点击开启；命令行同样需用户重新执行启动命令。**系统不得在回测结束后自动继续拉取**——何时恢复由用户决定。

因此本文以「**回测前停采集 → 回测 → 保持停止等待用户启动**」为准；原 fail-safe「宁可恢复采集」语义作废。

> 前置依据：`.specify/assessments/daemon-backtest-coexistence/`（intake → research → problem → concept → decision，verdict = **go**）。

## User Scenarios & Testing

### User Story 1 - 开着采集直接跑回测，跑完采集保持停止、由我决定何时恢复 (Priority: P1)

策略研发者在图形界面开着「常驻增量采集」的状态下直接发起回测，不必先手动点停。系统自动请求采集优雅停止（等当前任务到边界，超时则在任务内单元边界中断），等到采集进程真的退出后，回测才开始。回测结束后**采集不会自己回来**：界面按钮显示「未开启」，并明确提示「采集已因回测停止，请手动启动」，用户想什么时候恢复就什么时候恢复。

**Why this priority**: 这是本需求的核心价值与本次口径变更的落点——既免除手动停采集的麻烦，又不在回测结束后擅自消耗资源。

**Independent Test**: 开启常驻采集，直接点回测：观察采集优雅停止、按钮变为「未开启」、回测正常跑完；回测结束后等待至少一个采集周期，确认采集**没有**自行启动；手动点「开启」后采集正常恢复推进。

**Acceptance Scenarios**:

1. **Given** 常驻采集处于开启状态 **When** 用户发起回测 **Then** 系统请求采集停止并等待其退出，退出后回测启动并跑完，全程用户未手动停采集
2. **Given** 回测已结束（成功/失败/取消任一） **When** 用户不做任何操作并等待 ≥1 个采集周期 **Then** 采集**保持停止**，界面/终端明确显示「已因回测停止，请手动启动」，无自动拉起
3. **Given** 回测结束后采集处于停止状态 **When** 用户手动点「开启」（或重新执行启动命令） **Then** 采集正常恢复推进，状态与真实一致
4. **Given** 常驻采集未开启 **When** 用户发起回测 **Then** 行为与改动前一致（不引入额外的停止/启动动作）

### User Story 2 - 撞上正在写库的采集轮：看得见的等待，随时能取消 (Priority: P1)

用户发起回测时，恰好有一轮采集正在写数据。系统不在写事务中途强插，而是先请求它在任务边界收尾；等待超过阈值仍未到边界时，进一步请求它在任务内单元边界中断（未完成部分水位不推进、下轮重跑）。等待期间界面显示真实读数（正在等什么、已等多久），用户随时可以取消本次回测。

**Why this priority**: 没有这条，用户会遇到"点了没反应"的黑箱体验；强行插队会破坏采集的写入完整性。

**Independent Test**: 在采集轮运行期间发起回测；确认出现等待提示与递增的真实读数；采集在边界停止后回测开始；全程采集不出现损坏的写入。

**Acceptance Scenarios**:

1. **Given** 有一轮采集正在写库 **When** 用户发起回测 **Then** 界面显示"正在等待采集收尾"及真实已等待时长（随时间递增），不显示任何虚构的预计完成时间
2. **Given** 处于上述等待状态且超过阈值 **When** 采集在单元边界中断 **Then** 界面如实反映"已请求中断当前任务"，且该轮状态标记为因回测停止、水位未推进
3. **Given** 处于上述等待状态 **When** 用户点击取消 **Then** 回测不再开始；采集按已发生的停止动作保持停止（不回滚、不自动重启），界面明确告知"已取消"
4. **Given** 有一轮采集正在写库 **When** 回测触发停止 **Then** 该轮在**已提交的单元边界**停下，不出现半写事务

### User Story 3 - 拿不到数据访问权就明说，绝不空跑 (Priority: P1)

无论何种原因导致回测无法获得对数据主库的可靠访问，系统都必须显式拒绝或继续等待并说明原因；绝不允许回测在没有真实数据的情况下跑完并给出看似正常的空结果。

**Why this priority**: 空数据静默跑完会导致用户基于假结果做策略判断，其危害大于"跑不了"。这是诚信底线。

**Independent Test**: 构造无法获得数据访问的时机发起回测，确认要么被显式拒绝并给出原因、要么保持等待，绝不产出"成功但全空"的结果。

**Acceptance Scenarios**:

1. **Given** 数据主库当前不可被可靠访问 **When** 用户发起回测 **Then** 不开始取数，显式告知原因并提供可选动作（重试/等待/取消）
2. **Given** 回测已开始 **When** 取数过程中数据访问中断 **Then** 回测以失败终止并显式报告，不产出部分空数据的结果文件
3. **Given** 任意失败路径 **When** 回测结束 **Then** 不留下"结果看似成功、内容为空"的产物

### User Story 4 - 停止是明确的：不会悄悄停，也不会悄悄自己回来 (Priority: P1)

因回测导致的停止必须在任何界面进程中都能被看见：按钮状态、状态栏文案、终端输出都如实反映"采集已停止（因回测）"。无论回测成功、失败、取消，还是回测进程被强杀，采集都不会被系统自动拉起；用户重启界面后仍能看到"已停止"这一事实，而不会误以为采集还在跑。

**Why this priority**: 原设计的护栏是"自动恢复"；口径改为手动后，护栏变成"停止必须可见"。否则用户会以为采集在跑而实际停摆——这比原来的手动切换更危险。

**Independent Test**: 分别让回测成功、失败、取消、进程被强杀；每次之后重启界面，确认仍显示"采集已停止（因回测）"，且采集进程确实未运行、未被自动拉起。

**Acceptance Scenarios**:

1. **Given** 回测因异常失败 **When** 异常处理完成 **Then** 采集保持停止，界面/终端明确提示需手动启动
2. **Given** 回测被用户取消 **When** 取消生效 **Then** 采集保持停止（若已停），提示一致
3. **Given** 回测期间界面进程崩溃或回测进程被强杀 **When** 用户重启界面 **Then** 仍能看到"采集已停止"状态，采集未被自动拉起
4. **Given** 采集已因回测停止 **When** 用户手动启动 **Then** 状态与真实一致，不出现"按钮显示运行但进程不存在"的假状态

### User Story 5 - 命令行与图形界面同一套语义 (Priority: P2)

习惯用命令行的用户从命令行发起回测时，享有与图形界面完全相同的停止、等待、取消、不自动重启与拒绝语义。

**Why this priority**: 项目铁律要求双端对等。

**Independent Test**: 同一组参数分别从命令行与图形界面发起，行为一致，产物逐位一致。

**Acceptance Scenarios**:

1. **Given** 常驻采集开启 **When** 用户从命令行发起回测 **Then** 停止/等待/不自动重启行为与图形界面一致，并输出"采集已停止，请手动启动"提示
2. **Given** 同一组参数 **When** 分别从两端发起回测 **Then** 两份产物逐位一致

### Edge Cases

- **回测期间用户手动停止采集**：与回测停止同义；回测结束后同样保持停止，不自动拉起。
- **等待期间采集进程自身异常退出**：以"进程已不存在"为边界继续回测，并如实告知退出原因未知。
- **连续发起多次回测**：第二次请求在第一次结束后按同样规则进入（此时代采集已停，无需再停），不得并发争用，也不得静默丢弃。
- **回测时长跨越多个采集周期**：整个回测期间采集保持停止；回测结束后**不自动恢复**。
- **回测期间跨过交易日切换**：允许读不到当日最新数据（T-1 可读即可），不得误判为空数据。
- **用户忘记重启采集**：系统持续以显式状态提示（按钮/状态栏/终端），**绝不自动拉起**；这是本次口径明确接受的代价。
- **采集进程在 60 秒内未退出**：界面提示"采集尚未退出"并给出「继续等待 / 强制终止 / 取消回测」三个可选动作，不静默挂起。
- **回测取消发生在采集已停止之后**：采集保持停止，不因取消而重启。
- **排队已满（3 个）时再次发起回测**：显式拒绝并说明当前队列与执行情况。
- **界面进程在回测期间崩溃**：采集已停止这一事实由采集侧持久状态承载，重启界面后仍可见。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 允许用户在常驻采集开启且无需手动停止采集的情况下发起回测。
- **FR-002**: 发起回测时若采集在运行，系统 MUST 请求采集**停止并退出进程**（而非仅"本轮让路但进程存活"），并在确认其退出后才开始回测。
- **FR-003**: 回测结束后采集 MUST **保持停止**，系统 MUST NOT 自动拉起；恢复必须由用户显式启动（界面点开启 / 命令行重新执行启动命令）。
- **FR-004**: 因回测导致的停止 MUST 与用户手动停止同义；界面与终端 MUST 明示「采集已因回测停止，请手动启动」，且 MUST NOT 因回测结束而复启采集。
- **FR-005**: 停止 MUST 按**分级**执行：先等当前任务跑到任务边界（默认阈值 30 秒，可配置）；超过阈值仍未到边界时，MUST 请求在任务内单元边界中断；两种情形都 MUST NOT 打断正在写入的事务（只在已提交的单元边界停下）。
- **FR-006**: 等待采集停止期间系统 MUST 显示真实读数（正在等什么、已等待时长随时间递增），不得展示未经验证的预计完成时间；阶段升级（等任务边界 → 已请求单元中断）MUST 如实反映。
- **FR-007**: 等待期间用户 MUST 能够取消本次回测；取消后回测不得开始；已经发生的采集停止 MUST NOT 被回滚或自动重启。
- **FR-008**: 回测无论以成功、失败、取消还是进程异常终止结束，采集 MUST 保持停止且 MUST NOT 被系统自动拉起；停止事实 MUST 以采集侧持久状态为准，可被后续界面进程读取。
- **FR-009**: 「采集已停止」的展示 MUST NOT 依赖仅存活于界面进程内存中的状态；界面重启或崩溃恢复后 MUST 仍能看到该状态。
- **FR-010**: 当回测无法获得对数据主库的可靠访问时，系统 MUST 显式拒绝或继续等待并说明原因，MUST NOT 在无真实数据的情况下执行回测并产出结果；判据 MUST 以**取数过程**为准。
- **FR-011**: 回测在取数过程中失去数据访问时 MUST 以显式失败终止，MUST NOT 产出内容为空但标记为成功的结果；「策略本身合法零交易」MUST NOT 被判为空数据失败。
- **FR-012**: 系统 MUST 在采集因回测停止时留下可观测留痕（停止原因、停止边界、发生时间），使该现象不会被误判为采集故障。
- **FR-013**: 同一套停止/等待/不自动重启/拒绝语义 MUST 同时适用于图形界面与命令行两个回测入口，且 MUST 在同一交付内同时可用。
- **FR-014**: 连续多次回测请求 MUST 按到达顺序串行处理，不得并发争用数据主库；排队上限为 3，超出上限时 MUST 拒绝新请求并明确告知。
- **FR-015**: 系统的这些新行为 MUST NOT 改变回测的取数口径、撮合、费用、复权与任何可观察结果数值。
- **FR-016**: 系统的这些新行为 MUST NOT 改变采集的任务集合、水位推进、写入完整性与质量审计语义。
- **FR-017**: 单元边界中断后，本轮未完成的增量 MUST NOT 推进其水位；未完成部分 MUST 在用户下次启动后重跑，且本轮状态 MUST 如实标记为「因回测停止而中断」。
- **FR-018**: 停止/中断 MUST NOT 改变采集的最终数据完整性目标——重跑完成后的数据内容 MUST 与「从未发生过回测停止」时逐位一致。
- **FR-019**: 采集进程在等待窗口内未退出时，系统 MUST 提供「继续等待 / 强制终止 / 取消回测」三个显式选项，MUST NOT 无限期静默等待。**「强制终止」仅适用于分级停止已失效的卡死场景**（非普通路径）：被强终止时，未提交的单元自然丢弃、水位不推进，由用户下次启动后的采集轮重跑补齐；系统 MUST NOT 把强终止当作常规收尾方式。

### Key Entities

- **采集轮（Collection Round）**：一次常驻采集的独立执行单元；停止与中断以轮/任务/任务内单元为粒度。
- **停止请求（Stop Request）**：回测向采集发出的"请退出"请求，复用既有停止通道；分任务边界级与单元边界级。
- **回测窗（Backtest Window）**：从"采集确认退出"到"回测结束"的区间；期间采集不得自行启动。
- **停止留痕（Stop Record）**：记录停止原因（因回测）、边界点、时间与最终状态，供界面与运维判别。
- **停止状态（Stopped State）**：采集侧持久化的"已停止"事实，界面重启后仍可读取。
- **回测请求队列（Request Queue）**：待执行回测请求的到达顺序表，上限 3，超出即拒绝。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 常驻采集开启、无需手动停采集的情形下，发起并完成回测的成功率 = 100%（连续 20 次发起）。
- **SC-002**: 回测结束后采集**保持停止**的比例 = 100%（成功/失败/取消/进程被强杀四类，每类 ≥3 次，共 ≥12 次），期间**无一次被自动拉起**；随后用户手动启动成功率 = 100%（同样本量）。
- **SC-003**: 「空数据静默跑完」的回测次数 = 0（≥10 次验证，含至少 1 个「合法零交易但取数成功」对照，不得被误判）。
- **SC-004**: 同一组参数下，「手动停采集后回测」与「采集开启时直接回测」两份产物逐位一致（哈希一致，零容差）。
- **SC-005**: 回测期间采集停止时长 ÷ 回测时长 ≈ 1（比值 0.9–1.1；从采集确认停止起算，到回测结束为止）。
- **SC-006**: 撞上正在运行的采集轮时，真实等待读数在请求发起后 1 秒内出现，且持续递增直到采集停止。
- **SC-007**: 等待期间取消回测后，100% 的情形下回测未开始，且采集保持取消时刻的真实状态（未被自动重启）。
- **SC-008**: 图形界面与命令行两个入口在同一组参数下的产物逐位一致（哈希一致）。
- **SC-009**: 回测启动后 ≤10 秒内（含既有状态去抖），界面/终端显示「采集已停止（因回测）」；回测结束后该状态**保持**，不自行消失。
- **SC-010**: 在「单任务耗时显著超过 30 秒阈值」的构造场景下，采集停止在「阈值 + 单个任务内单元耗时」之内完成（记录实测值），该轮标记为因回测中断且水位未推进。
- **SC-011**: 因回测中断后，用户重启采集完成的重跑数据与「从未发生过回测停止」的对照数据逐位一致（零容差）。
- **SC-012**: 连续发起超过队列上限（第 4 个及以后）时，100% 被显式拒绝并给出当前队列状态，无一次静默丢弃。
- **SC-013**: 采集在等待窗口内未退出时，界面 100% 呈现「继续等待 / 强制终止 / 取消」三选项（无静默挂起）。

## Assumptions

- **不做真并发**：同一时刻只有一方持有数据主库访问权。
- **允许数据滞后**：回测可读不到当日最新数据，能读到前一交易日即可。
- **停止粒度按轮/任务/任务内单元**：不做语句级中断；单元边界中断后靠「水位不推进 + 下次重跑」保证最终一致性。
- **不改数据存储引擎与版本钉版**，不做副本读、快照读、单写者服务化或存储迁移。
- **双端默认对等交付**。
- **恢复时点由用户决定**：系统不自动拉起采集；用户忘记重启导致采集停摆，是本次口径明确接受的代价（以显式状态提示缓解）。
- **每次回测会启停采集进程**：启动握手/版本闸/锁的成本可接受（用户已据此选定本方案）。
- **单轮采集时长分布未知**：不承诺具体秒数上界，但承诺分级停止与真实读数可取消。
- **常驻采集节律为每 5 分钟一跳、轮内持有数据访问、轮间释放**。
- **既有工程与运维约束不变**：回测口径、撮合、费用、PIT/复权语义、采集任务集合与水位推进保持原样。
- **计时起点**：等待读数与 30 秒阈值均从用户发起回测请求的时刻起算。
- **CLI 与 GUI 的队列差异**：命令行单次调用不排队；队列仅适用于图形界面的连续发起。

## Out of Scope

- **回测结束后自动恢复采集**（本次口径明确排除）。
- 真并发读写、物理互斥消除、副本库/快照读、单写者服务、客户端-服务器化、存储迁移。
- 数据存储引擎版本升级或放开版本闸。
- 回测结果口径、撮合、费用、复权、PIT 语义的任何变更。
- 采集任务集合、水位推进、质量审计、写入锁与 WAL 机制的变更。
- 语句级中断、按查询粒度抢占。
- 承诺"回测期间采集不停"或"回测读到当日最新数据"。
