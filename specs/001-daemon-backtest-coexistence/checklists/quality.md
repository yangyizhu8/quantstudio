# Quality Checklist: 常驻采集与回测共存（全面评审）

**Purpose**: 校验 `spec.md` / `plan.md` 作为需求与技术方案是否完整、无歧义、内部一致；不校验代码实现。
**Created**: 2026-10-27 | **Reviewer**: 用户（本清单由评审者勾选，agent 不代勾）

## A. 主流程完整性

- [ ] A1 回测窗的**起止定义**是否对每条失败路径都给出了明确终态（成功/失败/取消/强杀/预检失败）？
- [ ] A2 「采集让路」在**轮发起前**与**轮内**两种时机的行为是否都写清了，且不会互相覆盖？
- [ ] A3 回测结束后采集自动恢复的**判定依据**是否不依赖界面进程存活（含崩溃/强杀）？
- [ ] A4 分级让路的**计时起点**是否明确（从发起回测起算，还是从首次等锁失败起算）？

## B. 边界与任务类型覆盖

- [ ] B1 任务内单元边界中断对**全部采集任务类型**（全市场按天、per_stock、分片、QFQ post-ingest）是否都成立？未覆盖时是否定义了降级行为？
- [ ] B2 若某类任务内部不响应中断，spec 是否允许"退化为等任务边界"，且不破坏正确性？
- [ ] B3 采集轮在等待期间**自身失败**时的行为是否定义（继续、重试、如实告知）？
- [ ] B4 回测跨多个采集周期、跨交易日时，是否明确不发起新轮且不误判空数据？

## C. 生命周期与并发安全

- [ ] C1 **租约过期但回测仍在运行**（进程卡顿未心跳）时，daemon 恢复采集与回测持锁之间的行为是否定义且安全？
- [ ] C2 系统时钟**回拨/跳变**是否会让窗口永久有效？TTL 判定是否需用单调时钟或容差？
- [ ] C3 窗口请求文件**残留/伪造**（他人 token、断电残留）是否被安全处理？
- [ ] C4 回测请求队列与回测窗的对应关系是否明确（每个排队项各自申请窗口，还是仅 in-flight 一项）？

## D. 用户意图与交互

- [ ] D1 「用户主动停止采集」的判定依据是否可落地（停止请求已被消费删除后如何仍能识别）？
- [ ] D2 回测窗内用户再次点"启动采集"的行为是否明确（禁止发起轮 + 明确提示）？
- [ ] D3 等待态取消与「已获窗口但预检中取消」的清理路径是否都定义？
- [ ] D4 CLI 单次调用与 GUI 队列的差异是否在 spec 中显式声明（避免被读成不对称）？

## E. 诚信底线（空数据）

- [ ] E1 「取数成功证据」的**数据来源**是否明确（引擎是否已提供成功取数计数/覆盖区间；若无，谁负责产出）？
- [ ] E2 「合法零交易」与「取数失败」的区分在结果产物上是否可机检？
- [ ] E3 被拒绝/失败的回测是否**保证不产出结果目录**（含部分写出的清理）？

## F. 可观测与可回滚

- [ ] F1 留痕是否足以让用户/运维区分「因回测让路暂停」与「采集故障」？
- [ ] F2 关闭共存开关后是否 100% 回到改动前行为（不写窗口请求、不预检、不加等待）？
- [ ] F3 轮内让路是否会与既有 `stop_requested` 语义混淆（让路 MUST NOT 置 `stop_requested=true`）？

## G. 验收可判定性

- [ ] G1 每条 SC 是否都有对应的可执行验证场景（quickstart 场景 A–I 是否覆盖 SC-001～SC-010）？
- [ ] G2 「与手动停采集后同参回测逐位一致」的**基线如何获得**是否写明（何时该基线中采集确实未运行）？
- [ ] G3 等待读数的"1 秒内出现"是否有可机读的判定方式（日志/信号时间戳）？

## Notes

- 勾选权在评审者：勾上 = 该质量判据经评审满足，**不代表实现完成**。
- 评审未通过项应回到 clarify / specify / plan 补齐后重出本清单。
- 本清单为 implement 阶段的**只读门**：未勾选项会触发停等询问。
